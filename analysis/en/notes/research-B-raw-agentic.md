## 1. Differences between multi-turn agent RL and single-turn RL

1. **[Conclusive · Official documentation] Multi-turn must use token-in/token-out; converting back to text will break advantage.**
   "Conversion between Token and text may be irreversible. For example, a Token converted from `<think>` will differ from a Token generated by the LLM. During training, Tokens generated by LLM inference must be used strictly to avoid inaccurate advantage (advantage) calculation."
   Source: https://verl.org.cn/en/latest/start/agentic_rl.html 《Agentic Reinforcement Learning Training》· [Official documentation] verl (ByteDance Seed)

2. **[Conclusive · Official documentation] How to handle "prefix mismatch" in multi-turn trajectories (turn-level mask).**
   slime's Anthropic Adapter uses string-in/token-out: when tool and environment observations are appended, `loss_mask=0`; newly sampled tokens from the model are `loss_mask=1`; "If a later prompt no longer token-matches an earlier sampled output, the unmatched suffix is dropped. If the drift cuts through the middle of a previous model output, the retained prefix of that whole output turn is also assigned `loss_mask=0`." The author calls this "the important correctness guard", because "A re-tokenization mismatch can make a string-level conversation look continuous while token-level provenance is broken."
   Source: https://thudm.github.io/slime/zh/_examples_synced/coding_agent_rl/README.html 《Coding-Agent RL》· [Official documentation] slime (Zhipu / Tsinghua THUDM)

3. **[Paper interpretation] GRPO has "insufficient advantage signal" on multi-turn, requiring step-level advantage.**
   "GRPO's effective signal comes from relative differences within the group. If the rewards of samples in the group are all the same (all correct or all wrong), advantage is close to 0 and the training signal is very weak…… A trajectory is very long; the final reward differs, but credit is very chaotic——you don't know which step the reward difference comes from."
   Source: https://estrellajer.github.io/blog/2026/agentic-rl/ 《Agentic RL Survey: Tool Calling, Credit Assignment, and Training Stability——From RAP to AEPO》· [Paper interpretation] personal blog (author Maoqi Liu)

4. **[Paper interpretation] GiGPO: using "repeated states" for offline step-level grouping, with almost zero extra rollout cost.**
   "Many states appear repeatedly…… The same state has different actions, and advantages can be computed among these actions. This process does not require extra rollout; it only requires offline grouping of existing trajectories, which can be implemented with a hashmap and has very low overhead."
   Source: https://juejin.cn/post/7641403640108793875 《Long-Horizon Agentic RL: GiGPO and HGPO》· [Paper interpretation] Juejin personal blog 「松间听晚」

5. **[Paper interpretation] GiGPO's first limitation: relies on exact state matching, fails in high-dimensional/noisy environments.**
   "Anchor-state grouping relies on precise state matching (exact state matching). In environments with extremely complex, high-dimensional, or noisy state spaces, it may be difficult to find enough completely identical states, thereby weakening the effect of step-level advantage estimation."
   Source: https://blog.csdn.net/weixin_44191845/article/details/148843120 《[Paper interpretation] GiGPO Enables LLM Agent to Achieve Fine-Grained Credit Assignment》· [Paper interpretation] CSDN blog

6. **[Paper interpretation] HGPO fixes GiGPO's "inconsistent historical context causing biased step-level advantage".**
   "Even if the current state is the same, the historical context may differ. In this case, directly comparing their action returns will lead to inaccurate advantage estimation." The ablation also found: "Adding trajectory-level advantage to the final estimate as well. In most cases performance drops, indicating that trajectory-level advantage bias is too large."
   Source: https://juejin.cn/post/7641403640108793875 (same as above) · [paper explainer]

7. **【Paper explainer · checklist of diagnosable anomalies】RAGEN's collapse and RAGEN-2's diagnostic metric replacement.**
   "vanilla PPO/GRPO collapses on multi-turn agents……the manifestation of collapse is Echo Trap: early on there is diverse symbolic reasoning, and late in training it turns into repetitive, deterministic, templated responses." RAGEN-2 further points out: "reasoning collapse does not necessarily manifest as low entropy, but may manifest as low input dependence……Template collapse is a failure mode invisible to both entropy and existing metrics." The handling method is SNR-aware filtering: "each rollout round → sample G trajectories for each prompt → compute the reward variance within this prompt → keep only top-p high-variance prompts for update".
   Source: https://estrellajer.github.io/blog/2026/agentic-rl/ · [paper explainer] (Note: RAGEN/RAGEN-2 details are paraphrased from the author's notes)

8. **【Official documentation】The context budget is clamped per turn, and samples are not dropped due to excessive length.**
   Original text: "`--rollout-max-context-len` is the multi-turn prompt+response budget enforced only during generation: each turn clamps `max_new_tokens` to the remaining context. Trajectory merge/export keeps the emitted segments and does not drop them for length."; and "`--rollout-max-response-len` is the per-turn generation cap passed to each SGLang `/generate` call as `max_new_tokens`."
   Source: https://thudm.github.io/slime/zh/_examples_synced/coding_agent_rl/README.html · [official documentation] slime

9. **【Official documentation · a typical "false anomaly"】Tool call parsing failure need not be treated as a training anomaly.**
   "Note: During training, because the model may sometimes fail to generate the correct toolcall tag, the console may output the error message 'Failed to decode tool call'; this does not indicate a training anomaly."
   Source: https://verl.org.cn/en/latest/start/agentic_rl.html · [official documentation] verl

## 2. Code sandbox / execution environment instability

10. **【Established conclusion · official documentation】Grading must be done in a second clean sandbox (to prevent test-cheating).**
    slime coding-agent example workflow: "a real coding agent (claude-code CLI) drives Read/Edit/Grep/Bash/Agent tools inside a fresh sandbox per sample, the model produces a `git diff`, and the diff is graded against the dataset's test harness in a second clean sandbox (no test-cheating)."
    Source: https://thudm.github.io/slime/zh/_examples_synced/coding_agent_rl/README.html · [official documentation] slime

11. **【Established conclusion · official documentation】Treat infrastructure noise as a first-class citizen: startup concurrency cap + outer fallback timeout.**
    `SWE_BOOT_CONCURRENCY` defaults to 16, "Cap on simultaneous sandbox boots (eases h2/SSL long-tail)"; `SWE_AGENT_TIME_BUDGET_SEC` defaults to 1800 (wall clock budget for the agent to think/edit/run inside the sandbox); `SWE_EVAL_TIMEOUT_SEC` defaults to 600 (evaluation sandbox cap); `SWE_ROLLOUT_GUARD_SEC` defaults to agent+eval+180, "Outer safety net wrapping the whole rollout (boot + workspace + agent + diff + eval)".
    Source: same as above · [official documentation] slime

12. **【Official documentation】The sandbox execution service defaults to rate limiting 10 concurrency / 30s timeout, and explicitly does not handle fault tolerance.**
    "`rate_limit` Global concurrent code execution limit. Default value: 10"; "`default_timeout` Timeout for each code execution (in seconds). Default value: 30"; one motivation is to prevent 429. Original text on non-goals: "Training effectiveness is not in this scope. Observability metrics are not considered. Distributed failover and component fault tolerance are not involved."
    Source: https://verl.org.cn/en/latest/sglang_multiturn/sandbox_fusion.html 《Sandbox Fusion Tool Integration》· [official documentation] verl

13. **【Personal experience / engineering conclusion】At industrial scale, environment stability determines success or failure more than algorithms.**
    The GLM-5 team found that "nondeterministic CUDA implementations of MoE routing can cause training instability — the same input routes to different experts on different GPUs, producing different gradients. They force the use of deterministic CUDA implementations to solve this"; the author's conclusion: "When deploying algorithm-level improvements (DAPO, VAPO, etc.) at industrial scale, engineering details (asynchronous scheduling, CUDA determinism, environment stability) often determine success or failure more than the algorithm itself."
    Source: https://xavierzhang2002.github.io/agentic-rl-analysis/agentic-rl/ch1/1.4-engineering/ 《Agentic RL Survey Report · 1.4 Engineering Practice》· [paper explainer / survey] personal survey report (author zhenliang)

14. **【Official documentation】Troubleshooting order for multi-turn training OOM / generation hang.**
    "OOM is often because `max_tokens_per_gpu` is set too high" (you can first set it to `rollout_max_response_len/cp_size`); "if you have performed custom data generation, check whether, in the case of multi-turn generation, the total generation length is much longer than expected." Next: "sglang generation takes an especially long time, and GPU power is maxed out" — first check whether the stop token is not set; for "grad NaN or Inf" you can set `--no-check-for-nan-in-loss-and-grad` to skip that step; for "grad norm is very high, training crashed" first check whether the chat template matches the model.
    Source: https://thudm.github.io/slime/zh/get_started/qa.html 《Common Q&A》· [official documentation] slime

15. **【Paper explainer】The tool ecosystem itself is an "engineering problem underestimated by papers".**
    Kimi K2 covers 3000+ MCP tools; the author comments: "The complexity of the tool ecosystem (compatibility, invocation formats, and error handling for 3000+ tools) is an engineering problem underestimated by papers."
    Source: https://xavierzhang2002.github.io/agentic-rl-analysis/agentic-rl/ch1/1.4-engineering/ · [Paper explainer/survey]

## 3. Reward design for agent RL

16. **【Paper explainer · pitfalls checklist】Tool outputs must be masked; otherwise the model learns to "restate the observation".**
    Engineering details from TORL: "tool output masking (if tool outputs are not masked, the model may learn to reproduce deterministic observations rather than learn how to call tools)"; verl's official documentation also states "natively supports loss masking on external information such as tool outputs (Loss Masking)…… this is a key feature for ensuring the stability of Tool RL training".
    Source: https://estrellajer.github.io/blog/2026/agentic-rl/ ; https://syhya.github.io/zh/posts/2025-09-30-agentic-rl/ · [Paper explainer]

17. **【Paper explainer】The experience with "reward length" is a negative conclusion.**
    ToolRL: "Long reasoning traces are not necessarily better; directly rewarding length may hurt performance"; "dynamic reward scale helps transition from simple behaviors to complex behaviors", "fine-grained reward decomposition is more stable and more effective than binary reward".
    Source: https://estrellajer.github.io/blog/2026/agentic-rl/ · [Paper explainer]

18. **【Personal tutorial · concrete defense code】Four types of reward hacking and their corresponding treatments.**
    Original table wording (flaw → hacking behavior → defense): "Reward by output length → output a large amount of meaningless filler text → switch to evaluating information density and penalize repeated content"; "Reward by number of tool calls → frantically call unnecessary tools → add a penalty for redundant calls and set a maximum number of steps"; "Only look at final answer correctness → output garbled text inside `<think>` to contrive the correct answer → also check the coherence of the reasoning process"; "Use LLM scoring as the only reward → learn to output wording that pleases the scoring LLM → mix rule-based rewards and LLM rewards". Example implementation: when `token_count > 1000`, `base_reward *= 0.7`; when `tool_calls > 8`, decay by `max(0.5, 1.0-0.05*(tool_calls-8))`.
    Source: https://haozhe-xing.github.io/agent_learning/zh/chapter_agentic_rl/05_grpo.html 《Learning Agent from Scratch Chapter 10 · 5.4 Defense Mechanisms Against Reward Hacking》· [Personal tutorial] (author Ayu)
19. **【Personal tutorial · monitoring metrics】Reward variance is the first signal for judging that the reward function has failed.**
    "Reward too loose → the model can get high scores for anything and stops learning → reward variance is 0 and there is no difference within the GRPO group"; "Reward distribution monitoring: regularly check the reward distribution; if most samples' rewards tend to be the same (very small variance), it indicates the reward function lacks discriminative power and needs to be redesigned"; "Every 100 training steps, randomly sample 20 high-reward and 20 low-reward samples for manual review".
    Source: same as above · [Personal tutorial]

20. **【Paper explainer · quantitative statistics】Literature distribution of sparse rewards and Advantage Collapse.**
    The survey report tallies 47 papers: "Sparse rewards (mentioned in 16/47 papers)"; "Advantage Collapse (3 papers): when GRPO's intra-group normalization has the whole group receive the same reward, the advantage degenerates to zero and the gradient vanishes"; mitigation approaches include EDGE-GRPO "introducing an entropy term to break the advantage=0 caused by identical rewards within the group" and PF-PPO "filtering unreliable samples based on RM uncertainty and training only with high-confidence rewards".
    Source: https://xavierzhang2002.github.io/agentic-rl-analysis/agentic-rl/ch1/1.2-reward-stability/ 《Agentic RL Survey Report · 1.2 Reward Signals and Training Stability》· [Paper explainer/survey]

21. **【Paper explainer】Verifiable rewards take precedence over reward models.**
    "Use rewards that can be automatically determined as much as possible (test passes, answer matches), and avoid the bias of reward models and reward hacking"; "Long trajectories + sparse rewards make RL more unstable."
    Source: https://meko1.github.io/llm-interview-guide/advanced/agentic-rl · [Paper explainer]

## 4. Efficiency problem of long-trajectory rollout

22. **【Established conclusion · official documentation】The primary purpose of asynchronous rollouts is to "keep the GPU from waiting for tools".**
    "Because the Agent needs to interact with the environment through various tool calls, in order to avoid the GPU being idle while waiting for tool call results to return, the system uses an asyncio-based coroutine mechanism to asynchronously execute each rollout request, thereby improving training performance"; and "enables a load-balancing mechanism to balance the load across multiple GPUs and reduce the impact of long-tail requests on performance".
    Source: https://verl.org.cn/en/latest/start/agentic_rl.html · [Official documentation] verl

23. **【Established conclusion · official documentation】fully-async: maintain a fixed in-flight pool across rollouts, without waiting for the slowest sample.**
    "A background asyncio worker keeps a fixed pool of in-flight generations across rollout boundaries, so the next training step doesn't wait for the slowest in-flight sample." Its purpose is stated in the README: "Fully-async rollout, useful for long-tail agentic generation where some samples take much longer than others."
    Source: https://thudm.github.io/slime/zh/_examples_synced/fully_async/README.html ; https://github.com/THUDM/slime · [Official documentation] slime

24. **【Established conclusion · official documentation】Known costs of fully-async (staleness and reruns).**
    Original Limitations text: "No evaluation mode (would conflict with the continuous-running model)"; "Ordering across rollouts is best-effort"; "TODO: partial-rollout-style resume for `ABORTED` trajectories is not yet wired; for now the trajectory is re-queued and starts over." That is, interrupted trajectories are currently rerun in full, with no partial resume.
    Source: https://thudm.github.io/slime/zh/_sources/_examples_synced/fully_async/README.md · [official documentation] slime

25. **【Established conclusion · official documentation】partial rollout / dynamic sampling are already implemented in slime's default rollout; asynchronization corresponds to "configurable staleness".**
    "By default, `slime/rollout/sglang_rollout.py`'s `generate_rollout` function is used for data generation. This file implements an asynchronous (asyncio) data generation pipeline based on sglang, and supports features such as dynamic sampling, partial rollout, etc." The ecosystem project Relax, by contrast, "enabling fully-async training at configurable staleness".
    Source: https://thudm.github.io/slime/zh/get_started/quick_start.html ; https://github.com/THUDM/slime · [Official documentation] slime

26. **【Paper explainer · Quantification】When the degree of off-policy is high, the learning rate should be lowered, rather than hard-clipping the IS ratio after the fact.**
    VCPO: "Rather than clipping extreme IS ratios after the fact, it is better to dynamically adjust the learning step size at update time based on the 'effective sample size'"——"when there are few effective samples (a high degree of off-policy), automatically lower the learning rate." ARLArena's controlled-variable experiments give the root cause of collapse: "negative advantage + accumulation of trajectories from loose IS clipping."
    Source: https://xavierzhang2002.github.io/agentic-rl-analysis/agentic-rl/ch1/1.2-reward-stability/ · [Paper explainer/survey]

27. **【Paper explainer】Multi-turn RL lacks convergence guarantees.**
    SeeUPO "proved that traditional algorithms (PPO, GRPO) have a fundamental contradiction on multi-turn tasks: no Critic (GRAE) and training convergence cannot both be achieved"; "directly moving single-turn RL algorithms to multi-turn scenarios is theoretically wrong." Limitations: "currently validated only on conversational tasks; applicability to agent tasks with very long steps (such as software engineering) is unknown."
    Source: same as above · [Paper explainer/survey]
