## 一、这个页面是什么

小米 MiMo 团队把自己的两次强化学习大训练过程直接开放在公网上，页面自己叫 "mimo-v2.6 RL"，
副标题写的是"两次强化学习训练，mimo-v2.6-pro 和 mimo-v2.6-flash，直接从训练器的日志里读出"。
页面底部写着 "streaming since 2026-09-16 04:00 UTC"（即北京时间 09-16 12:00 开始对外直播）。

两次训练的开始时间（页面自己标的）：

| 运行 | 开始时间 (UTC) | 开始时间 (北京时间) |
| --- | --- | --- |
| mimo-v2.6-pro | 2026-09-15 10:32 | 09-15 18:32 |
| mimo-v2.6-flash | 2026-09-15 15:16 | 09-15 23:16 |

也就是说，直播开始时两次训练已经跑了大约一天半。

## 二、页面结构（三个标签页）

页面顶部有 `overview` / `metrics` / `about` 三个锚点，实际是同一页的不同视图：

### 1. overview（概览，默认页）

从上到下依次是：

1. **顶栏时间与世界时钟**：Beijing / Los Angeles / New York / London 四个城市的实时时间，外加"Toggle theme"切换深浅色。
2. **TOTAL COST**：两次训练累计花费（美元），数字每秒跳动。
3. **notices（公告）**：官方手工发布的短消息，带"N 小时前"的相对时间。截至记录时共 3 条：一次 flash 从 step 15 重跑（某类基础设施错误约 3 小时没被正确识别）、一次 pro 因某节点显存问题重启、一次离线评测成绩更新。
4. **两张运行卡片**：分别对应 pro 和 flash，各显示：
   - 运行名 + `in progress` 状态
   - 当前 step 号
   - 已运行时长（`2d 00:16:18` 这种）
   - 开始时间
   - 一行阶段提示，例如 `step 19: training · 2,616/1,568 accepted · 1h 04m in`，或 `restarting · trainer relaunched 1h 19m ago`
   - 六个数字：`dynsam/avg@n`（及相对 step 1 的变化）、`cost so far`、`tokens · step N`、`tokens · total`、`samples trained`、`train batch size × n`（固定 1,568 × 16seqs）
5. **benchmarks（基准）**：目前只有一项 DeepSWE v1.1（mini-swe-agent, avg@3），给出两次训练当前最好 step 的成绩。这个栏目更新最慢，官方公告里说"离线评测出结果就会持续贴出来"。
6. **主图表区**：横轴可切 `step` / `time`，纵轴可切 `linear` / `log`，还有一个 `smoothing` 平滑滑块。下方是 18 个指标的缩略图（official pins），每个显示两次数值的当前值与相对上一 step 的变化箭头。
7. **dynamic sampler（动态采样器）**：分 pro / flash 两块。左边是滚动日志（`feed`），每 30 秒左右一条，格式是
   `accepted 2,616/1,568 · judged 2,458 · pass 0.601 (n=12,189) · remaining 89 +1,057 partial +396 rewarding · prewarm 292`；
   右边是**当前 step 的逐数据源明细表**，列为 `source / accepted、target / remaining / judged / in flight`。
8. **batch composition（批次构成）**：可切"按数据源"或"按 harness（实际训练的）"，可切 pro / flash，可切"数量"或"占比"。目前展示的是"每个 step 训练了多少 prompt、分属哪个大类"，配一张按 step 的堆叠柱图。

### 2. metrics（指标浏览器）

左侧是一棵树，按第一级命名空间分组（`actor` 257、`critic` 324、`ctx_prompt_length` 81 …），
右上角写着 `all 2069 tags`。顶部有一个筛选框，支持子串和 `/正则/`。
点任意一个指标会弹出模态框，里面是该指标的**官方一句话说明**（如果有）、两次 run 的 `last / Δ / min / max / mean / points`，以及曲线图。
模态框打开时地址栏会变成 `#chart/<URL编码的指标名>`，可以直接分享单个指标的链接。

### 3. about（关于）

只有一句话："We are streaming our RL big runs. The mimo-v2.6 series is coming soon." 以及 X 账号 @XiaomiMiMo。

## 三、数据接口（页面背后的 JSON）

页面本身是个前端应用，数据全部来自同一域名下的公开 GET 接口。这些接口不需要登录、不需要 token，
用普通 HTTP 请求就能拿到和页面完全一样的 JSON。弄清这一点是本次能"连续监测"的前提。

| 接口 | 作用 |
| --- | --- |
| `/rl/api/runs` | 运行列表、首页固定展示的指标清单、数值格式化规则、**22 条官方指标说明**、批次构成配置、页脚文案 |
| `/rl/api/status?run=pro\|flash` | 单次运行的当前状态：成本、当前 step、阶段（`rollout` 等）、进度、累计 token / 沙箱数、重启次数，以及**每个 step 的完整事件序列**（step 值、增量、tokens、是否重跑、重启时间点） |
| `/rl/api/live?run=pro\|flash` | 动态采样器的**最新一条采样日志**，含 `latest` 汇总字段和最近 60 条滚动明细 |
| `/rl/api/notices` | 官方公告 |
| `/rl/api/benchmarks` | 离线基准成绩，按 step 组织 |
| `/rl/api/tags?run=pro\|flash` | 该运行的全部指标名（pro 2019 个、flash 2052 个）和当前数据版本号 `v` |
| `/rl/api/series?run=&v=&tags=` | 指定指标的逐步历史。指标名很长，必须分批请求，否则 URL 超长返回 414 |

页面本身每次刷新只请求首页那批指标；切换到 metrics 视图后才按需拉取更多序列。

**数据版本号**（`v`）形如 `3-5513.14.7.0`（pro）和 `3-5513.20.3.16`（flash），
两次运行的版本号不同。每次重启后 step 序列会重排（flash 的 step 16、17 带 `redo: true` 标记），
`series` 接口返回的 `steps` 数组就是当前有效的 step 列表。

## 四、更新节奏

| 内容 | 更新频率（实测） |
| --- | --- |
| TOTAL COST、运行时长、世界时钟 | 每秒（前端本地推算 + 服务端对齐） |
| 运行卡片上的 step / 阶段 / `since` | 十几秒量级 |
| dynamic sampler 滚动日志 | 约 30 秒一条 |
| 每个 step 的指标数值 | 一个 step 结束时写入，step 之间通常间隔 1.5~3 小时 |
| notices | 手工发布 |
| benchmarks | 手工更新，最慢（按天） |

**关键含义**：看板上绝大多数"曲线上的点"是**一个 step 一个点**，而一个 step 要跑 1.5~3 小时。
所以真正的高频数据只有成本、时钟、动态采样器日志、当前 step 的进度。
本项目的监测频率因此定为 20 分钟一次——足够捕捉 step 边界、重启、采样器异常，又不会产生无意义的重复数据。

```

    ├── latest.json                最新一次的精简记录
```

采集脚本在项目根目录的 `codes/scripts/` 下（按项目约定，脚本不放进 tasks 子目录）：

- `capture_mimo_rl.py` —— 采集一次全部接口并落盘
- `monitor_mimo_rl.ps1` —— 按固定间隔循环调用上面那个脚本
- `analyze_mimo_rl.py` —— 把原始快照整理成 `notes/03`、`notes/04`
- `inventory_mimo_rl.py` —— 生成 `notes/02`
