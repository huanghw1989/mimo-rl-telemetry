# 指标可信度审计：哪些数字不能信、为什么、怎么自己验证

**一句话结论：pro 的 1944 个指标里 311 个（16.0%）可以直接丢弃，259 个属于"报了 0 但其实没数据或没触发"；
抽查 12 条中文解读的实测数字，9 条只在旧的写作窗口内成立、3 条对不上；另外新定位了 3 类此前没人指出过的坏数据。**

## 摘要

这次把看板上两个 run 的全部 `series` 指标逐条过了一遍：pro 有 1944 条序列（`tags` 列出 2029 个指标名，
其中 85 个从头到尾没有任何数据），flash 有 1974 条（列出 2062 个，88 个空），逐步填充率 92.1% / 92.6%。
另外把 `content/metrics.json` 里的 109 条中文解读当成对照面，逐条核查它引用的实测数字。

命中总量：

| 类别 | pro | flash |
| --- | ---: | ---: |
| 可直接丢弃（全空或取值恒定） | 311 个（16.0%） | 290 个（14.7%） |
| 放宽到"只有两个取值"也可丢 | 362 个（18.6%） | 314 个（15.9%） |
| "报 0"（已上报但 ≥90% 的步精确为 0） | 259 个 | 230 个 |
| 覆盖率 < 50% | 139 个 | 139 个 |
| 精确/仿射重复簇 | 151 簇，其中可信 133 簇 | 151 簇，其中可信 136 簇 |
| 相邻步变化 ≥10 倍 | 214 个 | 215 个 |
| 断点数（相邻步突变） | 286 个 | 610 个 |
| 断点能被重启/版本切换/公告解释 | 43.0% | 44.4% |
| 数据里存在但没有任何解读覆盖的指标名 | 两 run 合计 1796 个（覆盖 10.6%） |  |

**最危险的三条**（都是这次新定位的，不是"再看一遍"）：

1. `train/passrate/passrate_0_ratio` 和 `train/passrate/passrate_1_ratio`（名字里带 ratio，
   看着像"这一步的比例"）实际是**累计平均**。flash 30 步里严格单调递增、增量恒为正；
   pro 在第 15、23 步各出现一次大幅回撤。把它当逐步比例读，会得到方向完全相反的结论。
2. `train/passrate/avg_passrate/visual/dataset-ol8x` 与 `.../dataset-gtav` 里的精确 0
   不是"通过率 0%"，是**没有采样到**。pro 7 个 0 值步、flash 5 个，两个数据集的 0 值步集合
   完全相同，且与"该数据集的 `partial/.../1/frac` 为 null"、"`num_accepted/step` 恰好等于 `held`"
   三者严格互相对齐。这是三类信号指向同一件事，不再是"疑似"。
3. `ctx_total_length/max`（单条轨迹的最大总长度）存在**两档截断上限**：多数指标反复取到
   1048570（≈2²⁰），但 `code/dataset-4onq` 反复取到 262144（=2¹⁸），flash 的 chat 类数据集也是
   262144。用这个指标横向比"谁的长上下文能力强"，比的是两套不同的截断阈值。

除此之外，`partial/<k>/n_tokens`（按数据新鲜度分桶的 token 计数）在旧桶上出现了
"全局、agentic 切片、某个数据集切片三个不同口径报同一个数"的重复，说明这一族在旧桶上没有分口径统计。

## 一、恒等与派生指标：不是坏数据，但会污染任何相关性排行榜

### 1.1 同名不同层级的一批指标其实是同一条曲线

**现象。** 把每条指标序列两两做相关（要求至少 6 个重叠步），pro 出现 1252011 对候选里
142 对**逐值完全相同（含 null 位置）**、48 对精确线性、6 对近似线性；flash 是 150 / 24 / 9 对。
用并查集合并后两个 run 各得到 151 个重复簇；剔除"取值几乎全是 0 或只有很少几步有值"的稀疏簇之后，
pro 剩下 133 个可信簇（覆盖 274 个指标），flash 剩下 136 个（覆盖 278 个）。

典型的簇：

- `critic/advantages/max` = `critic/agentic/advantages/max` = `critic/returns/max` =
  `critic/agentic/returns/max`（优势的最大值、回报的最大值、以及 agentic 切片的同名量，四条完全一样）。
- `critic/rewards/min` = `critic/score/min` = `critic/agentic/rewards/min` = `critic/agentic/score/min`。
- `critic/rewards/mean` = `critic/score/mean`（这条上一份笔记已经写过，这次确认在 24/30 步上仍然精确相等）。
- 每个数据集的 `critic/<cat>/dataset-<id>/rewards/min` = 同数据集的 `score/min`。

**为什么。** 这套系统里"reward"和"score"是同一个量（`critic/rewards/*` 与 `critic/score/*` 逐值相等），
"returns"和"advantages"在 max/min 这两个分位上恰好也取同一批轨迹。于是同一个物理量被抄成了
多份 tag。做相关性分析时，这些 tag 会互相把相关系数顶到 1.0，挤掉真正有信息的关系。

**验证方法。**

```
bun src/audit_report.ts
```

看输出【1】节的"完全相同/仿射精确/重复簇"行，以及 JSON 里
`identity.<run>.clustersTop[].members`（每个簇的成员清单）和
`identity.<run>.examples.identical`（逐对清单）。想手工复核任意一对，直接比较两条数组即可。

**影响。** 任何"指标相关性排行榜"必须先把这 133（pro）/ 136（flash）个高置信簇压成一个代表。
直接排序会把 `critic/rewards/mean`、`critic/score/mean` 这类同值对排到最前面，看起来是"最强关系"，
实际上只是复制粘贴。

一个额外的坑：相关性扫描本身会被**稀疏序列**骗。比如 `ctx_total_length/visual/dataset-ol8x/clip_ratio`
在 24 步里有 23 步是 0，只有一个非零值，它和另一个同样几乎全 0 的序列会"完全相关"。
脚本把这种簇单独标成 `sparse`：pro 151 个簇里有 18 个是这种假性重复，可信的是 133 个（覆盖 274 个指标）；
flash 15 / 136（覆盖 278 个）。**做这种扫描必须加稀疏过滤，否则结论会被 0 淹没。**

### 1.2 `ctx_total_length = prompt + response` 只在 `/mean` 上成立

**现象。** 逐分位核查这条加和关系：

| 分位 | pro 最大相对误差 | flash 最大相对误差 |
| --- | ---: | ---: |
| `mean` | 6.3e-6 | 7.0e-6 |
| `max` | **0.645** | **0.684** |
| `min` | **0.947** | **0.925** |

`mean` 那条在 24/30 步上仍然是精确的（误差量级就是站点只给 6 位有效数字带来的舍入）。
但 `max` 和 `min` 差到几十个百分点。

**为什么。** `max(总长)` 取的是某一条轨迹，`max(prompt)` 和 `max(response)` 取的是另外两条轨迹，
三个最大值一般不在同一条轨迹上，所以加起来不等于总长的最大值。这是数学事实，不是数据错误——
但看板把 `ctx_total_length/*`、`ctx_prompt_length/*`、`ctx_response_length/*` 三族并列展示，
很容易让人以为可以互相加减。

**验证方法。** 对同一分位取三条序列逐 step 相减：脚本 `identity.<run>.curated` 里
`ctx_total_length/<stat> = ctx_prompt_length/<stat> + ctx_response_length/<stat>` 那一行给的就是
`maxAbs` 与 `maxRel`。手工复算时注意 `mean` 的误差上限是 1 个 token 级别的舍入。

**影响。** 用 `max` 或 `min` 做"上下文预算"推算会错得很离谱（pro 上单步能差 67 万 token）。
要拆解上下文构成，只能用 `mean` 一族。

### 1.3 `perf/total_num_tokens ≈ 1568 × 16 × ctx_total_length/mean` 是近似式，不是恒等式

**现象。** 全部步都成立，但偏差系统性为负：pro 24 步偏差 −0.15%~−1.17%（平均 0.42%），
flash 30 步 −0.29%~−2.69%（平均 0.71%）。误差最大的三步是 flash 第 16、17、18 步。

**为什么。** 1568 是每步的题目数（`dynsam/num_target`），16 是每题采样的序列数。
乘积是"理论上限"，实际进训练的序列里有一部分被判无效或丢掉，所以真实 token 数总是略低。
第 16、17 步异常是因为 flash 在这两步重跑过（`events` 里各有两条 step 事件），
批次构成和其余步不同。

**验证方法。** `identity.<run>.curated` 里那条 `perf/total_num_tokens ≈ ...` 给出 `minRel/maxRel/meanRel`。
单步复核：`系列[perf/total_num_tokens][i] / (1568*16*系列[ctx_total_length/mean][i]) - 1`。

**影响。** 拿它当恒等式去"校验数据有没有被读错"会一直报假警；反过来，当偏差突然从 0.4% 跳到 2.5%
（flash 第 16 步就是这样），说明这一步的批次构成异常，值得单独看一眼。

### 1.4 `partial/<k>/n_tokens` 在旧桶上没有分口径

**现象。** pro 的桶 4~7、flash 的桶 4~9，`partial/<k>/n_tokens`（全局）、
`partial/agentic/<k>/n_tokens`（agentic 切片）、`partial/code/dataset-yfch/<k>/n_tokens`（单个数据集切片）
**逐值完全相同**（含 null 位置）。而这三者的 `frac` 各不相同。桶 0~3 没有这个现象。

**为什么。** 三个不同口径的切片报出同一个绝对计数，物理上不可能同时成立（除非三者是同一个集合）。
最合理的解释是旧桶的按切片计数没有被单独统计，落回了全局值。看板没有说明。

**验证方法。** 直接比较三条数组是否逐值相等：

```
bun -e 'const s=require("./data/store/runs/flash/series.json");
for (const k of [3,4,5]) console.log(k,
  JSON.stringify(s[`partial/${k}/n_tokens`])===JSON.stringify(s[`partial/agentic/${k}/n_tokens`]),
  JSON.stringify(s[`partial/${k}/n_tokens`])===JSON.stringify(s[`partial/code/dataset-yfch/${k}/n_tokens`]));'
```

（`require` 对 JSON 需要 Bun 的解析器，也可以直接用 `Bun.file(...).json()`。）
JSON 里对应 `identity.<run>.clustersTop` 中 `partial/<k>/n_tokens` 开头的簇。

**影响。** `partial/<k>/n_tokens` 的绝对值本来就有一半对不上账（上一份笔记第 8 条），
现在可以进一步说：**旧桶的按切片拆分不可用，只有 `frac` 可用**。任何"某个数据集在陈旧数据里占多少"
的分析，在桶 ≥4 上都会得到假的"完全相同"。

## 二、恒零与常数列：1944 / 1974 个指标里能直接丢多少

**现象。** 按"不同取值个数"分类（阈值说清楚，因为样本只有 24 / 30 个点）：

| 类别 | 判据 | pro | flash |
| --- | --- | ---: | ---: |
| 全空 | 24/30 步全是 null | 0 | 0 |
| 恒 0 | 非 null 值全是精确 0 | 226 | 204 |
| 恒 1 | 非 null 值全是精确 1 | 69 | 69 |
| 其它常数 | 只有一个非空取值，且不是 0/1 | 16 | 17 |
| 两取值 | 恰好两个不同取值 | 51 | 24 |
| 合计 | 全空 + 常数 | **311（16.0%）** | **290（14.7%）** |
| 合计（放宽） | 再加"两取值" | **362（18.6%）** | **314（15.9%）** |

**回答那个问题：pro 1944 个里 311 个（16.0%）可以直接丢，flash 1974 个里 290 个（14.7%）。**
如果接受"只有两个取值、且两种取值之间没有中间态"的指标对趋势分析没有价值，放宽到 362 / 314。

**为什么。** 恒 0 的第一大来源是判分流水线的保护性计数器和"从未触发"的分支：
`penalty/stage_credit_group` 一个族就占 pro 139 个、flash 123 个恒 0。
第二大来源是 `actor/*/pg_clipfrac` 与 `actor/*/ppo_kl`（各 25 个 tag）——这两个量在
两个 run 的全部步上都是被上报的数字 0，不是 null。恒 1 的最大一族是
`critic/*/rewards/max` 与 `critic/*/score/max`（每步都至少有一条满分轨迹），
以及 `penalty/stage_credit_group/*/pass2_success_rate`、`train/harness/*/training/nonzero_adv_rate`
（一批 harness 的"优势非零率"恒为 1）。

**验证方法。** 脚本【2】节直接给出每类的数量和按族的分布；
JSON 里 `constants.<run>.const0ByFamily`、`.const1List`、`.constOtherList`、`.twoValuedByFamily`。
逐条复算就是 `new Set(series[tag].filter(Number.isFinite)).size`。

**影响。** 别把"恒 0"当成"训练很健康"的证据（这一点上一份笔记已经警告过）；
这里补的是规模——它占了全部指标的六分之一，任何"指标总数""异常检测维度数"的说法都要先减掉这批。
`constOtherList` 里的非 0 常数更值得注意：`actor/num_zeros_in_grad_encoders` 在 pro 的 24 步里
精确等于 294705000，一次都没变过（详见第七节）。

## 三、覆盖率与"报 0"：缺失和报 0 是两件事，报 0 更危险

**现象。** 覆盖率（该指标有值的步数 / 总步数）分布：

| 覆盖率区间 | pro | flash |
| --- | ---: | ---: |
| [0, 0.1) | 30 | 16 |
| [0.1, 0.25) | 36 | 54 |
| [0.25, 0.5) | 73 | 69 |
| [0.5, 0.75) | 119 | 75 |
| [0.75, 0.9) | 3 | 61 |
| [0.9, 1] | 1683 | 1699 |

覆盖率 < 50% 的指标：pro 139 个、flash 139 个。低覆盖的族几乎全是 `partial/` 的高位桶：
`partial/7`（pro，平均 8%）、`partial/9`（flash，平均 17%）、`partial/6`、`partial/8` 等。

**为什么。** `partial/<k>/` 是"按数据新鲜度分桶"的统计，桶号越大表示数据越旧。
桶号大的桶只有在训练连续跑了很多步之后才会出现，所以天然只有后几步有值——**这是设计使然，不是缺数据**。
真正的"断供"是另一类：pro 有 218 个指标在某个步之后再也不上报（尾部断供），
flash 177 个；pro 有 186 个指标中间有洞，flash 274 个。

**验证方法。** 脚本【3】节给出直方图、<50% 的族、断供族、中间有洞的族；
JSON 里 `coverage.<run>.hist`、`.below50Families`、`.trailingCutByFamily`、`.interiorMissingByFamily`。
手工检查某个指标：`arr.map(v => v===null)` 看 null 的位置是"只在尾部"还是"中间也有"。

**"报 0"单独统计。** 已上报（非 null）但 ≥90% 的步精确等于 0 的指标：pro 259 个、flash 230 个。
按族：

| 族 | pro | flash |
| --- | ---: | ---: |
| `penalty/stage_credit_group` | 144 | 127 |
| `actor` | 56 | 57 |
| `critic` | 28 | 19 |
| `ctx_total_length`（各数据集 `clip_ratio`） | 18 | 13 |
| `train` | 8 | 8 |
| `penalty/action` | 3 | 3 |
| `penalty/signed` | 2 | 2 |
| `env` | 0 | 1 |

**影响。** 这 259 / 230 个指标在"缺失值检查"里全部通过（它们有值），在"是否有异常"里全部通过
（值是 0）。它们是最容易被静默忽略的一批。要么明确写"这一族当前不工作"，要么从看板拿掉。
其中 `ctx_total_length/<cat>/dataset-<id>/clip_ratio`（单个数据集被截断的轨迹占比）特别值得单列：
pro 25 个数据集里 18 个、flash 25 个里 13 个有 ≥90% 的步是精确 0，剩下的一两个非 0 值往往
是"一条轨迹"的量级（1e-3 量级），这更像是"长尾还没堆起来"而不是"没有截断"。

### 3.1 ol8x / gtav 的精确 0：三类信号严格对齐，可以定性为"未采样哨兵"

**现象。** `train/passrate/avg_passrate/visual/dataset-ol8x` 和 `.../dataset-gtav`
（这两个数据集的逐步平均通过率）在两个 run 里都出现精确 0：

- pro：两个数据集各 7 个 0，步号都是 **1, 2, 3, 11, 15, 17, 23**（两个集合完全相同）。
- flash：各 5 个 0，步号都是 **1, 3, 16, 25, 28**（同样相同）。

同一批步上还有两件事同时发生：

- `partial/visual/dataset-<id>/1/frac`（这个数据集在"陈旧 1 代"桶里的占比）为 **null**；
- `dynsam/visual/dataset-<id>/num_accepted/step`（本步受理题数）恰好等于
  `.../num_accepted/held`（题池持有量）。

三者的步号集合**完全一致**（脚本逐格核对，pro/flash 四个数据集全部 `true`）。

**为什么。** 受理数等于持有量，意味着这一步这个数据集的题池没有净消耗；对应的 `partial/.../1/frac`
为 null，意味着这一步它根本没有数据进入训练。在这种情况下"平均通过率"没有分母，
正确写法是 null。实际写成了 0，于是 0 被读成"这一步一道都没做对"。
从时间上看，pro 的这 7 个步与 `events` 里的重启步完全重合（重启落在
1(×2)、2、3、11、15(×2)、17(×2)、23(×2)），flash 的 5 个步是 4 个重启步加上第 1 步（run 起始步）。
**两个数据集共享同一套 0 值步，说明这是按步发生的上报行为，不是这两个数据集自身的数据问题。**

**验证方法。** 脚本【11】节把三件事的步号并排列出，并给出 `alignedWithBucket1Null` /
`alignedWithStepEqHeld` 两个布尔值。手工复算：

```
对每个步 i：
  zero   = series["train/passrate/avg_passrate/visual/dataset-gtav"][i] === 0
  noData = series["partial/visual/dataset-gtav/1/frac"][i] === null
  flat   = series["dynsam/visual/dataset-gtav/num_accepted/step"][i]
           === series["dynsam/visual/dataset-gtav/num_accepted/held"][i]
三个布尔值应完全一致（pro 7 步 / flash 5 步）。
```

**影响。**

- 这两个数据集的通过率曲线在重启步上是断的，不是"掉到 0"。任何"重启后质量暴跌"的读法都是错的。
- 计算"视觉类数据集平均通过率"时，这些 0 会把均值拉低。pro 第 15 步的视觉类 6 个数据集里，
  按原样平均是 0.4420，把这两个"无数据"的 0 剔除后是 0.6630——**差 22 个百分点**。
  第 2、17、23 步的差额分别是 20.7、20.9、23.7 个百分点。这个量级的偏差足以改变结论。
- 反过来，如果拿"三个信号一致"当检测器，可以用它**不依赖 `events` 就找出重启步**：
  pro 是 {1,2,3,11,15,17,23}，flash 是 {1,3,16,25,28}。

## 四、哨兵值：除了 0 和 1，还有"反复出现的整齐大数"

**现象。** 用"某个整齐值（精确 0、精确 1、2 的整数次幂、10 的整数次幂、贴近这些值）在已上报步里
占比 ≥50% 且该指标不是常数"作判据，pro 命中 78 个指标、flash 77 个。除了 3.1 的 ol8x/gtav，
另有两类值得单列：

1. **反复出现的两取值"计数器"**。例如
   `penalty/stage_credit_group/harness/harness-A/groups_judged_after_drop`
   在 pro 24 步里有 23 步是 0，只有 1 步是 1；flash 的
   `actor/chat/dataset-eup7/pg_tis_clipfrac_pos_high` 30 步里 29 步是 0，唯一非 0 是 7.6e-8。
   这类序列的"均值""趋势""相关性"全都没有意义。
2. **撞上限的长上下文指标**。`ctx_*_length/*/max` 在 pro 有 7 个、flash 有 10 个指标
   反复取到某个整齐大值，而且那个值就是该指标全期的最大值：

| 上限档 | pro 命中指标 | flash 命中指标 |
| --- | ---: | ---: |
| 1048570（≈2²⁰，即 2²⁰−6） | 5 个（全局 `ctx_total_length/max` 11/24 步、`ctx_total_length/agentic/max` 11/24、`code/dataset-yfch/max` 9/24 等） | 7 个（`ctx_total_length/cyber/dataset-9aui/max` 13/30、全局 15/30 等） |
| 262144（=2¹⁸） | 2 个：`chat/dataset-lm3t/max` 7/24、`code/dataset-4onq/max` 16/24 | 3 个：`chat/dataset-lm3t/max` 14/30、`code/dataset-4onq/max` 25/30、`chat/dataset-eup7/max` 6/30 |

**为什么。** 第一类的 0 大多是"这个分支没触发"，0 是真值但不是"比例为零"的意思。
第二类的两个整齐值都贴着 2 的整数次幂，是典型的截断阈值（token 上限）。两档并存说明
**不同数据集/不同模块的截断长度不一样**：多数走 2²⁰，`code/dataset-4onq` 和部分 chat 数据集走 2¹⁸。

**验证方法。**

```
bun src/audit_report.ts    # 看【4】【12】两节
```

JSON 里 `sentinels.<run>.sentinelCandidates`（每个候选给出值、出现次数、已上报步数、占比、其他取值），
`caps.<run>.tiers`（按上限值分档）。手工复核某个指标：

```
const a = series["ctx_total_length/code/dataset-4onq/max"].filter(Number.isFinite);
a.filter(v => v === 262144).length / a.length      // 应该 ≈ 0.67（pro）
Math.max(...a) === 262144                          // true，说明它就是上限
```

**影响。**

- 用 `ctx_total_length/<cat>/dataset-*/max` 比较数据集之间的长上下文能力，比的是两套阈值。
  `code/dataset-4onq` 的天花板是别人的四分之一，它在图上永远"更短"，这与模型能力无关。
- 更重要的一处细节：**1048570 不是硬上限。** flash 的 `ctx_total_length/max` 里有
  1049640、1048610、1048690、1054990 四个值高于它，还有第 14 步的 2236430（约为上限的 2.13 倍）。
  pro 也有 105 万以上的值。所以"这个量一定 ≤ 2²⁰"的假设是错的，不能拿它当数据校验规则。
- `actor/num_zeros_in_grad_encoders` 恒等于 294705000（pro 24 步，flash 没有这个 tag）。
  它既不是 2 的幂也不是 10 的幂，但它一次都没变过。见第七节。

## 五、尺度与量纲：跳变很多，真正的越界是 0 个

### 5.1 相邻步变化 ≥10 倍的指标有 214 / 215 个，绝大多数是分桶结构

**现象。** pro 214 个、flash 215 个指标在相邻两步之间变化超过 10 倍。变化倍数最大的几个：

| 指标 | 变化 | 步 |
| --- | --- | ---: |
| flash `partial/visual/dataset-ve5o/0/n_tokens` | 1629 → 57318600（×35186） | 16 |
| flash `partial/visual/dataset-ve5o/0/frac` | 0.0000299 → 1（×33398） | 16 |
| flash `partial/code/dataset-yfch/0/frac` | 0.0000913 → 1（×10948） | 16 |
| pro `critic/code/dataset-zg6q/advantages/mean` | 3.49e-6 → −0.007698（×2206，符号翻转） | 9 |
| pro `partial/visual/dataset-ve5o/0/n_tokens` | 50424 → 58943500（×1169） | 23 |

**为什么。** 大部分是"桶刚开启"：`partial/<slice>/<k>/{frac,n_tokens}` 里，某个陈旧度桶在这一步之前
没有数据（`frac` 极小或为 null），这一步突然有了，于是 `frac` 从 ~0 跳到接近 1。
这是分桶统计的正常开端，不是异常。按这个判据扣除后，pro 真正需要看的跳变是 194 个、
flash 186 个——仍然很多，其中大部分是"接近 0 的量在符号或量级上翻转"
（例如上面的 `critic/*/advantages/mean`，从 −1e-5 级别翻到 −1e-2 级别）。
这类量的相对变化没有意义，**要看绝对变化**。

**验证方法。** 脚本【5】节列出跳变清单，JSON 里 `scale.<run>.jumps[].bucketOpen`
标记了哪些属于"分桶开启"。手工复核某个指标：找出相邻两步的比值，再看这两步的
`partial/.../frac` 是不是从 null/极小变到 1。

**影响。** 用"变化超过 10 倍"当异常报警线会得到 200 多个报警，等于没有报警。
要么先过滤分桶族，要么改用"绝对变化 / 该指标自身的 MAD"（见第六节）。

### 5.2 越界检查：比例类没有越界，计数类没有负数

**现象。** 对名字以 `frac`、`ratio`、`rate`、`share`、`pct`、`clipfrac`、`zero`、`one`、`mid` 结尾的
指标检查是否落在 [0,1] 之外；对名字含 `num_`、`n_tokens`、`count`、`rollouts`、`groups`、`tokens`
的指标检查是否为负。**两个 run 都是 0 个越界。**

`ctx_total_length/clip_ratio`（被截断的轨迹占比）pro 最大 9.18e-4、flash 最大 3.10e-3，都没到 1。
`actor/clip_high` / `actor/clip_low`（PPO ratio 的裁剪上下界）在两个 run 的全部步上分别是 0.27 和 0.2。

**为什么。** 站点显然在写日志前做了 clamp，或者这些量本身就不可能越界。
"没有越界"本身是个有用的结论：它意味着**如果哪天出现越界，那就是真的出事了**，
可以放心把它当成一条硬报警线。

**验证方法。** 脚本【5】节最后两行给出 `outOfRange` 的条数和 `clip_ratio` 的范围；
JSON 里 `scale.<run>.outOfRange`（空数组就是没有）、`.clipRatio`、`.clipBounds`。

**影响。** 这条是"数据没坏"的正向证据，值得写进校验脚本——它比"看起来正常"强，
因为它是可判定的。

## 六、结构性断点：pro 的"第 15 步最多"这个说法已经不成立

**判据。** 对每个指标，取相邻两步的差 `Δ`，用这个指标自身差分的中位数绝对偏差
（MAD，median absolute deviation，一种对离群点不敏感的波动度量）当尺度：
`|Δ| / (1.4826 × MAD) > 8` 且相对变化 > 5% 记为一次断点。这样做的好处是每个指标按自己的
常态波动定标，不会像"变化 10 倍"那样把平稳的小量误报。

**现象。** pro 共 286 个断点，flash 610 个。断点最多的步：

| | 原始计数前 6 | 除以该步可比对指标数后前 6 |
| --- | --- | --- |
| pro | 14:29、22:29、23:29、15:24、21:24、7:16 | 23:1.66%、22:1.60%、14:1.60%、15:1.44%、21:1.34%、20:0.91% |
| flash | 25:60、3:42、30:39、29:35、28:33、16:32 | 25:3.29%、3:2.45%、30:2.24%、29:2.06%、28:1.92%、16:1.89% |

**独立复核结论：**

- flash 侧，"断点最多的是第 25 步"**成立且更明显**（原始计数 60，是第二名的 1.4 倍；
  归一化后 3.29%，是第二名的 1.3 倍）。第 25 步确实有两次重启落在同一步区间里。
- pro 侧，"断点最多的是第 15 步"**不再成立**。第 15 步现在排第 4（24 个），
  第 14、22、23 步各 29 个并列第一。原因很直接：上一份分析写在 pro 只跑到第 19 步的时候，
  第 20~24 步是后来才有的，而第 22、23 步正好卡在指标集版本从 2019 个变成 2029 个的位置。

**"有多少断点能被外部事件解释"。** 把"这一步区间内发生过重启、或版本号切换、或有公告"
定义为事件步。pro 有 11 个事件步（1,2,3,11,15,16,17,18,20,23,24），落在其上的断点 123/286 = **43.0%**；
flash 有 9 个（3,16,19,20,21,25,26,27,28），落在其上的断点 271/610 = **44.4%**。
**也就是说超过一半的断点没有外部事件对应。**

断点最多、又没有外部事件的步：

- pro：14（29 个）、22（29）、21（24）、7（16）、6（14）、19（11）。
- flash：30（39）、29（35）、2（30）、4（29）、17（24）、24（21）。

**为什么。** 断点集中在少数几步，一部分来自重启（重启后重新预热，采样分布会变，
上一份笔记第 2 条已经讲过机制）；一部分来自版本切换（新 tag 出现、旧 tag 消失，指标集换了）；
剩下的一大部分是**指标自身的稀疏结构**：很多指标只在部分步有值，一旦上一步/这一步的值对
出现在"桶刚开启"的边界上，就会记一次断点。

**验证方法。** 脚本【6】节给出每步的原始断点数、归一化断点数、事件步清单、
以及"墙钟 vs 上报耗时"的缺口表。JSON 里 `breakpoints.<run>.counts`（逐步计数）、
`.ranked`、`.rankedRate`，以及 `eventAlignment.<run>.intervals`（每个步区间的
`restarts` / `notices` / `versions`）。

手工复算某一步的断点数：对每个指标算 `Δ` 序列、MAD、然后数 `|Δ|/(1.4826MAD) > 8 && rel > 0.05`。

**影响。** 把"断点最多"直接当成"这一步出事了"是不成立的：44% 的断点有事件对应，
另外 56% 需要用别的信号（比如 3.1 的三元对齐、或者下面的墙钟缺口）去区分。

### 6.1 flash 第 25 步：两次重启映射到同一步，墙钟比上报多 4.5 小时

**现象。** 把每个重启事件的时间戳落到"第一个完成时间晚于它的步"上：

| run | 重启映射到的步 | 同一步内多次重启 |
| --- | --- | --- |
| pro | 1(×2)、2、3、11、15(×2)、17(×2)、23(×2) | 1、15、17、23 |
| flash | 3、16、25(×2)、28 | 25 |

flash 第 25 步的区间墙钟是 7.51 小时，而 `timing_s/step` 只报了 3.02 小时，差 4.49 小时。
这一步的断点数（60）也是全场最高。

**为什么。** `timing_s/step` 不含重启等待（上一份笔记第 1 条），而第 25 步里塞了两次重启，
所以缺口全部体现在这一步。平均步长约 1.6~2.5 小时，7.51 小时等于把三步的墙钟压进了一个步号。
看板把这一步画成一个点，但它实际上跨了三个"正常步"的时间。

**验证方法。** 脚本【6】节最后一节直接列出"墙钟、上报、缺口、区间内重启数"四列，
按缺口排序。手工复算：取 `events` 里连续的 step 事件时间戳相减得到墙钟，
减去 `series["timing_s/step"]` 就是缺口。

**影响。** flash 第 25 步的任何"单位时间"派生量（每秒 token、每小时成本、吞吐）都不可比；
这一步的 `partial/0/frac`（新鲜数据占比）反而是 0.844，与 pro 第 15 步 1.000 的"全新鲜"不同，
所以也不能简单套用"重启步 = 全新鲜"的规律。

## 七、指标生命周期与语义漂移：`tags.json` 的两个时间戳都不能直接用

### 7.1 `first_seen` 被改写，`last_seen` 全部等于最近一次同步

**现象。** pro 的 `tags.json` 里 2029 个指标的 `first_seen` 只有三个值：
2011 个是 1789642198（遥测第一次记录的时刻）、5 个是 1789706684、13 个是 1789787223。
`last_seen` 则**全部 2029 个**都等于最近一次同步时间。flash 同样：2040 / 7 / 15，`last_seen` 2062/2062 全等。

进一步核对仓库自己的历史（`git show 1810150:...tags.json` 对比当前文件）发现，
`partial/visual/dataset-gtav/{1/frac, 1/n_tokens, avg_staleness}` 三个 tag 的 `first_seen`
在旧版本里是 1789642198（第一次记录），现在是 1789787223（晚 40 小时）。

**为什么。** `last_seen` 的更新条件是"这一轮同步时该指标还在列表里"，而当前所有 tag 都在，
所以它退化成"最近同步时间"，**不能用来找消失的指标**。`first_seen` 被改写说明它记录的是
"遥测最近一次看到它出现的时间"，中途消失又回来的指标会被重新计时。再加上遥测本身是
**左截断**的（第一次同步时 pro 已经跑到第 14 步），第 14 步之前出现或消失的指标完全看不到。

**验证方法。**

```
bun -e 'const t=await Bun.file("data/store/runs/pro/tags.json").json();
const f={},l={}; for(const v of Object.values(t.tags)){f[v.first_seen]=(f[v.first_seen]||0)+1;l[v.last_seen]=(l[v.last_seen]||0)+1;}
console.log(f,l);'
git show 1810150:data/store/runs/pro/tags.json > /tmp/old.json   # 与当前文件比对
```

脚本【7】节直接打印两个直方图。

**影响。** 任何"指标生命周期"分析只能得到两个结论：中途**新增**的（`first_seen` 晚于第一次记录）
可以信，pro 18 个、flash 22 个；中途**消失**的不能从 `tags` 直接读，必须用下面这个方法。

### 7.2 用"版本里的指标总数"减"新增数"反推消失：pro 8 个、flash 12 个

**现象。** `tags.json` 的 `versions` 数组记录了每次版本切换时的指标总数 `n`。
把相邻两次版本之间的"新增数"（`first_seen` 落在区间内的 tag 数）和 `n` 的变化放在一起：

| run | 版本区间 | n 变化 | 新增 | 反推消失 |
| --- | --- | ---: | ---: | ---: |
| pro | 14.7.0 → 15.8.15 | 0 | 0 | 0 |
| pro | 15.8.15 → 17.10.17 | 0 | 5 | **5** |
| pro | 19.10.17 → 22.12.23 | +10 | 13 | **3** |
| flash | 21.3.16 → 22.3.16 | +4 | 7 | **3** |
| flash | 22.3.16 → 26.4.25 | +6 | 15 | **9** |

合计 pro 消失 8 个、flash 消失 12 个。

**为什么。** `n` 是站点在那一刻返回的指标总数，`first_seen` 是遥测记的新增。
两者相减就是"这一区间内消失了多少个"。**但消失的指标名字读不出来**——
`tags.json` 只保留当前存在的指标；遥测也没有存历史 tag 列表。

**影响。** 用它来解释"某个指标怎么突然没了"是可行的；
但**具体是哪些**只能靠外部公告和常识猜。已知能对上的两处：

- pro 有 52 个指标最后有值在第 14 步：其中 42 个名字里带 `cyber`（`actor/cyber/dataset-9aui/*`、
  `dynsam/cyber/dataset-9aui/*`、`env/cyber/dataset-9aui/active` 等），与公告
  "we also removed the cyber dataset from the upcoming pro run"（2026-09-17T12:20Z）对得上。
  **但剩下 10 个与 cyber 无关**：`train/harness/harness-R/training/` 下的 6 个
  （`advantage_mean`、`negative_adv_rate`、`nonzero_adv_rate`、`positive_adv_rate`、`rollouts`、
  `trained_rollout_share`），加上 4 个零散的 `partial/` 桶标签。这 10 个的消失没有公告解释。
- flash 有 4 个指标最后有值在第 19 步、之后 11 步全空：`penalty/signed/pos_scale_clamped`、
  `penalty/stage_credit_group/dev_neg_turns`、`.../end2end_success_rate`、`.../groups_attempted`。

### 7.3 语义漂移（同名指标换了口径）：找到的候选只有 4 个，而且都不是"整体换数量级"

**现象。** 用两种判据找：一是"以版本切换点为界，前后两段的中位数比值 ≥10 且取值区间不重叠"，
二是"把序列任意切成两段，找中位数比值最大且区间不重叠的那一刀"。

- 按版本切换：pro 0 个，flash 1 个。
- 按任意切分：pro 0 个，flash 3 个。

全部候选：

| 指标 | 切点 | 中位数变化 | 倍数 |
| --- | --- | --- | ---: |
| flash `partial/visual/dataset-pt5v/2/n_tokens` | 第 14 步 | 2026580 → 44953600 | ×22.2 |
| flash `partial/visual/dataset-pt5v/2/frac` | 第 19 步 | 0.0568 → 0.7509 | ×13.2 |
| flash `ctx_response_length/general/dataset-trla/min` | 第 6 步 | 349 → 3822 | ×11.0 |
| flash `partial/visual/dataset-pt5v/2/n_tokens` | （版本 21.3.16，第 20 步） | 3670705 → 56273800 | ×15.3 |

**为什么。** 这四个都是 `partial` 桶或 `min` 这一类统计量：`partial/.../2/*` 是"陈旧 2 代"的桶，
在训练前期这个桶根本没有数据，后期才逐渐有值，所以"前段中位数小、后段中位数大"是桶的成长，
不是口径改变。`ctx_response_length/*/min` 是单条最短轨迹的长度，取值本来就在几百到几千之间跳。

**验证方法。** 脚本【8】节（按版本）与【14】节（任意切分）分别列出候选，
JSON 里 `drift.<run>.driftHits` 和 `levelShift.<run>.hits`。每个候选都给了切点步、前后中位数、倍数。
手工复核：把该指标按切点分两段，各取中位数和取值范围。

**影响。** **没有找到"同名指标悄悄换了数量级"的证据。** 这是一个重要的否定结论：
这次数据里没有出现那种"指标名没变、含义变了"的最危险情况。
反过来说，用"中位数比值 ≥10 且区间不重叠"这个判据能扛住桶成长和重启的干扰，
可以放进常规校验。

### 7.4 两个 run 之间同名指标的行为不一致（比版本漂移更隐蔽）

**现象。** `actor/num_zeros_in_grad_vocab`（梯度里为零的 vocab 维计数）：

- flash：**30 步全部是精确 0。**

`actor/num_zeros_in_grad_encoders` 则是 pro 恒为 294705000、flash 根本没有这个 tag。
`actor/update_successful` 只在 flash 存在且恒为 1。

**为什么。** 这三个 tag 属于同一族优化器诊断量，但两个 run 的上报口径不同：
pro 统计了 vocab 和 encoder 两部分，flash 只统计了总和且 vocab 部分恒 0。
看板上它们用同一个前缀并列，看不出这个差别。

**验证方法。**

## 八、文档与数据一致性：109 条解读里抽查 12 条，9 条只在写作窗口内成立、3 条对不上

### 8.1 整体情况：解读的写作窗口是 pro 19 步 / flash 25 步，数据已经到 24 / 30

**现象。** `content/metrics.json` 的 109 条解读里，有 `observed`（"这一轮实测"）字段的条目，
引用的步号范围全部止于 pro 第 19 步、flash 第 25 步。而当前 `series` 是 pro 24 步、flash 30 步。
逐条抽查 12 条含具体数字的解读（脚本【9】节）：

- **9 条在解读自己的写作窗口内能精确复现，但对当前全期已经过期。**
  例如 `dynsam/avg@n` 写"flash 第 25 步 0.640833，最高就是末步"——
  第 25 步的值确实是 0.640833，在 ≤25 步里确实是最高；但全期最高已经变成第 29 步的 0.662291，
  当前末步（第 30 步）是 0.643526。`critic/rewards/max` 写"全步都是 1"，
  现在 24+30=54 个值仍然全是 1，只有"共 44 个值"这个计数过期了。
- **3 条对不上。**

### 8.2 三处对不上的地方（这是给文档纠错）

**错误 1（硬错误）：`ctx_total_length/max` 的 flash 上限步数写错了。**
解读原文："flash 25 步里有 17 步等于 1048570"。实测在 flash 第 1~25 步里，
`ctx_total_length/max` 精确等于 1048570 的只有 **13 步**（第 6、7、9、12、13、15、18、19、20、21、22、23、24 步），
不是 17。同一处说法在 `ctx_total_length/mean` 那条解读里又出现了一次（"pro 有 8/19 步、flash 有 17/25 步"），
pro 的 8/19 是对的，flash 的 17/25 是错的。这个数字是"上限确实存在"这件事的核心证据，
写错会削弱结论。

**错误 2：`benchmark/lag`（离线榜比训练落后几步）写的是"恰好 4 步"。**
实测现在 pro 榜到第 18 步、训练到第 24 步（差 6），flash 榜到第 25 步、训练到第 30 步（差 5）。
"恰好都是 4"当时大概是巧合：离线评测成绩是人工补录的，训练在跑、榜单不会同步跟。
**这条不该写成一个稳定的数字，应该写成"榜单滞后随训练推进而变大"。**

**错误 3：`perf/total_num_tokens` 的 flash 偏差上限对不上。**
解读写"flash −0.29% ~ −2.77%（平均 0.77%）"。在 ≤25 步窗口内实测是
−0.29% ~ **−2.69%**（平均 0.76%）；全期是 −0.29% ~ −2.69%（平均 0.71%）。
误差最大的步仍然是第 18、16、17 步，与解读的定性描述一致。
**推测**（标注为推测）：第 16、17 步在 flash 上被重跑过，`series` 里的值被重写，
偏差从 −2.77% 变成 −2.69%。旧值已无法从当前仓库复现。

### 8.3 解读覆盖了但数据里根本没有的指标

- `dynsam/avg@n_no_infra`：解读自己就写了"本仓库没有数据"，核对无误——
  两个 run 的 `tags` 与 `series` 里都没有它。官方 22 条说明里有它，但站点没有上报。
- `penalty/stage_credit_group/always-zero`：这是一个"组条目"（把一批恒 0 计数器合并讲一条），
  不是一个真实指标名，属于正常写法。

另外核查官方 `descriptions`（`meta.json` 里的官方指标说明）指向的 22 个名字，
其中 **2 个在数据里完全不存在**：`dynsam/avg@n_no_infra` 和
`dynsam/passrate/hist9_ratio`（后者官方还专门给了 `hist_prefix` 前缀，
但两个 run 的 `series` 里没有任何 `hist9` 开头的指标）。

### 8.4 数据里有、但完全没有解读覆盖的指标

109 条解读的 id 展开后（含通配和族匹配）只命中了 pro+flash 去重后 2009 个指标名里的
**213 个（10.6%）**，剩下 **1796 个**没有任何解读。按族排（族内指标数）：
`penalty/stage_credit_group` 507、`critic` 289、`actor` 210、`train/harness` 138、
`partial/code` 108、`partial/visual` 54、`train` 49……

**验证方法。** 脚本【9】节的 `perId` 表给出每条解读 id 命中的指标数，
`uncoveredByFamily` 给出未覆盖的族分布，`priorityFamilies` 给出按"族内指标数 × 平均覆盖率 ×

**影响。** 解读的覆盖面和数据的面不是一个量级。现在的 109 条更像是

## 十、最该补解读的 10 个

排序依据：族内指标数量、平均覆盖率、取值波动幅度，再人工剔除"已经被别的条目顺带讲过"的。
脚本给出候选表（`docAudit.priorityFamilies`），下面是我挑的 10 个并说明理由。

1. **`critic/<cat>/dataset-<id>/advantages/{mean,min,max}`**（约 290 个未覆盖）。
   这是价值网络的原始输出，但 `advantages` 与 `returns` 的 max/min 完全相同（第 1.1 节），
   而 `advantages/mean` 与 `returns/mean` 又是另一组。不解释清楚，读者会以为是两组独立信号。
2. **`critic/<cat>/dataset-<id>/rewards/min`**（含在上一项里，但值得单列）。
   大量数据集在这一族上 ≥90% 的步精确为 0（pro 28 个 `critic` 指标属于"报 0 派"），
   且与 `score/min` 逐值相等。这是"稀疏 0 哨兵"最集中的地方之一。
3. **`penalty/stage_credit_group/select_v4/*` 的四个 rate**：
   `select_hack_attempt_rate`、`select_pass_new_tests_rate`、`select_probe_disagree_rate`、`select_r3_rate`。
   现有解读只讲了这条流水线的计数和通过率，没讲这四个率；它们的量级在 0.4~0.7，
   是这一族里少数真正在动的信号。
4. **`penalty/stage_credit_group/<harness>/…` 与 `select_v4_nogold/…` 两套平行前缀**。
   同一批指标按 harness 和按"是否有 gold 用例"各切了一遍，加起来 507 个未覆盖指标。
   不说清楚这两套切分的关系，读者无法知道该看哪一套。
5. **`train/harness/<harness>/training/{advantage_mean,negative_adv_rate,nonzero_adv_rate}`**（138 个未覆盖）。
   这是"哪个 agent harness 产出的训练信号更好"的唯一入口，而 `nonzero_adv_rate` 在一批 harness 上恒为 1。
6. **`train/passrate/avg_passrate/<cat>/dataset-<id>`**（49 个 `train` 未覆盖的多数）。
   顶层 `avg_passrate` 有解读，按数据集拆开的没有；而 3.1 的哨兵问题正出在这一族上。
7. **`ctx_total_length/<cat>/dataset-<id>/max` 与 `/clip_ratio`**（44 + 18 个未覆盖）。
   第四节证明这一族有两档截断上限；不写清楚，横向比较必然出错。
8. **`partial/<k>/train_infer_diff/new_infer/*`**（桶级 KL 与尾部分布）。

9. **`actor/<cat>/<dataset>/pg_tis_clipfrac{,_pos_low,_pos_high,_neg_low,_neg_high}`**（约 130 个）。

   现有解读里"低边界一侧比高边界一侧高一个数量级"这个结论需要靠它们复算。
10. **`dynsam/<cat>/<dataset>/num_accepted/{step,held,carryover}` 里的虚拟数据集行**。

## 十一、我们看不懂的地方（不用猜测补齐）

1. **`actor/num_zeros_in_grad_encoders` 恒等于 294705000。**
   pro 24 步一次没变，flash 没有这个 tag。它既不是 2 的幂也不是 10 的幂，

   第 23 步没有任何公告。**回撤的触发条件不知道**，所以这两个指标只能按"累计平均、回撤点之后不可比"来用。
4. **`partial/<k>/n_tokens` 的旧桶为什么三个口径报同一个数。**
   已确认现象（第 1.4 节），但不知道是回退、是复制、还是这三个切片真的重合。

5. **`partial/<k>/n_tokens` 加起来只有 `perf/total_num_tokens` 的一半左右。**
   上一份笔记已经记过这条，这次确认它在 24/30 步上仍然成立（pro 45%~55%、flash 44%~56%）。
   **另一半 token 记在哪里，不知道。**

   1048570 与 262144 两档并存，而且还有 1049640、1048690、1054990、2236430 这些超过上限的值。

7. **`penalty/stage_credit_group` 那一族的具体语义。**
   996 个指标、没有官方说明，命名只能直译。本文只把它当成"恒 0 占比最高的一族"统计，

   "每 12 步重复一次"这种周期序列。本文没有对周期性做检测，这是一个已知的盲区。

## 十二、怎么自己复算

```
# 从项目根目录
bun src/audit_report.ts
```

脚本会打印全部【0】~【15】节，并写出 `analysis/zh-CN/numbers/A3-audit-numbers.json`。
脚本里没有任何硬编码的结论数字，只有阈值（集中在文件顶部的 `T` 对象里：
相关系数 0.999、仿射残差 1e-9 / 1e-4、断点 8 倍 MAD、跳变 10 倍、哨兵占比 50%、
报 0 占比 90%、量级漂移 10 倍）。改阈值只需要改这一处。

常见问题的对应 JSON 字段：

| 想知道什么 | 看哪里 |
| --- | --- |
| 有多少指标可直接丢、都是哪些 | `constants.<run>` |
| 覆盖率分布、断供、报 0 | `coverage.<run>` |
| 哪些指标是重复的 | `identity.<run>.clustersTop` / `.examples` |
| 有没有越界 | `scale.<run>.outOfRange` |
| 断点集中在哪几步 | `breakpoints.<run>.ranked` / `.rankedRate` |
| 重启落在哪一步 | `eventAlignment.<run>.restartsByStep` / `.intervals` |
| 指标何时新增/消失 | `lifecycle.<run>` |
| 有没有换口径 | `drift.<run>` / `levelShift.<run>` |
| 解读的数字对不对 | `claims[]`（含 `ok` 与 `stale` 两个布尔值） |
| 哪些指标没解读 | `docAudit` |

最后一点：**这份审计本身也有边界。** 只有 24 / 30 个点，任何"常数"判定都是有限样本下的判定；
所有结论对应的都是 2026-09-18 这份快照，站点继续跑之后必须重跑脚本。

## 附录：术语速查表

| 术语 | 一句话解释 |
| --- | --- |
| `pro` / `flash` | 站点在跑的两个训练作业，pro 是大模型（成本 $5.71/秒）、flash 是小模型（$2.855/秒） |
| 序列（series） | 一个指标名对应的一串逐步取值，长度与步号数组严格对齐，没有数据的位置是 `null` |
| 覆盖率 | 该指标有值（非 `null`）的步数占总步数的比例 |
| 恒零 / 常数 | 非 `null` 值全部相同；"不同取值个数 = 1"是本次用的判据 |
| 哨兵值 | 为了表示"没有数据""没触发"而写进去的占位数字，最常用 0 和 1，与真值无法从数字上区分 |
| 报 0 | 指标有值、值是精确 0，但实际含义可能是"没数据"或"该分支未触发" |
| 分桶（`partial/<k>/`） | 把同一组统计按"数据从采样到训练隔了几个策略版本"切开，桶号越大数据越旧 |
| `frac` | 某个桶在本步 token 里的权重（占比），各桶之和 ≈ 1 |
| `staleness`（过期代数） | 数据从采样到被训练之间隔了几个策略版本，`partial/avg_staleness` 是它的平均值 |
| 恒等式 / 仿射关系 | 两条序列逐值相等，或满足 `y = a + b·x`；本次用"残差 / 取值范围 < 1e-4"判近似 |
| MAD（中位数绝对偏差） | 一种对离群点不敏感的波动度量，本次用它给每个指标自己的"常态波动"定标 |
| 断点 | 相邻两步的变化超过该指标自身 MAD 的 8 倍、且相对变化超过 5% |
| running mean（累计平均） | 到当前步为止所有步的平均值，会单调收敛、并且被重置时突然下降 |
| `harness`（智能体框架） | 同一批题用不同的 agent 脚手架跑，`train/harness/<名字>/...` 是按框架拆分的统计 |
| `tags.json` 的 `first_seen` / `last_seen` | 遥测第一次/最近一次看到该指标名的时间戳；本次证明两者都不能直接当生命周期用 |
