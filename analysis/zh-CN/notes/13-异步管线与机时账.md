## 一、摘要：结论先行

1. **"上报耗时不含重启"这件事被证实，但幅度和分母都要改口径。** 用"真实步耗时之和 − 上报耗时之和"算，
   pro 缺口 **26.15 小时**（占真实步耗时之和的 28.0%，折 **$537,478**，占总账单 $1,941,107 的 **27.7%**）；
   flash 缺口 **14.15 小时**（17.3%，折 **$145,403**，占总账单 $854,045 的 **17.0%**）。
   旧洞察里的 23.7 小时 / 48.8 万美元能复现，但那是"截至第 19 步的旧切面 + 用挂钟做分母"的另一套口径（见 5.1）。

2. **缺口不等于"重启等待"，把它读成停机时间会错。** 缺口能且只能拆成三块：
   (a) 上一步完成 → 最后一次恢复运行之间的跨度、(b) 恢复运行 → 本步计时器启动的开销、(c) 被整步丢弃的重算工作。
   (b) 可以精确量出且非常稳定：**pro 每次 740~800 秒、flash 每次 328~367 秒**。
   flash 第 16 步缺口 5.63 小时里有 **3.96 小时是"已经跑完两个整步（s16、s17）又被作废重跑"**
   （有 `redo=true` 事件为证），真正的恢复等待只有 0.09 小时。**这是算力白烧，不是停机。**

3. **管线在这些层没有堵：54 个步观测里，背压计数器全部恒为 0。**
   `train/trace/backpressure_waits`、`backpressure_wait_seconds_sum/max`、`orphan_resolves`、
   `failed_writes`、`terminal_conflicts` 在 pro 24 步 + flash 30 步上**无一例外全为 0**；
   排空等待 `drain_wait_seconds` 最大 8.23 秒，写出 `outcome_write_seconds` 最大 1.60 秒。
   "长尾把吞吐吃掉"这个故事在本轮数据里没有留下痕迹——不是因为没有长尾，而是因为这一层还有余量。

4. **陈旧度（`partial/avg_staleness`）不是排队延迟的代理，是一支"重启时钟"。**
   段内它与"距上次重启的步数"秩相关 **0.944（pro）/ 0.885（flash）**，与真实步耗时却只有
   **−0.235 / −0.070**。所以"步变长 → 轨迹跑不完 → 数据变旧"这条链在本数据里**不成立**：
   变长是真的（干净步真实耗时秩相关 +0.931/+0.909），变旧也是真的（flash 第 24 步有 9 个桶、约 84% 的 token 来自 1 个版本以前），
   但中间那一环接不上——**陈旧度的方差被重启吃掉了，不是被负载吃掉的**。

5. **单位成本：pro 每 10 亿训练 token $23,197，flash $8,203（都只用无重启的干净步）。**
   累计口径那条"从 $77,819/B 降到 $34,282/B 的下降曲线"主要是第 1 步被重启污染（那一步花 $140,115 只换来 1.80B token），
   不是效率提升；按干净步看，单位成本随步**略升**（pro 与步号秩相关 +0.84）。判分算力的美元占比**估不出来**，
   只能给出并发量级：pro 中位约 80 个判分组、flash 约 112 个（口径见 3.7）。

## 二、方法与口径

### 2.1 三层时间口径（本文最容易混淆的地方，先定死）

| 口径 | 定义 | 数据来源 | pro | flash |
| --- | --- | --- | --- | --- |
| 真实步耗时 | `axis.walls[i] − walls[i−1]`（第 1 步用 `run_start`） | `axis.json` | 合计 93.329 h | 合计 81.800 h |
| 上报步耗时 | `timing_s/step[i]` | `series.json` | 合计 67.182 h | 合计 67.653 h |
| 缺口（口径 A） | 真实 − 上报，**只统计步窗口内** | 上两行 | **26.147 h** | **14.147 h** |
| 缺口（口径 B） | 计费秒数 − 上报合计；计费秒数 = `end ?? now` − `run_start` | `status.json` | **27.248 h**（now 仍在走） | **15.441 h**（停在 `end`） |
| 旧洞察口径 C | （`now` − `run_start`）− 上报合计，且用挂钟做分母 | 旧切面 | 23.74 h / 32.9% | 14.57 h / 21.6% |

口径 A 是"步窗口内的账"，口径 B 多算了最后一次完成之后的尾巴，口径 C 是上一版。
**本文正文一律用口径 A**，百分比的分母是账单（`rate × 计费秒数`），另给 `占真实步耗时之和` 的比例。

### 2.2 解析口径（哪一行、哪个字段代表什么）

- `axis.walls` 相邻两项之差是**唯一**能拿到真实步耗时的来源；`timing_s/step` 是进程内计时。
- `events.json` 的 `kind:"restart"` 的 `t` 是**新进程恢复运行的时刻**，不是崩溃时刻。依据：`timeline.jsonl` 的
  `restarted_at` 就等于该 `t`，且 `step.since` 从该 `t` 起算（逐点差值吻合到 1 秒以内）。崩溃时刻不可观测，
  这是本文所有"等待 vs 白烧"只能给区间的根本原因。
- `timeline.jsonl` 里 `step` = `status.json` 的 `step.last`（最近**完成**的步），`since` / `expected` / `progress` /
  `gen_frac` 描述的是**正在跑的那一步**。文件共 27 行（27 个同步点），不是逐步一行。
- `live.jsonl` 的 `latest` 字段（`accept` / `judged` / `remain` / `prewarm_wait` 等）看板未给官方说明，
  本文只用它做旁证，不参与任何结论计算。
- 成本口径沿用看板原样：`cost = rate_per_s × (now − run_start)`，是**费率推算的账单，不是实测计费**。
  pro `rate = 5.71`、flash `rate = 2.855`（精确 2:1）。

### 2.3 统计

样本小，所以：相关一律用 Spearman 秩相关；两组对比用 Mann-Whitney U（正态近似 + 并列校正）给 p 值，
同时给 Cliff's delta 效应量。**n=11 / n=5 的重启对比不提供任何"规律"级结论。**
所有数字由脚本重算并写入 `analysis/zh-CN/numbers/A3-pipeline-numbers.json`。

### 3.2 缺口是不是全部来自重启？

**结论：缺口的"起因"100% 是重启，但缺口的"内容"不是等待，而是三样东西的混合，其中只有一样能精确量出。**

缺口有一个精确恒等式（脚本对每一步验算，误差 < 0.001 秒）：

```
缺口 = (上一步完成 → 最后一次恢复运行)          ← 混合项：被丢弃的进度 + 崩溃到恢复的停机
     + (最后一次恢复运行 → 本步完成) − 本步上报耗时   ← 恢复开销：可精确量出
```

| 步 | 缺口 s | 混合项 s | 其中已证实的"整步作废" | 其中部分进度（上限） | 恢复开销 s |
| --- | --- | --- | --- | --- | --- |
| pro s1 | 14,968.7 | 14,636.0 | 0 | 0 | 332.7 |
| pro s2 | 6,578.7 | 5,820.5 | 0 | 0 | 758.2 |
| pro s3 | 11,018.7 | 10,255.6 | 0 | 0 | 763.1 |
| pro s11 | 10,690.0 | 9,928.0 | 0 | 0 | 762.0 |
| pro s15 | 17,025.4 | 16,225.6 | 0 | 0 | 799.9 |
| pro s17 | 21,172.9 | 20,410.4 | 0 | 0 | 762.5 |
| pro s23 | 12,615.9 | 11,875.6 | 0 | 0 | 740.3 |
| flash s3 | 6,980.0 | 6,642.0 | 0 | 0 | 338.0 |
| flash s16 | 20,277.7 | 19,945.6 | **14,265.4**（s16+s17 各一次） | 5,680.2 | 332.1 |
| flash s25 | 16,180.7 | 15,852.3 | 0 | 0 | 328.3 |
| flash s28 | 7,270.1 | 6,903.1 | 0 | 0 | 367.0 |

三件事值得单独记住：

1. **恢复开销是个常数，而且两条 run 差一倍。** pro 每次 740~800 秒（12.3~13.3 分钟），flash 每次 328~367 秒
   （5.5~6.1 分钟）。这是"新进程起来到步计时器开始"之间没被计入的时间（大概率是加载权重、重建数据管线）。
   它可以直接拿来估"每次重启最少烧掉多少钱"：pro 约 $4,300/次，flash 约 $980/次。
2. **flash 第 16 步的缺口 70% 是白烧的算力，不是停机。** `events.json` 里第 16、17 步各出现两次、第二次带
   `redo=true`，公告 `n-b60f90` 写明"we restarted the flash run from step 15"。这两个整步跑完后被扔掉重跑，
   共 **14,265.4 秒 = 3.96 小时**，按 flash 费率是 **$40,728**。再加上重跑本身消耗的 18,193.1 秒（5.05 小时，
   这部分被正常计入了上报耗时），这一次故障让 flash 相对"没出事"多花了 **24,202 秒 = 6.72 小时 ≈ $69,097**。
3. **pro 的每一次重启都只留下"混合项"，没有任何整步作废**（`events.json` 里 pro 没有任何 `redo=true`）。
   也就是说 pro 的 24.78 小时混合时间里，"崩溃前被丢弃的进度"和"崩溃到恢复的停机"各占多少，
   **用现有数据分不开**——这是本文最大的一个数据缺口，不是可以靠更努力分析补上的。

### 3.3 上报耗时内部拆不开

**结论：`timing_s/step` 里 `outer_gen` + `trainer_ops` 占 97.9%（pro）/ 97.2%（flash），剩下的"其余"是 166~320 秒且随负载增长，但**没有**任何现有指标能解释它。**

- `outer_gen + trainer_ops ≤ timing_s/step` 在 54 个步上全部成立（脚本逐点校验）。
- "其余"（脚本 `othersplit.other_s`）：pro 中位 200.7 秒（占步 1.58%~2.64%），flash 中位 224.7 秒（1.81%~5.67%）。
- 它随负载走：与 `perf/total_num_tokens` 的 Pearson 相关 pro 0.884 / flash 0.719。
- **对不上的候选**（同一步的量级对照，全部差一个数量级以上或量级对不上）：

| 候选 | pro 量级 | flash 量级 | 与"其余"（200 / 225 s）对得上吗 |
| --- | --- | --- | --- |
| 判分每组总耗时 `time_total_sec_mean` | 中位 553.7 s | 中位 570.9 s | 量级同档，但它跑在**判分集群**上，与训练步计时不同池，不能相加 |
| 判分 pod 启动 `time_pod_setup_sec_mean` | 中位 14.66 s | 中位 14.95 s | 差 10~15 倍 |
| 排空等待 `drain_wait_seconds` | 1.29~8.23 s | 2.55~5.87 s | 差 25~170 倍 |

| 干净步每步新建沙箱数 | 中位 41,216 | 中位 42,032 | 是"次数"，没有单次 setup 秒数就换不成时间 |

**确认到哪一步：** 只能确认"其余"存在、稳定、随 token 量增长，**不能**把它归到沙箱 setup、判分或写盘上。
缺的数据是：步计时器的分阶段明细、checkpoint 写入/权重同步耗时、单次沙箱 setup 的秒数。
**这是"看不懂"的一格，不是"不重要"的一格**——它一个 run 累计 5,060 秒 / 6,717 秒。

### 3.4 排队论视角：Little 定律量出的沙箱平均存活时间

**结论：用 `env/active = λ × W` 反推，沙箱平均存活时间 pro 中位 1.43 小时、flash 中位 1.99 小时，且随训练推进单调变长。**

概念（可迁移）：**Little 定律 `L = λW`**。任何稳定排队系统里，"系统内的平均顾客数"等于"到达率 × 平均逗留时间"。
训练管线上它有一个特别好用的形态：`env/active`（在飞沙箱数）本来就是个瞬时水位，看起来只能当"忙不忙"的读数；
但只要再拿到"沙箱创建速率 λ"，就能**不打断点**反推出"每个沙箱平均被占用多久 W"。

口径：`L` = 该段 `env/active` 均值；`λ` = 该段"自复位以来累计创建沙箱数 ÷ 自复位以来墙钟秒数"；
复位时刻 = 段内最后一次 `restart` 事件的时间戳（依据：`env/total_setup` 在重启后恰好等于 `env/active`，pro/flash 各 7/5 个复位步逐点核过）。
只用段长 ≥ 3 步的段（段长 1~2 步时计数器复位会把上一段的创建量并进来）。

| run | 段（步） | λ（个/秒） | L（均值在飞） | **W（隐含存活）** | 每步每槽翻台 |
| --- | --- | --- | --- | --- | --- |
| pro | 3–10 | 5.35 | 23,061 | 1.198 h | 1.79 |
| pro | 11–14 | 4.55 | 23,450 | 1.430 h | 1.90 |
| pro | 17–22 | 3.60 | 23,231 | 1.793 h | 2.02 |
| flash | 3–15 | 6.17 | 37,840 | 1.705 h | 1.09 |
| flash | 16–24 | 5.25 | 38,270 | 2.023 h | 1.24 |
| flash | 25–27 | 5.52 | 38,729 | 1.951 h | 1.44 |
| flash | 28–30 | 4.96 | 38,675 | 2.168 h | 1.47 |

两件事：

1. **W 在两条 run 上都随步单调变长**（pro 1.20 → 1.79 h，flash 1.71 → 2.17 h），
   与同期的平均生成长度上涨（pro 68k → 115k token，flash 67k → 143k token）方向一致。
   即"沙箱被长轨迹占得更久"是能在这条链上量出来的——这是对 `notes/08`（生成长度突增）在系统侧的补充读数。
2. **看板上流行的读法 `env/total_setup ÷ env/active` 会高估翻台率。** 它是**段内累计**创建数除以水位
   （pro 段 3–10 得 14.341），除以段内步数才是每步翻台（1.793）。把 14 读成"每步翻台 14 次"会把沙箱数算错 8 倍。
3. **对不上 `time_pod_setup_sec_mean`：** W 是"整条 agentic 轨迹占着沙箱的时间"（上千秒），
   判分 pod setup 是"判分容器的启动时间"（十几秒），两者不是同一个量，**本文不宣称它们能对上**。

### 3.5 陈旧度：不是排队延迟的代理，是重启时钟（一条被推翻的链条）

**结论："步变长 → 轨迹跑不完 → 数据变旧"这条链在本数据里断在中间。变长是真的，变旧是真的，但两者之间没有因果关系。**

三个事实先摆出来（两条 run 都是）：

| 检验（只用非重启步） | pro | flash |
| --- | --- | --- |
| `avg_staleness` vs 距上次重启步数 | **+0.944** | **+0.885** |
| `avg_staleness` vs 桶个数 | +0.944 | +0.880 |
| 桶个数 vs 距上次重启步数 | **+1.000** | +0.998 |
| `avg_staleness` vs 真实步耗时 | −0.235 | −0.070 |
| `avg_staleness` vs 平均生成长度 | −0.177 | +0.031 |
| 干净步真实步耗时 vs 步号 | +0.931 | +0.909 |

机械恒等先排除：`avg_staleness = Σ_k k × frac_k`（逐点验算，最大误差 < 1e-7），
所以它不是一个独立观测量，而是"桶配比"的加权和，会随桶配比变化。
桶配比本身由**距上次重启的步数**唯一决定：pro 每次重启后桶数从 1 数到 8，flash 从 1 数到 10，单调无例外。

**链条的真相：** 重启把数据管线清零（桶 0 = 刚采出来的数据），此后每推进一个训练步就往 batch 里掺进一个更旧的版本，
直到下一次重启再清零。所以 `avg_staleness` 画出来是一个锯齿，**每个齿的"高度"就是那一段里攒了几个版本**：
pro 的三个齿峰是 1.82（s9，s11 复位）、1.21（s14，s15 复位）、1.29（s22，s23 复位），run 结束前在 0.75 处还在爬；
flash 的两个齿峰是 1.89（s15，s16 复位）、2.18（s24，s25 复位），末段爬到 1.19 时 run 就结束了（没有再复位）。
**齿的个数和高度由重启间隔决定，跟步长没关系。**

**"轨迹跑不完"这一环只有间接旁证**：`live.jsonl` 的采样器快照里有 `remain_partial`（未完成的 prompt 数）
和 `partial` 三元组，但看板没给字段定义，量级在数百到一千多之间；本文不据它下结论。

### 3.6 背压：这一层没有堵

**结论：13 个追踪类指标里，6 个"溢出计数器"在 54 个步观测上恒为 0。**

| 指标 | pro（24 步） | flash（30 步） |
| --- | --- | --- |
| `backpressure_waits` | 全 0 | 全 0 |
| `backpressure_wait_seconds_sum` | 全 0 | 全 0 |
| `backpressure_wait_seconds_max` | 全 0 | 全 0 |
| `orphan_resolves` | 全 0 | 全 0 |
| `failed_writes` | 全 0 | 全 0 |
| `terminal_conflicts` | 全 0 | 全 0 |
| `drain_wait_seconds` | 1.29 ~ 8.23 s | 2.55 ~ 5.87 s |
| `outcome_write_seconds` | 0.46 ~ 1.60 s | 0.52 ~ 0.85 s |
| `late_finishes` | 0 ~ 47（中位 0） | 0 ~ 210（中位 24） |
| `writer_seconds_max` | 16 ~ 57 s | 16 ~ 51 s |
| `files`（每步） | 3,038 ~ 6,019 | 2,639 ~ 5,882 |

概念（可迁移）：**背压（backpressure）是排队溢出的直接读数。** 有界队列写不进去时，生产者会被挡住，
"被挡住"这件事一定会被计数；所以判定"是不是这一层堵"，看的是**溢出计数器的非零次数**，
而不是利用率百分比。**全 0 的正确读法是"这一层的缓冲足够大 / 长尾被并发吸收了"，不是"没有长尾"。**
判断规则：溢出计数器全 0 + 排空等待在秒级 → 这一层不是瓶颈，别在这里优化；
溢出计数器非 0 且等待时间进入分钟级 → 才是真背压，优先扩这一层的缓冲或写入并行度。

旁证：`train/trace/records` 在 pro 第 17 步从 1.63e6 跳到 3.27e6（恰好翻倍），
同一时刻 `writer_seconds_sum` 从约 5,000 秒升到约 8,000 秒——像是第 17 步那次并行策略调整顺带把 trace 写入并行度翻了一倍。
看板没给这两个字段的定义，这只是一个吻合的时间巧合，**不作为结论**。

### 3.7 钱花在哪

**结论：账单能拆的只有"时间 × 费率"；每步的钱随步变多，每 token 的钱在干净步上基本走平、略升。**

| 口径 | pro | flash |
| --- | --- | --- |
| 费率 | $5.71/s | $2.855/s（恰好一半） |
| 账单（`rate × 计费秒数`） | **$1,941,107**（now 仍在走） | **$854,045**（停在 `end`） |
| 训练 token 累计 | 55.96 B | 81.40 B |
| 每 10 亿 token（累计口径） | $34,686 | $10,492 |
| 每 10 亿 token（**只用干净步**） | **$23,197**（17 步 / 46.48 h / 41.19 B） | **$8,203**（26 步 / 56.59 h / 70.91 B） |

| 每步花费（首步 / 末步，含重启） | $140,115 / $75,167 | $18,959 / $35,464 |
| 干净步单位成本 vs 步号 | +0.84 | +0.28 |
| 缺口（口径 A） | 26.147 h = **$537,478 = 账单的 27.7%** | 14.147 h = **$145,403 = 账单的 17.0%** |

- **每步花多少钱随步怎么变**：干净步真实耗时从 pro 的 1.905 h 涨到 3.657 h（秩相关 +0.931），
  flash 从 1.845 h 涨到 3.451 h（+0.909）。步变长就是每步变贵，这是上下文变长的直接账单。
- **每十亿 token 花多少钱**：**累计口径的"下降"是假象。** pro 的累计值从 $77,819/B 降到 $34,282/B，
  但第 1 步本身是 6.82 小时里夹了两次重启、只产出 1.80B token，把起点抬得极高。
  剔掉重启步后，pro 的单位成本随步**上升**（+0.84），flash 基本走平（+0.28）。
  所以正确说法是"**单位成本没有随规模下降**"，而不是"训练变便宜了"。
- **"什么都没干"的时间值多少钱**：pro $537,478（27.7%）、flash $145,403（17.0%）。
  但注意 3.2 的结论——这块钱里真正"纯停机"的部分两条 run 都量不出来，只有 flash 的 3.96 小时能**证明**是白烧的算力。
- **判分算力的占比：估不出来，只能给并发量级。** 判分每组总耗时中位 553.7 s（pro）/ 570.9 s（flash），

  于是并发判分组数 ≈ `组数 × 每组秒数 ÷ 真实步耗时` ≈ **pro 80 个、flash 112 个**（若用 `groups_attempted` 则 36 / 65）。
  **美元占比算不出来的原因很硬：`status.json` 里只有一个全局 `rate_per_s`，没有判分集群自己的费率。**
  这个 rate 到底是"训练集群的机器数读数"（`notes/07` 的读法）还是"训练 + 判分一起"，数据里没有答案。

| 原因 | 次数 | pro | flash | 覆盖公告 |

**其余 10 次没有公告**：pro 的 s1×2、s2、s3、s23×2（后两次正是 `notes/07` 提到的 09-19 早上那两次），
flash 的 s3、s25×2、s28。公告栏不是重启的完整日志。

口径：样本 = "被重启打断的那一步的**前一个已完成步**"的特征值（pro n=6 vs 其余 18；flash n=4 vs 其余 26）。

### 3.9 flash 为什么"有序停止"：从系统侧看它停在了什么状态

**结论：`end` 之后计费表停了；速率从头到尾没变过；停止时那条"进行中的步"的时钟也一起冻结了。**

`notes/07` 已经确立了"速率 = 机器数读数、flash 的机器没被腾给 pro"。本文在同一口径上补三个可验证的系统侧事实：

1. **计费表在 `end` 处冻结，不是继续走。** `cost.so_far ÷ rate = 299,140.0 秒`，而
   `run.end − run_start = 299,140 秒`，**精确相等**；同一时刻 `now − run_start = 322,900 秒`。
   也就是说 flash 的最终账单就是 $854,044.70，停止后那 6.6 小时（23,760 秒）没有计费。
   （pro 没有 `end`，`cost.so_far ÷ rate` 就等于 `now − run_start`，说明这个恒等式对两条 run 都成立。）
2. **费率确实是 pro 的一半，且停止前后都没有台阶。** flash `rate_per_s = 2.855`，pro `5.71`，比值 2.000；
   `timeline.jsonl` 的 27 个同步点里 flash 的 `rate` 字段全程 2.855，无一跳变。
   **"停止后速率还成不成立"这个问题有一个比 `notes/07` 更硬的答案：它不再累加了，所以"停止后速率"这个量不存在了。**
3. **停止瞬间的"步内状态"被一起冻结。** 最后 5 个同步点（第 30 步完成之后）里，
   `step` 恒为 30、`since` 恒为 4659.006 秒、`gen_frac` 恒为 0.5173、`progress`/`phase` 变成 `null`。
   即：看板停在"第 31 步跑了 4659 秒（预期 12066 秒，进度 39%）"，且这个数不再刷新。
   这解释了为什么社区看到的是"停在那了"而不是"报错了"。
4. flash 停在第 30 步、pro 还在跑，两者 `env/active` 的对比也支持"机器没被搬走"：
   flash 停止前 38,694，pro 同期从 23,400 跳到 38,437——**pro 是把自己的并发水位抬到了 flash 的高度**，
   但它的 `rate_per_s` 一点没动。**（这一条是本文新发现，`notes/07` 当时还没看到第 23 步：pro 的 `env/active`
   在 s23 一步之内从 23,419 跳到 37,888，+61.8%，此后保持；同期 s24 单步新建沙箱 64,976 个，是干净步中位 41,216 的 1.58 倍。）
   按 `notes/07` 的读法"速率 = 机器数"，费率没变说明**训练机器数没变，变的是沙箱并发上限**——
   这是一次编排层的配置改动，不是加机器。

### 3.10 `step.since` / `expected` / `progress` / `gen_frac` 可信吗

**结论：`since` 和 `phase` 是真信号；`progress`、`expected`、`gen_frac` 三个都不是"当前这一步"的实时观测。`expected` 中位数几乎无偏，但误差分布很宽，且在最需要它准的时候（步长上台阶）单边偏乐观。**

（先纠一处我自己写错过的地方：初稿把 flash 第 20 步轨迹的 `gen_frac` 写成 0.5318，复算后是对的 **0.4144**，
等于上一步 s19 的 `3632.2 ÷ 8765.3`。第三节那张表已改正，`gen_frac` 的口径没有例外。）

三个机械恒等，全部在 27 个同步点上逐点验过（两条 run 都是 27/27 命中，最大误差 0）：

| 字段 | 真实口径 | 命中 |
| --- | --- | --- |
| `progress` | `min(1, since / expected)` | 最大绝对误差 **0** |
| `expected` | **最近 3 个已完成步的上报耗时之中位数**（滚动 3 中位，进入当前步时冻结） | 27/27 |
| `gen_frac` | **上一步的 `outer_gen ÷ 上一步的上报耗时`**，整步冻结不变 | 27/27 |

所以：
- `progress` 不含任何新信息，它是 `since / expected` 的派生值；
- `gen_frac` **不能**用来看"这一步生成到几成了"——它描述的是**上一步**的生成占比，本步从头到尾是同一个数；
- `expected` 是一个"后视 3 步中位"预测器：它不看这一步的负载，也不看趋势，只用最近三步的历史。

量化偏差（只用非重启步，`expected` 对该步真实耗时的相对误差）：

| run | 步数 | 中位 | 均值 | 最小（最乐观） | 最大（最悲观） | 偏乐观的步数 |
| --- | --- | --- | --- | --- | --- | --- |
| pro | 17 | +0.13% | +0.68% | **−11.26%（第 7 步）** | +31.24% | 8 / 17 |
| flash | 25 | −1.57% | −1.13% | **−21.54%（第 30 步）** | +32.24% | 16 / 25 |

**读法要精确**：`expected` **不是**"永远偏乐观"——按中位数它几乎无偏（pro +0.13%，flash −1.57%），
悲观和乐观各占一半。真正的问题是**误差幅度**：pro 的十分位是 −10.7%，flash 是 −13.6%，
即"偏乐观那一侧的前 10% 会低估一成以上"。而这些大偏差集中出现在**步长上台阶的那几步**：
pro 第 7、9、14 步分别是 −11.3% / −10.7% / −10.3%，flash 第 30、14、20 步是 −21.5% / −13.9% / −13.6%。
机制很直白：滚动 3 中位追不上单调上涨，而步长上涨是这一轮训练的常态（干净步真实耗时秩相关 +0.93 / +0.91）。
反过来在步长抖动的步上它会偏悲观（pro 最大 +31.2%）。
**用 `progress` 判断"还要多久"，不会持续骗你，但会在最慢的那几步骗你最多。**

**三个完整的步内轨迹（还原口径：把 `timeline.jsonl` 里同一"进行中步号"、`since` 单调递增、
`restarted_at` 不变的行连起来）：**

**（1）flash 第 20 步——唯一一个从 0 秒开始、覆盖全过程的样本（9 个采集点，间隔 1205 秒）**

| 墙钟 | `since` | `progress` 字段 | 重算 `since/expected` | `phase` | `gen_frac` |
| --- | --- | --- | --- | --- | --- |
| 1789647041 | 8.2 | 0.0009 | 0.0009 | rollout | 0.4144 |
| 1789648245 | 1211.3 | 0.1382 | 0.1382 | rollout | 0.4144 |
| 1789649450 | 2417.8 | 0.2758 | 0.2758 | rollout | 0.4144 |
| 1789650655 | 3617.9 | 0.4127 | 0.4127 | rollout | 0.4144 |
| 1789651858 | 4824.0 | 0.5503 | 0.5503 | **training** | 0.4144 |
| 1789653062 | 5989.5 | 0.6833 | 0.6833 | training | 0.4144 |
| 1789654266 | 7232.2 | 0.8251 | 0.8251 | training | 0.4144 |
| 1789655469 | 8437.0 | 0.9625 | 0.9625 | training | 0.4144 |

实际完成在墙钟 1789657177.8（`since` = 10,143.5 秒），上报 10,142.1 秒（差 1.4 秒，是干净步）。
三个读数：`gen_frac` 全程钉在 **0.4144**（= 上一步 s19 的 `3632.2 / 8765.3`），
`phase` 在 `since` 3617.9~4824.0 之间从 rollout 翻到 training（与上报的 `outer_gen` = 4932.0 秒基本吻合），
`progress` 在 `since` = 8765.3（= `expected`）打到 1.0，而这一步实际跑了 10,143.5 秒
——**也就是说"进度 100%"这个状态持续了 1376.8 秒，占该步 13.6%**（精确值 = 上报耗时 − `expected` = 10,142.1 − 8,765.3）。

**（2）flash 第 19 步——后半程样本（5 个采集点，末尾缺前 3931.9 秒）**

`since` 3931.9 → 7570.9，`phase` 在 5159.1 处从 rollout 翻到 training，`expected` 8,930.4 秒，
实际 8,766.1 秒 / 上报 8,765.3 秒。这一步 `expected` 偏悲观 1.9%——**正好和"步在变短"对上：**
s19 的 8,765 秒比 s18 的 8,930 秒短，滚动 3 中位还没跟上。

**（3）pro 第 15 步——带重启的步，最能说明 `progress` 为什么不能信（11 个采集点）**

重启 #7 在 1789644107.334 恢复，此后 `since` 从 526.0 涨到 12564.7，`expected` = 9416.42（滚动 3 中位 =
s12/s13/s14 的 9063.0 / 9416.4 / 10491.6 的中位数）。`progress` 在 `since` = 9416.4 打到 1.0，
**但这一步此后还跑了 3465.2 秒——占该步上报耗时（12881.6 秒）的 26.9%**，
而且这 3465 秒全程 `phase = training`、`progress = 1.0000`（脚本字段 `progress_pinned_seconds_exact`）。
按"进度 100%"去判断"马上好了"，会错将近一小时。
（通过采集点能直接数出来的最少时长是 3148.3 秒，因为最后一个采集点落在 12564.7 秒处。）

**（4）flash 停止后的冻结（第 31 步，6 个采集点）**

`since` 恒为 4659.006、`progress` 和 `phase` 为 `null`、`gen_frac` 恒为 0.5173。
这不是"卡住了"，是 run 已经 `end`，看板不再更新——同时也是 3.9 第 3 条的证据。

## 四、不确定、被推翻、对不上

**被推翻 / 需要修正的**

1. **旧洞察 `timing-excludes-restart` 的 23.7 小时 / 48.8 万美元**：在"截至第 19 步的旧切面 + 挂钟做分母"下能复现

   换成当前切面和口径 A 之后是 **26.15 h / 28.0% / $537,478**。**结论没被推翻，数字需要跟着切面和分母一起重报。**
2. **旧洞察 `notices-explain-outages`（"五条公告解释了几乎所有的重启"）**：按完整数据只有 6/16 次重启有公告，10 次没有。
3. **`notes/07` 与指标解读里 `env/total_setup ÷ env/active ≈ 14` 是"翻台率"**：那是**段内累计**翻台次数，

**"任务里假设、但数据不支持"的一条**

5. **"步变长 → 轨迹跑不完 → 数据变旧"这条链断在中间**（3.5）。变长和变旧都是事实，
   但它们之间没有可检出的关联：`avg_staleness` 与真实步耗时的秩相关是 −0.235 / −0.070，

**对不上的（明确写出来，不用猜测补齐）**

   54 个步全部如此，方向一致但比例不固定。看板没给口径，**不据此下任何结论**。
7. **"其余"（`step − outer_gen − trainer_ops`）找不到对应物**（3.3）。量级 200~225 秒，随 token 量增长，
   与判分耗时同档但不同池，与 pod setup / 排空等待 / 写出差 1~2 个数量级。
8. **`timeline.jsonl` 只有 27 个同步点**，所以"步内轨迹"只对 flash 第 20 步是完整的；
   其余步要么缺开头（pro s24、flash s19）、要么跨重启（pro s15、flash s25）、要么整段被冻结（flash s31）。
   **"进度字段准不准"的结论建立在 4 条轨迹、共 35 个采集点上，样本量按采集点算很小。**
9. **`live.jsonl` 的字段（`accept` / `judged` / `remain` / `remain_partial` / `prewarm_wait` / `partial` 三元组）
   看板没有任何官方说明。** 其中 `prewarm_wait` 的量级很大（pro 最大 7,671 秒、flash 最大 5,309 秒），

10. **`expected` 的偏乐观幅度是我初稿写错、复算后修正过的一处**（3.10）：中位数其实几乎无偏，

**方法上的硬限制**

## 六、可迁移的专业概念（定义 + 本文体现 + 一条判断规则）

### 概念 1：Little 定律用在训练管线上——用并发水位反推服务时间

**定义**：稳定排队系统里 `L = λW`：系统内平均顾客数 = 到达率 × 平均逗留时间。三者知道两个就能算第三个。
**本文体现**：`env/active` 就是 L，`env/total_setup` 的单步增量除以真实步耗时就是 λ，
于是 W（沙箱平均存活时间）不用打点就能算出来：pro 1.43 h、flash 1.99 h，随训练推进单调变长（3.4 的表）。
**判断规则**：只要手上有"水位 + 到达速率"两个指标，就能反推"每个单位被占用多久"，
用它可以判断"指标变差是因为来得多还是因为单个跑得久"——本文里 W 变长说明是后者（轨迹变长），不是并发被压。

### 概念 2：陈旧度（staleness）作为排队延迟的代理——但要先问它什么时候清零

**定义**：异步管线里，训练用到的数据是"若干个策略版本之前"采出来的，`avg_staleness = Σ k × frac_k`
（k 是版本差，frac 是该版本 token 占比）就是"数据平均落后几个版本"。它在概念上等价于排队系统的逗留时间。
**本文体现**：pro 每次重启后 staleness 从 0 涨到 1.82，flash 涨到 2.18，然后归零重来；
它与"距上次重启步数"秩相关 0.944 / 0.885，与真实步耗时只有 −0.235 / −0.070。
**判断规则**：**任何一个"延迟型"指标，先找它的清零事件。** 如果清零由外部事件（重启、回滚、重置）触发，
那么该指标的方差主要来自清零频率，不能直接当负载表用；要测负载对它的影响，必须在两个清零事件之间的段内做回归。

### 概念 3：背压（backpressure）是排队溢出的直接读数，不是利用率

**定义**：有界队列满时生产者被挡住，叫背压；工程上通常体现为"等待次数"和"等待秒数"这类显式计数器。
**本文体现**：`backpressure_waits` / `backpressure_wait_seconds_sum` / `backpressure_wait_seconds_max` /
`orphan_resolves` / `failed_writes` / `terminal_conflicts` 在 54 个步观测上恒为 0，
`drain_wait_seconds` ≤ 8.23 秒（3.6 的表）。
**判断规则**：判断"是不是这一层堵"看**溢出计数器的非零次数**，不看利用率。
全 0 只说明"缓冲够/长尾被并发吸收了"，不等于没有长尾；非 0 且等待进入分钟级才是真背压。

### 概念 4：累计计数器 vs 单步增量——复位语义会制造"假规律"

**定义**：很多监控量是"自上次进程启动/复位以来的累计值"（本文的 `env/total_setup`、`env/total_error`、
`train/trace/records`）。看板上排在一起的两个数，可能一个累计一个瞬时。
**本文体现**：`env/total_setup ÷ env/active ≈ 14` 看起来像"每步翻台 14 次"，其实它是段内累计翻台次数
（pro 段 3–10 共 8 步），除以步数只有 1.793；`env/total_setup` 在重启步恰好等于 `env/active`，
于是重启后第一步的增量会把上一段漏掉的创建量一起算进来（pro 该位置约 64k~80k，而干净步中位 41k）。
**判断规则**：看到"比值异常大/异常稳定"的两个数，先确认两者是不是同一时间口径；
累计值要做差、要按复位点切段，否则会把"段长"读成"速率"。
