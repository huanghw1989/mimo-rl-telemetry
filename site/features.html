Feature comparison功能对照

mimo-rl-telemetry

Enhanced telemetry for Xiaomi MiMo’s $3M+ live RL run: interactive metric explainers, cross-curve correlation analysis, and step-by-step historical replay. The upstream dashboard at mimo.xiaomi.com/rl exposes about 2,000 metric series and ships an official one-line description for 22 of them; this project explains the rest, and keeps every sync so those readings can be checked across the whole run. 为小米 MiMo 这场 300 万美元级的在线 RL 训练做的增强遥测层：可交互的指标解读、跨曲线相关性分析，以及逐步的历史回放。上游看板 mimo.xiaomi.com/rl 暴露约 2000 条指标序列，其中只有 22 个带官方的一行说明；本项目把剩下的讲清楚，并把每次同步都留存下来，让这些解读能跨整轮训练核对。

How it works它是怎么工作的

The telemetry does not re-host the dashboard. It keeps every upstream asset as-is and patches a telemetry layer around it. 遥测层不是把看板重做一遍：它把原站资源原样保留，只在外面补一层遥测。

01

Two cadences: ~30 s samples, 20 min syncs两种节奏：约 30 秒采样，20 分钟同步

The trainer writes a dynamic-sampler report about every 30 seconds and finishes a step in roughly 3 hours. This layer syncs every 20 minutes: going denser would not add information, only log lines. A 12-skip ceiling forces a full refresh, bounding anything missed to about 4 hours.训练器大约每 30 秒写一条动态采样器报告，约 3 小时走完一步。这一层每 20 分钟同步一次——再密也不会多出信息，只会让日志变长。连续跳过 12 次就强制全量，任何漏抓最多兜到约 4 小时。

02

The diff: decide whether to ask差量：先决定要不要发这个请求

/series returns everything and ignores range parameters, so the saving is not in the query but in skipping it. After /status, if the local max step equals status.step.last, no unseen rerun exists and fewer than 12 syncs were skipped, the ~500 KB fetch is skipped — traffic falls from about 1 MB to about 40 KB./series 不认任何区间参数、每次都全量，所以省下来的不是查询而是「要不要发」。抓完 /status 后，如果仓库最高步号等于 status.step.last、没有没见过的新重跑、且连续跳过不到 12 次，就跳过那约 500 KB 的抓取——实测流量从约 1 MB 降到约 40 KB。

Merging is per cell: fill nulls, ignore equal values, overwrite only when that step was rerun, otherwise keep the local value and warn. That warning has never fired.合并是按格子判断的：本地空就填、相同就不动、那一步重跑过才覆盖，否则保留本地值并打警告。这条警告至今没触发过。

03

Warehouse vs. index仓库与索引分开

data/store (JSON, one row per metric) is the authority: human-readable, greppable, diffable. data/telemetry.sqlite is derived and queryable (WHERE step <= ?), so replay is a range scan rather than parsing the whole file.data/store（JSON，一个指标一行）是权威副本：人可读、能 grep、能 diff。data/telemetry.sqlite 是派生的查询接口（WHERE step <= ?），回放因此是一次范围扫描，而不是把整个文件解析一遍。

Values are Float64 blobs keyed by (run, tag): the naive three-column long table measured 10.6 MB against 1.7 MB for the whole blob layout, because one 45-byte metric name repeated over 75k rows costs ~3.4 MB of pure duplication.数值按 (run, tag) 存成 Float64 blob：最自然的三列长表实测 10.6 MB，而 blob 布局整库只有 1.7 MB——指标名平均 45 字节，7.5 万行就是约 3.4 MB 的纯重复。

04

A layer around upstream, not a fork叠在原站上，而不是分叉

Upstream assets stay byte-identical (style.css, theme.js, format.js, charts.js), and a copy lives in data/upstream so sync can flag a redesign by hash. app.js carries 6 patches (9 [telemetry] markers, +56/−3 lines) and index.html 6 added lines; everything else is telemetry.css, telemetry.js and correlate.js.原站资源逐字节保持原样（style.css、theme.js、format.js、charts.js），并在 data/upstream 留一份原始副本，同步时比对哈希、改版会报出来。app.js 有 6 处补丁（9 个 [telemetry] 标记，+56/−3 行），index.html 多 6 行；其余全部落在 telemetry.css、telemetry.js 和 correlate.js。

The telemetry replaces fetch to append asof, and the whole interface back to the original code is two functions: Telemetry.replay() and Telemetry.bind().遥测层换掉 fetch 补上 asof，对原站代码暴露的接口只有两个：Telemetry.replay() 和 Telemetry.bind()。

05

One algorithm, two paths一套算法，两条路径

The correlation kernel is a single UMD file (site/js/correlate.js) loaded by both the browser and the server, so the online and offline numbers cannot drift apart. The offline bundle carries the full series, which is what lets offline.html recompute the same analysis with no network.相关性内核只有一份 UMD 实现（site/js/correlate.js），浏览器和服务端加载同一个文件，在线和离线算出的数字不会各算各的。离线包里本来就有全量序列，所以 offline.html 能就地复算同一套分析。
