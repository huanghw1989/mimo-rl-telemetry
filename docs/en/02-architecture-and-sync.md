# Local Telemetry and Sync Mechanism

This document describes how this repository brings `https://mimo.xiaomi.com/rl/` local,
how incremental updates work, where data is stored, and how replay is produced.

For what each field in the data itself means, see `docs/en/01-dashboard-data.md`. This one only covers engineering implementation.

## 2. What one sync does

```
bun src/sync.ts
```

1. Fetch `/runs`, `/notices`, and `/benchmarks` (about 6 KB total).
2. For each run:
   - Fetch `/status` (about 3 KB), and decide whether to fetch the series (see Section 3).
   - If needed, fetch `/tags` and `/series` (about 500 KB, 23 batches).
3. Merge the results into `data/store/`:
   - `notices` is deduplicated and merged by `id`.
   - `benchmarks` is merged by `(key, run, step)`, append-only.
   - `events` is deduplicated and merged by `(kind, step, t)`.
   - `tags` registers newly appearing metric names and updates timestamps.
   - `series` fills in new cells. Existing non-empty values are left untouched by default; overwriting is allowed only if that step was rerun.
4. Append a sync record to `syncs.jsonl`; this is the source of the replay feature's timeline.
5. Incrementally update the SQLite index.
6. Compare hashes of the original site's frontend assets, and notify if there is a change.
7. Add Chinese translations for newly added / original-text-changed announcements (Section 7.3; `--no-translate` can be skipped).

On first use (or to rebuild history), run:

```
bun src/sync.ts --bootstrap
```

It will load those 15 early snapshots under `data/seed/` into the repo in chronological order,
then do an online sync. After loading, the repo has the complete history from the first day of the run to now,
and replay can go all the way back to the first step on 2026-09-15.

Common switches:

| Switch | Effect |
| --- | --- |
| `--bootstrap` | Import historical snapshots first |
| `--force` | Skip the "no new data" check and force a full refetch of all series |
| `--reindex` | Rebuild only the SQLite index, no network |
| `--no-assets` | Do not compare against the origin site's frontend assets |
| `--no-translate` | Do not add Chinese translations for new announcements |

## 3. How incremental fetching works

`/series` does not recognize any range parameters (tried `from`, `since`, `start`, `step_from`, `offset`; all ignored),
It always returns the full set. So what cannot be saved is "the request being sent"; what can be saved is "whether to send it".

### First layer: whether to send this request

After fetching `/status`, decide:

- The highest step number of that run in the repo matches `status.step.last`, **and**
- there is no "new rerun step we haven't seen before", **and**
- the number of consecutive skips has not reached 12

If all three are satisfied, skip `/tags` + `/series`. Measured: when both runs are skipped, the traffic of one sync
drops from about 1 MB to about 40 KB.

The mandatory full fetch on the 12th time is a fallback: if the site has writes we didn't anticipate, at most 12 sync cycles are missed
(at one every 20 minutes, that's 4 hours) before it gets corrected.

**Here's a counterintuitive point**: the condition cannot use "event count equals step count". Reruns make the event count larger than the step count
(flash has 24 steps but 26 step events); using the count would always think the data changed and refetch the full set every time.
The correct check is either to compare step numbers using `status.step.last`, or to handle reruns separately.
I actually hit this bug during implementation; the output at the time can be seen in the logs.

### Second layer: whether to write this data

`mergeSeries` compares cell by cell for each metric:

- Local is `null` and remote has a value → fill it in and count it as a "new cell".
- Local has a value and remote is the same → do nothing.
- Local has a value and remote is different → two cases:
  - That step appears twice in the event stream (rerun) → overwrite with the remote value and log an entry.
  - Otherwise → **keep the local value** and emit an `!!` warning indicating "it doesn't match the site, and was not caused by a rerun".

I validated with 15 historical snapshots: under normal conditions without reruns, the value in the same cell never changes.
This guard has never triggered so far, which means the data is clean; I keep it because if it ever triggers, it means
our understanding of the site differs from reality, and we must know.

## 4. Storage format selection and measurements

For the same data, the measured sizes of three storage methods:

| Storage method | Size | Description |
| --- | --- | --- |
| The 15 raw snapshots left by the old collection script | **14,489 KB** | Each is a full dump; the same data is stored 15 times |
| This repo's JSON columnar format (`data/store`) | **1,325 KB** | The authoritative copy after deduplication |
| └ of which the two runs `series.json` | 720 KB | One metric per row, convenient for grep and diff |
| └ of which the two runs `tags.json` | 509 KB | Metric name + lifecycle; the metric names themselves are very long |
| SQLite index (`data/telemetry.sqlite`) | **1,768 KB** | Derived, rebuildable |

Deduplication compresses 14.5 MB to 1.3 MB, about 11×. As for why there still has to be a SQLite in the end:

**JSON is good as a repo, not as a query interface.**

- When the frontend fetches series by tag, if it reads JSON directly, every request has to parse the entire `series.json`.
  At 720 KB now it's still tolerable; once there are thousands of metrics and hundreds of steps, it becomes tens of MB parsed repeatedly.
- Replay needs to filter data by "steps completed before a given time". With JSON, the full set must first be read into memory and then filtered;
  SQL is just a single `WHERE step <= ?`.
- bun ships with `bun:sqlite`; no dependencies need to be installed.

### Why values in SQLite are stored as BLOB instead of a long table

To start with the conclusion: a long table is at a big disadvantage in this data shape.

My first version used the most natural three-column long table `series(run, tag, step, value)`; measurements:

| Approach | Size |
| --- | --- |
| `series` three-column long table | 10.6 MB (plus 7.7 MB of unreclaimed WAL) |
| `series(run, tag, n, v)`, `v` is Float64 binary | **1.7 MB (entire DB)** |

The reason for the 11× difference is that **metric names are stored once per row in the long table**. Measured metric names average 45 bytes,
75,000 rows means 3.4 MB of purely repeated strings; adding B-tree overhead turns it into 10×.

The layout after switching to columnar is:

```sql
CREATE TABLE series (
  run TEXT NOT NULL, tag TEXT NOT NULL,
  n INTEGER NOT NULL,      -- number of cells written
  v BLOB NOT NULL,         -- Float64 array, index = step - 1
  PRIMARY KEY (run, tag)
) WITHOUT ROWID;
```

- The metric name is stored only once per metric.
- Values are arranged in fixed-length 8-byte cells, located directly by index; fetching a metric is one primary-key lookup plus one slice.
- Missing values are represented by `NaN`. The site's values come from JSON and cannot be `NaN`, so they won't collide with real values.
- The blobs of 3905 metrics total **612 KB**, i.e. 8 bytes per cell with no extra overhead.

**When to switch to a heavier format.** Right now the two runs total 75,000 cells and 1.7 MB. At the current speed of about 3 hours per step,
running to 1000 steps is about 4 million cells and 32 MB; SQLite can handle that completely. The real inflection point is in two directions:

- If rollout-level details are to be stored later (each question, each trajectory), the data volume is in the millions to hundreds of millions,
  at that point what should be used is Parquet or DuckDB, with columnar compression + predicate pushdown, rather than continuing to stuff it into SQLite.
- If it's just more metrics and more steps, the current blob columnar setup is sufficient for a long time.

## 5. SQLite table schema

```sql
meta(key, value)                 -- configuration for /runs, one key per row, value is JSON
runs(key, label, note, color_index, start, mode, rate, headline_tag, version)
tags(run, tag, first_seen, last_seen)          -- lifecycle of metric names
steps(run, step, t, wall, value, delta, tokens, redo)
series(run, tag, n, v)                          -- the Float64 blob mentioned above
notices(id, t, run, text)
benchmarks(bkey, title, note, format, run, step, value)
syncs(sid, captured, server_now, source)        -- sync points; sid matches the line number in syncs.jsonl
timeline(sync_id, run, cost, step, phase, progress, gen_frac, ...)  -- run status at each sync point
live(sync_id, run, t, step, passrate, n, pr0, pr1, json, entries)  -- entries is the sampler's rolling detail
assets(path, sha256, bytes, fetched)            -- hashes of original-site frontend assets
```

Writes are incremental: `indexRun` reads the existing blob for each metric and extends the tail according to the array in the JSON repo,
only writing back if it actually changed. A full rebuild takes 0.1–0.2 seconds, and incremental updates during sync are usually within 0.1 seconds.

The indexing phase is wrapped entirely in one transaction, because the server side may be another process doing read-only queries,
table-by-table DELETE + reinsert would let it read a half-finished state.

## 6. How replay is produced

The core is one invariant:

> The values of a step appear in `/series` only when that step completes; after appearing, they never change.

(The exception is reruns; a rerun leaves two events with the same number in the event stream, and the sync script follows up and overwrites accordingly.)

Thus "the dashboard at a given time" equals **truncating each metric array up to that time**. The specific approach:

1. Each sync point on the timeline has an `captured` timestamp, recorded in the `syncs` table.
2. After the request carries `asof=<epoch 秒>`:
   - `steps` takes only rows with `COALESCE(t, wall) <= asof`. It prioritizes the timestamp in the event stream,
     if absent, it falls back to `wall` in the series timeline. The two differ at the minute level, which does not affect replay.
   - `series` performs `WHERE step <= ?` truncation by the maximum visible step number.
   - `notices` takes `t <= asof`'s.
   - `benchmarks` keeps only points whose corresponding training step has completed.
   - `live` takes the **last archived entry** of `captured <= asof` (strictly searching backward; if not found, return empty,
     never fall back to "the latest one"—that would stuff future sampler data into a past slice),
     and assembles the sampler rolling details before that moment (see the next section).
   - `timeline` takes the last row of `captured <= asof` to get the phase, progress, and restart count.
   - `clock.now` directly returns `asof`, so the clock, "elapsed time", and cost on the page are all frozen.
3. Cost is recalculated: `rate × (asof − run.start)`. This will differ from the
   `cost.so_far` recorded in the snapshot at the time by a few seconds (because `clock.now` in the snapshot is slightly later than `captured`),
   This is a definitional difference, not an error.

> **`asof` must be passed through unchanged; it cannot be rounded.** The sync point's `captured` has a decimal part
> (for example `1789871319.416`); earlier the frontend used `Math.round()` to convert it to an integer before passing it:
> When the fractional part is less than 0.5, the result is smaller than `captured`, and the server-side `pickSync` lands on the **previous**
> sync point——the symptom is that the slider stops on the latest slot, but the data shown is from the previous slot. Now it is passed through unchanged.

### How sampler data (dynamic sampler) is replayed

The sampler panel has two blocks of data, with different sources and different replay methods:

- **The table keyed by data source**: `/live`'s `latest.ds`. Each sync archives the entire `latest` to
  `runs/<run>/live.jsonl`; during replay, the last entry is taken by `captured <= asof`, so what each slice sees is
  the quota, accepted count, grading, and in-flight count at that moment.
- **Rolling report (feed)**: `/live`'s `entries` (about one every 30 seconds, 60-entry window).
  Previously only `latest` was archived, so during replay the feed contained only step/restart events, and the sampler's own
  "accepted X/Y · judged … · pass …" were all lost. Now during sync, `entries` is archived along with it:
  Deduplicate by the `log_time` of the previous archived entry (window 30 minutes > sync interval; without deduplication, it would be stored twice),
  write it into `live.jsonl`'s `entries` field and index it into the `live.entries` column.
  During replay, merge the details archived in each occurrence before `asof`, deduplicate by `t`, and take the last 60 entries.
- **Old repositories do not have `entries`** (this field was added later): fall back to assembling a report from the `latest` of each sync
  at **sync granularity**, and label it on the panel as 「details are at sync granularity」——it will not pass off one every 20 minutes
  as one every 30 seconds. Both the online (`/api/live`'s `entries_approx`) and the offline (`bundleLiveEntries`)
  paths carry this marker.

### Render race in the slice detail panel

`enterReplay()` is 「first `setExpanded(true)`, then `goto(idx)`」; both times it calls `renderSlice()`
and sends requests concurrently; on the first call `asof` is still null, so it renders **real-time** data onto
the timestamp of the **first slice**, and it may arrive later and overwrite the correct render. The symptom is that the toolbar says
「slice 29/29」, but the panel body says 「sync point 1/29」 + real-time data.
The fix is to give `renderSlice()` a guard: after the async return, if `i !== state.index`, discard it directly.

### How the frontend hooks in

In the original site's `js/app.js`, all requests are hard-coded relative URLs (like `api/status?run=pro`).
The telemetry layer does not modify these calls; instead, in `js/telemetry.js` it **replaces `window.fetch`**:
As long as the path matches `/api/`, it appends the `asof` parameter. This way, not a single line of the original site code has to be changed for replay.

But there are a few things interception alone cannot do, so 6 changes were added in `app.js` (all with `[telemetry]` comments,
9 markers in total):

1. **`isFinal()` must recognize replay.** The original site treats `mode === "ended"` as "this run has ended",
   once ended, it no longer polls and does not draw the sampler panel. In a replay slice, `mode` remains as-is, but if handled according to the original logic,
   the sampler panel would disappear entirely. Adding a layer of `&& !M.replay()` solves it.
2. **`vnow()` must be frozen.** The original site computes "now" as `服务器时钟 + 本地已经过了多久`, which keeps moving forward.
   During replay, it must directly return `clock.now`, i.e. the slice time; otherwise the relative time on the page will slowly drift.
3. **The status term must be able to show the slice.** The original site displays `in progress` / `completed`; during replay it is changed to
   `replay · 2026-09-17 15:11Z`, to avoid being misread as "this step is running".
4. **The telemetry layer must be given a refresh entry point.** The original site caches sequences by metric (`S.series`),
   when switching slices, the cache must be invalidated; otherwise the charts still show old data. So `app.js`, through `Telemetry.bind()`,
   exposes a `refresh()` that clears the cache, refetches state, and redraws.
5. **The evaluation leaderboard card carries `data-bench`.** When chart linkage selects an evaluation leaderboard, it must be able to recognize which leaderboard was selected.
6. **Granularity hint for sampler details.** During replay, if the details are only at sync granularity, next to the time in the feed card
   add 「details are at sync granularity」.

In addition, only two lines were added to `index.html`: one line imports `telemetry.css`, and one line, **before** `app.js`,
imports `telemetry.js` (the fetch interception must be installed first, otherwise the first request will miss `asof`).

That "replay" button in the navigation is a toggle: `enterReplay()` / `exitReplay()` are inverses of each other,
`state.on` records whether it is currently on (based on whether the toolbar is displayed, not inferred from `asof`——just after clicking,
in the instant when the timeline has not finished loading, `asof` is still null). So clicking again goes straight back to real time,
without having to go over to the toolbar and press "back to real time".

The telemetry layer and the original site code have exactly two interfaces in total: `Telemetry.replay()` and `Telemetry.bind()`.

### Why the replay interface is full-screen

The replay panel has two states, and the toggle button is at the far right of the toolbar:

- **Full-screen** (default): `.telemetry-bar` becomes `position: fixed; top: var(--nav-h); bottom: 0`,
  inside is a flex column——the 42px toolbar is fixed, and the detail area `flex: 1` plus `overflow: auto` takes up the remaining height.
  The navigation itself does not move, so the slice controls and "back to real time" are always reachable.
- **Collapsed**: it falls back to a 42px toolbar attached below the navigation, and the entire detail block `display: none`,
  the original dashboard below is revealed and rendered for this slice.

At first it was made as a panel half a page high embedded in the toolbar, but it was very awkward in practice: the details include a table with more than twenty steps,
plus announcements and evaluations, three blocks of content, crammed into 52vh, it could only keep scrolling internally, and the lower half of the screen still had the original dashboard taking up space.
After switching to full-screen, all the information for one slice can be seen on one screen, and the original dashboard retreats behind a button.

When writing this layout, I stepped into a flex pitfall: `.telemetry-bar.expanded` is a column-direction flex container,
while `.wrap` comes with `margin: 0 auto`, and **auto margins override `align-items: stretch`**,
so the toolbar shrank to content width and floated centered in the middle. Giving `.telemetry-bar > .wrap` an explicit `width: 100%` solved it.

### Offline copy

`bun src/export.ts` compresses the data in the repository into a
`window.__TELEMETRY_BUNDLE__` written into `site/data/bundle.js` (about 2 MB, of which about 0.3 MB is
sampler rolling details——needed for replaying the feed), then generates a `site/offline.html`.

When a bundle is present, `telemetry.js`'s fetch interception slices and returns in place directly, without sending a single network request.
So double-clicking `offline.html` opens it; no server needs to be started, no network connection is needed, and replay still works.

The cost is that it is a snapshot from the moment of export, does not update itself, and must be re-exported when the data changes.

### Consistency between the two paths

The same data has two retrieval paths: online uses SQLite, offline uses bundle. Each side has its own asof slicing logic,
Duplicate implementations are risky — so I compared them field by field and confirmed they are interchangeable.

The approach was to open `offline.html` (which shares the same source as `/api/*`), and use `XMLHttpRequest` to bypass `telemetry.js`
the fetch interception to hit the real server, then compare with the bundle result obtained from `Telemetry.api()`:

```js
const a = await xhr('/api/status?run=pro&asof=1789648245');   // server-side
Telemetry.setAsof(1789648245);
const b = await Telemetry.api('api/status?run=pro&asof=1789648245'); // offline bundle
// stringify after sorting object keys before comparing, to avoid false differences caused by key order
```

Across 4 slices (earliest, middle, second-to-last, latest) × 7 interface types, 45 comparisons in total,
Except for `offline`, a flag bit that intentionally differs, everything else matched.

This comparison caught three real bugs, none of which could be found by "looks right":

1. **The server-side `totals` used the latest value.** During replay, `/api/status`'s `tokens_cum` should have been that
   moment's value, but the fallback at the time read the latest `status.json`. The reason was subtle: the
   `getTimelineAll` SELECT statement did not list `totals`, so `tl.totals` was undefined,
   so it silently fell back to the latest value. Now it uses a dedicated `getTimelineAt()` to fetch the whole row directly.
2. **benchmarks order changed.** The table's primary key is `(bkey, run, step)`, and the `WITHOUT ROWID` table sorts by primary key,
   so the query came out in alphabetical order for `automation / deepswe / inhouse-coding`, whereas the original site had
   `deepswe / inhouse-coding / automation`. Added a `ord` column to remember the original order.
3. **The offline bundle's step list had duplicates.** At the time, `export.ts` used the event stream's row count to infer the step list,
   but steps that were rerun had two rows in the event stream, so that step appeared twice in the detail table and the step count was inflated.
   Changed to use `axis.steps` as authoritative.

There was another issue of the same kind in the offline bundle: `/api/tags` was not filtered by `asof`,
so during replay it listed metric names that did not yet exist at that moment. Now the export includes the `tagFirstSeen` array.

## 7. Server

```
bun src/server.ts --port 8787
```

**Live mode (URL without `asof`)**

| Interface | Data source |
| --- | --- |
| `/api/runs`、`/api/status`、`/api/live`、`/api/notices`、`/api/benchmarks` | Forward to original site (about 25 KB total) |
| `/api/tags`、`/api/series` | Local SQLite (about 500 KB) |
| `/api/content` | Two JSON files under local `content/` |

`/api/content` does not exist on the original site; it returns `{metrics, insights, ...}`, for the documentation panel.
It **ignores `asof`** — explainers and insights are documentation, not data, so slicing by time has no meaning for it.
It reads the file on every request, so after changing `content/` there is no need to restart the service.

Any forwarding failure (network outage, original site down, 6-second timeout) automatically falls back to rebuilding from data in the repository, so the page will not go blank.
Adding `--offline` can completely disable forwarding and route everything locally.

**Replay mode (with `asof=`)** everything goes local, no network.

## 7.1 How metric explainers and insights are wired into the page

This content has three entry points, all implemented in the telemetry layer; the original site code only has two extra buttons:

1. **The "Explainers" button in the navigation** → opens a full-screen documentation panel, with group filters on the left and cards on the right.
   The panel is an overlay independent of the app.js router, so the original site's route table does not need to be changed, and the offline copy can use it too.
2. **Any chart's detail box** → uses `MutationObserver` to watch for class changes on `#modal`,
   as soon as it opens, it appends this metric's explainer. The original site's `openChart(tag)` writes the metric name into
   `#modal-title`, and the telemetry layer reads it for lookup, so **not a single line of original site code needs to change**.
   The detail box contains only the most relevant sections (what it measures, why we watch it, this run's measurements),
   the detailed reading is folded inside `<details>`.

   The detail box layout hit a pitfall: `.modal-card` is a vertical flex of `max-height:100%`,
   once the explainer block goes in, it **proportionally compresses all child items**, and `.modal-chart` is squeezed from 420px to 44px,
   while `.chart-plot`'s `min-height:60px` makes the canvas instead overflow the container, with axes and curves piling up together
   (more obvious after expanding "How to read"). The fix is for the telemetry layer to use `modalSplit()` to put statistics and charts into the left column,
   and the explainer occupies the right column separately and scrolls on its own: only DOM positions are moved, charts and statistics are still looked up by id, and app.js still does not need to change.
   The left column `flex:1 1 auto` fills the space, the right column `flex:0 0 400px` + `overflow-y:auto`,
   expanding the explainer only affects the height of the right column; the chart column does not move a single cell.
3. **Cards link to each other** → each explainer lists related metrics at the bottom; clicking one jumps to that entry;
   insight cards list the metrics they involve at the bottom, also clickable.
4. **The third tab, "Provenance Overview"** → looks at it from the material side instead: each paper/blog/official doc/own calculation is a card,
   listing which entries cite it and what stance each takes. The sidebar gives a cross-validation ledger
   (N entries registered, M cited, how many places marked "doubtful · boundary"), plus a **search gap**:
   no public material was found that could verify the corresponding reading. A gap is also a conclusion — listing it separately keeps readers from
   assuming by default that every explainer has literature backing.
5. **The dashboard table headers** → the dynamic sampler's data sources table and the two batch composition tables
   are rendered by app.js. The telemetry layer does not change it; instead it uses **event delegation** to catch clicks on column headers, mapping by "table type +
   column header text" to the `table/...` batch of entries (group "Sampler Tables"), then goes through the same `openDoc`.
   the table is fully rebuilt on every 10-second poll, so you cannot bind a listener directly to `th`; `title` is also
   lazily added when the mouse passes over. Entries starting with `table/` have no corresponding curve, so the card does not draw a "View this curve" button.
   The process of verifying the definitions of this batch of entries is in `docs/en/03-sampler-table-caliber.md`.

There is a detail in lookup: some explainers are written by "family", one covering a family of metrics, such as the freshness buckets'
`partial/<k>/frac`, one covers pro's 0~7 and flash's 0~9. So when an exact match is not found, it will
generalize the tag level by level and search again: numeric segments are replaced with `<k>`, and in `dynsam/<category>/dataset-<id>/...`
the category and dataset segments are replaced with placeholders. This way, clicking `partial/3/frac` also shows that explainer.

**The panel's position is written in the address bar**, so refreshing or sending the link to someone else goes directly to the same column and the same entry:

```
#doc/metrics                                 metric explainers, all
#doc/insights                                data insights
#doc/metrics/group:奖励信号                   only view the "奖励信号" group
#doc/sources/srckind:paper/@adamw            only view papers, and locate the adamw material
#doc/metrics/@critic%2Frewards%2Fmean         locate the explainer for critic/rewards/mean
```

The format is `#doc/<页签>[/<筛选名>:<值>][/@<条目 id>]`, and values are always `encodeURIComponent`
(The `/` in metric ids becomes `%2F`). All triggers are covered: clicking the "Explainers" button, switching tabs, clicking a left-column filter,
clicking "View full explainer" from the detail box, or clicking a card title rewrites the address; **scrolling the list also does** — after scrolling stops for 150 ms,
it writes the entry currently pinned at the top of the list, so if you scroll casually to a spot, copying the address bar gives the link to that entry.
The scroll listener only changes the address without redrawing (`replaceState`), so scrolling all the way does not pile up history entries.

Why not use `location.hash = ...`: that would trigger app.js's `hashchange` route, and `#doc` is not one of its
views in the route table, so it would be treated as an unknown view and fall back to overview and redraw. The panel floats over the full screen,
so redrawing the chart underneath is purely wasted, and it might even flicker when switching groups. So here it is "change the address but do not trigger routing",
Only when first entering the page with `#doc/...` (refresh, external link) does `routeDocHash()` open the panel;
Closing the panel switches the address back to the view from before it was opened, so that a refresh doesn't pop it up again by itself.
Under `file://`, Chrome only allows `replaceState` with a pure fragment (ones with a path are rejected),
What is passed here is exactly `#doc/...`, so deep links in the offline copy work just as well; if it is actually rejected, fall back to changing the hash, the routing function is idempotent.

In the offline copy, this part still works: `export.ts` will pack the contents of `content/` into
`bundle.js`, in `telemetry.js`'s `bundleApi` a `/content` branch was added that returns in place.
(This branch originally omitted three fields: `sources` / `sources_note` / `sources_gaps`,
so the "provenance overview" in `offline.html` was empty; it has already been filled in.)

### How content is maintained

Explainers are not written as strings scattered in HTML, but as structured JSON. Each entry has fixed fields
(`what` / `how` / `why` / `read` / `observed` / `traps` / `related`, optional `table`),
This way there is only one rendering logic; changing the layout doesn't require touching the content. Group drafts are placed in `content/_draft/`,
One file per group (concurrent writes to different files will not overwrite each other), merge:

```
bun run mimo:content          # validate + merge into content/metrics.json
bun run mimo:content --check  # validate only, do not write
```

Merging does three things:

- Validate that each entry has all required fields, `read` is in the range 3~6 entries, `traps` does not exceed 4 entries
- Deduplicate by id (when two groups both write the same metric, keep the entry with more complete fields and report it)
- The `dynsam/<category>/dataset-<id>/num_accepted/{step,held,carryover}` family
  is condensed into 3 entries: writing 25 datasets one by one would get 25 cards with identical content; change it to "explain the concept once +
  one comparison table of each data source", with no numbers missing. The numbers in the table are calculated on the fly from the store during merging.

`insights.json` is handwritten and is not managed by the merge process, but it is also validated once.
What is specifically guarded against is this pitfall: **writing Chinese quotation marks as half-width quotation marks in JSON will truncate the string early**,
The error location is hard to spot at a glance, so give it an explicit message.

### Provenance evidence

Each explainer can carry a set of 「provenance evidence」, stating the source of this reading: public papers, engineering blogs, official documentation,
or conclusions we calculated ourselves from the data. On the page there is a rounded button 「Provenance evidence · N items」,
Only when clicked does it expand the full explanation (title, author, year, **verbatim original quotation**, and which sentence it specifically supports/refutes).

Structurally, a deliberate separation was made:

```
content/sources.json     registry: title, author, link, verbatim citation. **All URLs exist only here**
content/_draft/*.json    in entries only write ref: {"ref":"grpo","stance":"support","note":"…"}
content/_research/*.json raw output of the research subagent; apply_sources.ts consumes it
```

This separation has three benefits: URL accuracy depends only on the registry (manually verified), and the sub-agent **has no opportunity to fabricate links**;
When one source is referenced in multiple places, changing it once is enough; a wrongly referenced ref will fail directly at build time, and the page will not show
sources that cannot be opened or do not match. `stance` has only three kinds: `support` (supports our reading),
`challenge` (conflicts or gives boundary conditions), `context` (background). `challenge` is the most valuable kind,
it records "under what conditions this reading does not hold".

Process:

```
# 1. The research subagent writes content/_research/*.json (only ref may be written; verbatim source text must come from pages it fetched itself)
# 2. Apply to entries (the family id is written to all dataset entries in that family; at build time take the union by ref)
bun run mimo:apply-sources
# 3. Merge into the registry
bun run mimo:registry
# 4. Verify: for arXiv, compare the real title by id (70 entries); for web pages, check whether the citation exists verbatim
bun run mimo:verify-sources
# 5. Expand into full sources and validate
bun run mimo:content
```

The verification script deserves special mention, because **writing arXiv ids from memory has a high probability of error, and after an error the link still opens,
it just points to another paper, and it is almost impossible to spot with the naked eye**. In this round of research, our own briefing wrote 5 ids wrong
(`2002.11803`, `2506.17863`, `2506.10947`, `2508.10695`, `2509.23798`), all were caught by this script
and the sub-agent's per-paper verification. `verify_sources.ts`'s approach is: query the official API by id to get the real title,
and compare word sets with the title in the registry; when the real title is completely contained in the registry title (when the title has an explanatory suffix like 「Appendix B」)
also counts as passing. For web entries, it fetches the body text to check whether the quotation appears verbatim — this check is ineffective for frontend-rendered pages
(that's how those two Notion pages slipped through), so they can only be verified separately by rendering with a real browser; the conclusions are recorded in the script's
`RENDERED` whitelist.

At build time, two additional types of sources are automatically added to ensure every card has provenance to click:

- **Official wording**: metrics present in the original site's `meta.json`'s `descriptions` (22 fixed metrics),
  use the official English original text as `quote`, and note "if it conflicts with this, the official source prevails";
- **This site's data**: when there is neither literature nor official explanation, it explicitly says "this round of provenance did not find a directly corresponding
  public literature", and gives the curve link for that metric so readers can verify it themselves.

Parsing is in `sources.ts`; the server side and offline export share the same function; it is **idempotent for already-expanded entries**,
so when `metrics.json` (the build artifact) is parsed again, it will not insert duplicate sources.


**Interfaces added by telemetry itself** (not present on the original site):

| Interface | Purpose |
| --- | --- |
| `/api/telemetry/timeline` | Timeline of the replay slider: sync points + the state at each sync point |
| `/api/telemetry/summary?asof=` | A horizontal summary of some slice, used by the replay panel |
| `/api/telemetry/store` | Repository size statistics |

`/api/tags` has a deliberate deviation: it **echoes back the `v` that comes in with the request**. The original site returns its own version number,
but the frontend uses `v` as a cache key; if the live `/status` version is newer than the repository, the mismatch between the two will cause the sequence cache
to be repeatedly invalidated. Echoing back avoids this problem.

## 7.2 How chart linking is done

The feature itself (check "linking", click a step on any chart, and all charts jump to the same step) is written in the README,
Here we only discuss the implementation and why it is done this way.

**What the requirement looks like.** Each chart on the original site manages itself: `pointermove` / `pointerdown` triggers its own
`_hover`, draws the vertical line, value point, and readout box on its own canvas, and then `pointerleave` removes them.
To "follow along all at once with one click", you have to reach all these mutually independent chart objects at the same time, but `app.js` stores the instances in
its own closure's private state (`S.cards`, `S.telemetry`), which cannot be accessed from outside.

**Three paths, chose the third.**

1. In `app.js`, open an extra `[telemetry]` outlet and expose `S.cards`. Feasible, but every time a feature is added
   you have to modify the original site files, and `S.cards` only covers card charts; benchmarks, batch composition, and detail boxes
   each have their own containers, so exposing them would require another round of selection.
2. Inferring instances from the DOM: attach data attributes to canvas and maintain a mapping via event bubbling. This avoids modifying the original site,
   but the chart instances have no markers at all, so the mapping itself would have to be established through additional changes.
3. **Wrap the constructor.** `charts.js` is loaded **before** `telemetry.js` (the order of `index.html` is
   `format.js → charts.js → telemetry.js → app.js`), so when `telemetry.js` executes
   `window.Charts` is already there. Wrap `Charts.Line` / `Charts.Stacked` each once:

   ```js
   var Wrapped = function (container, opts) {
     var inst = new Orig(container, opts);
     registerChart(inst);
     return inst;            // the constructor returns an object; what new produces is the original instance
   };
   Wrapped.prototype = Orig.prototype;
   ```

   A constructor returning an object will override `this`, so `app.js`'s `new Charts.Line(...)` gets
   is still the original instance; `instanceof`, `destroy()`, `setData()` all remain as before, while the telemetry layer, in
   `registerChart`, gets every instance. Neither of the original site's two files needs to be modified.

**After obtaining the instances, do three things:**

- **Click.** Attach `click` on canvas: `_hover(e)` first calculates the nearest x according to the original site's logic, and `Line` uses
  `prepared.series[].xs` to look up the step number, and `Stacked` directly uses `hoverI` to get `data.steps`.
  Step number is global state, not x—under the replay time axis the two runs' x values differ; only the step number can align them.
- **Draw.** Reuse the original site's drawing directly: `Line` sets `hoverX` then `draw()` + `_tooltip(x)`;
  `Stacked` synthesizes a fake event of `clientX` landing on that bar and feeds it to `_hover()`.
  So the linked annotation looks exactly like "mouse hover"; there is no second drawing path to maintain.
- **Receive.** The handler for `pointerleave` is registered by the original site; it cannot be replaced, nor is it easy to preempt; so register another one
  `pointerleave`, running after the original site's one, to add back the linked step. The two handlers run within the same event dispatch
  to completion synchronously; the browser repaints only once, so no jitter is visible.

**Value column.** The column at the card's top right was originally the latest value; when linking, it changes to "the value at that step", by rewriting
`card-head .val`'s `innerHTML`; before modifying, first save the original, and restore it on cancel.
The value-column layouts differ between the two card types, chart-card and benchmarks (benchmark has an extra run name),
so decide whether to add the run name based on "whether the original contains `span.dim`", rather than hardcoding a template.

**A few deliberate choices:**

- When linking is off, these handlers `return` at the first statement, so page behavior is frame-for-frame identical to the original site;
  The checked state is stored in localStorage; which step is locked is not stored—refreshing returns to real time.
- If a chart does not have that step (metric missing value, benchmark's scatter points are sparse, that run has not reached it yet),
  the vertical line is not drawn, and **its own annotation from the previous round is cleared**. We stepped on this once: only `return` without clearing,
  resulting in some charts having jumped to step 26 while several remain at step 24.
  The value column instead falls back to the nearest step and marks the actual step number (`@s19`), because "how much was this run at that time" is still meaningful,
  but the step number must be marked out, otherwise it will be taken as the number for that step.
- The control is mounted at the far right of the chart toolbar, together with `step/time`, `linear/log`, `smoothing`.
  It was initially placed on the right side of the nav; measured in a 900 px wide window it made the page header overflow into a horizontal scrollbar
  (the original site's row of "total cost + four city clocks" was already nearly full), and after moving it into the toolbar it does not widen at any width.

**To be clear about the cost:** this layer depends on how several of the original site's internal members are written—`_hover`, `_tooltip`,
`hoverX`, `hoverI`, `prepared`. `sync.ts` compares the hash of the original site's frontend assets on every sync,
and prints it out when the site changes; if these names are actually changed, linking will break (other features are unaffected),
at which point just update `telemetry.js` against the new version in `data/upstream/`.

## 7.3 How the announcement panel is built

The original site's notices are an English list that only grows and never shrinks; the telemetry layer replaced it with its own block (Chinese translations, scrolling list,
marking the training step when each announcement was posted, one positioning slider per run). Here we only discuss the implementation and tradeoffs.

**Conclusion first: this panel does not touch app.js, but it also does not reuse its rendering.** The original site's `#notices` renders as usual,
it is just hidden by the telemetry layer adding a class (`#notices.mn-src-hidden { display: none }`),
and the panel inserts itself after it, fetches its own data, and renders itself. The reason is that the requirements already exceed "adding a layer on top of the original text":
translation, scrolling, step numbers, and sliders all need their own structure; reverse-engineering the DOM assembled by app.js back into data and then rearranging it
is more fragile than rendering it anew.

**So how do we know "the announcements changed"?** Use `MutationObserver` to watch `#notices`'s `childList`.
app.js redraws it in three cases: the announcement list changed, the entire overview is redrawn (switching views / switching back to a replay slice /
data version changes), and app.js calls it once itself after the view is rebuilt. The telemetry layer does not need to distinguish among these;
refetching with a 120 ms debounce uniformly is enough. When `#notices` is rebuilt as a whole (in `renderOverview`
`root.innerHTML = ...`), the observer becomes invalid along with the node, so `ensureNoticesPanel()`
compares node identity every time: if it changed, it reattaches the observer and refetches; if the panel itself was deleted, it rebuilds it.

There is a place here that is easy to write into an infinite loop: the panel rendering itself also triggers the observer on `#main`
(which is also responsible for patching the chart toolbar). So data fetching is triggered only by the observer on `#notices`,
and the observer on `#main` only performs the idempotent check of "whether the node is still there"; the two sides do not trigger each other.

**Where the data comes from.** The panel requests three endpoints itself, rather than reading app.js's private state:

| What is needed | Where it comes from |
| --- | --- |
| Announcement body and timestamp | `/api/notices` (during replay the server truncates by `asof`) |
| Run list and color scheme | `/api/runs` (fetched once and cached) |
| Completion time of each step | `events` in `/api/status?run=<key>` (only `kind === "step"` is taken) |
| Chinese translation | `notices_zh` of `/api/content` (the same pathway as metric explainers) |

**How the step number is computed.** For each step, take the last completion time—reruns make the same step number appear twice,
and only the latter is final and effective (flash has 24 steps but 26 step events; section 3 already stepped on this pitfall once).
Then for one announcement:

```
Completed step number = max{ step | that step's completion time ≤ announcement time }
```

Take the "maximum step number" rather than the "most recent completion", because reruns can make the "most recently completed" fall back to a smaller step number,
while what the reader wants to know is "how far training had gotten at that time". In the replay slice, `/api/status` has already been truncated by `asof`,
so there is no need to judge again here.

**The positioning slider uses indices, not step numbers.** The first step recorded locally is not step 1 (step numbers earlier than the first snapshot
have no completion time); if the slider were laid out by `1..max`, dragging the front section would do nothing.
So the slider's value range is the index of the "recorded steps" array; the value range is decoupled from step numbers, and every position has a corresponding result.
Scrolling is computed using the difference of `getBoundingClientRect()`, not `offsetTop`: the reference for `offsetTop` is
the nearest positioned ancestor, which is not necessarily the same as the scroll container (we stepped on this once, and the scroll amount was always computed wrong).

**Why the translation stores the English original.** Each `content/notices.zh.json` entry is `{en, zh}`:
`en` is the English original at the moment the translation was written. If the original site rewrites an announcement, the translation does not automatically follow,
at which point the page marks it "original updated" to warn that it may be outdated—better than silently showing a Chinese sentence that does not match the original.
If a new announcement has no translation, it falls back to English and is marked "untranslated". This file is conveniently validated by `bun run mimo:content`
(each entry must have `zh`; missing `en` only warns and does not error), and like insights.json it blocks the low-level mistake of Chinese quotes being written as half-width
and causing JSON truncation.

**Translations are automatically filled in by a model (`translate.ts`).** Each time `sync.ts` ingests data and finishes rebuilding the index,
it calls `src/translate.ts` once: it compares the announcements in the repository against the translation file,
picks out the two categories of "no translation" and "`en` no longer matches the current original", and leaves the rest untouched—so **human-polished translations
will not be overwritten by the model**; only when the original actually changed will it be retranslated. The translation file has the same announcement order as the store (newest first),
and the `note` field is also preserved as is.

The model goes through env (the same path as `scripts/image_prompt.py`): `OPENAI_BASE_URL` / `OPENAI_API_KEY`
Required, `TEXT_MODEL` optional (defaults to `glm-5.3-flash`; if missing, falls back to `VLM_MODEL`).
A request has at most 8 announcements; 2 requests run concurrently by default; batches run through a fixed-size pool, and within a batch everything is fetched in one call.
The return requirement is a JSON object of `{"<id>": "<译文>"}`; when parsing, tolerate one layer of ```json fence,
A translation that is empty, contains no Chinese, or is identical to the source counts as a failure—retry the whole batch, and if the retry still fails, skip it,
**Do not let a translation failure kill the entire sync** (the data is already in the database; the translation can be filled in next time). The exit code is only useful when running standalone:
if there is an entry that failed translation, it is 1.

The prompt hard-codes two things that are easy to get wrong: **which words stay in English** (`pro` / `flash` / `mimo-v2.6-pro`,
abbreviations such as dataset and benchmark names `cyber` / `DeepSWE`, `GPU OOM` / `VRAM`, and `rollout`) and
**which expressions should get idiomatic renderings rather than literal word-for-word translation** (`at step 17` → step 17, `from step 15` → from step 15,
`the pro run` → this pro run, `grader deployment` → grader service, `expert load imbalance` →
expert (expert) load imbalance……). For ones like `expert` / `grader` that have common Chinese names, write them as "Chinese (English)",
so `grader` will be "grader (grader) service" rather than a bare English word.
The prompt also pins two human translations as examples, fixing the tone and sentence breaks; to adjust the style, change `translate.ts`
the three parts `KEEP_EN` / `GLOSSARY` / `EXAMPLES` in it, then `bun run mimo:translate -- --force`
retranslate.

**Incidentally, step number correlation does not need to be done separately.** The `pro@s17` on the panel is computed by the frontend from `/api/status`'s step
events on the fly (formula in section 7.3); as soon as a new announcement is stored, it automatically has a step number, and what is obtained in the replay slice is still the progress at that moment;
`translate.ts` just recomputes the same measure and prints it in the sync log, making it easy to compare at a glance, without persisting it—
persisting it would instead become stale because re-runs rewrite the step number completion time.

**Why the panel is collapsed by default.** The first version was "all announcements + fixed-height scrolling"; in practice it had two problems:
This block took up 531px on the first screen (the status cards and charts were all pushed to the second screen), and the bottom edge of the scroll area happened to cut one announcement
in half, looking like broken layout. Now it has been changed to: by default render only the latest 3 (no height set, no scrolling, so there are no
half rows); only when you click the button for earlier ones does it expand into a scroll area; at the bottom of the scroll area add a `mask-image` fade,
when you scroll to the end, remove the fade—"there is more below" and "you have reached the bottom" should look like two different things.
The positioning slider is the same, collapsed by default: two sliders plus hint text are 84px, and there is no need for them to sit there when not in use,
so it is hidden behind a "positioning" button on the right side of the title, and the open/closed state is stored in localStorage.

**The positioning slider's position must be stored separately.** The panel is redrawn as a whole due to expansion, language switching, or toggling "compare with source",
after redrawing, the slider returns to the default "latest step" while the highlight is still on an old announcement—the reading and the pointer are inconsistent, visible at a glance.
So the current position is stored in `nz.pos[run]`, and when rendering it is filled back in from it, so it is not lost on redraw.

**The detail box's statistics row was also tightened up along the way.** After the left column gives up 400px for the explainer, only about 640px remains; the original site's run name
reserved `min-width: 240px` squeezes one row of statistics into two lines (`mean`/`points` drops to the second line),
looking misaligned. The telemetry layer changes the name to content width and reduces the inline spacing from 16px to 12px, so it fits on one line.

## 7.4 How custom dashboards are built

That batch of charts on the home page comes from `pins` of `/api/runs` (18 metric names); app.js in `renderOverview()`
`for (const tag of S.cfg.pins) grid.appendChild(chartCard(tag))`. **Switching to a different set of charts = switching this array**,
so the telemetry layer's approach is: maintain several "dashboards" itself (a name + a list of metric names), and when switching tabs, replace
`S.cfg.pins` with this dashboard's array, then have app.js redraw the current view.

For this purpose, four more handles are exposed in `M.bind({...})`:

```js
pins: (tags) => { if (tags) S.cfg.pins = tags; return S.cfg.pins; },
render: () => renderView(),
union: () => (S.union ? S.union.list : null),
board: (grid, tags) => { /* only swap the cards in the chart area; see the section below 「Switching tabs only replaces the chart area」 */ },
```

`pins` writes and reads back when passed a value other than an empty array (`app.pins()` reads when called without arguments), `render` redraws the current view,
`union` gives all metric names (the bulk selection dialog needs the full list), `board` swaps the chart area in place (the main path for switching tabs).
The first three are all one-line arrow functions, and `board` is about ten lines; this is the only new change to the original site at this layer.

**Why reuse app.js's `chartCard` instead of drawing them yourself.** The charts in custom dashboards and the charts on the home page must be the same kind of thing:
hover crosshair, top-right value column, x-axis step/time preference, chart linking (section 7.2 hooks in by wrapping `Charts.Line`),
clicking the title to pop up the explainer (section 7.1 hooks in through `#modal`'s class change)—all these capabilities hang off the cards created by app.js.
Rendering them yourself amounts to reimplementing these capabilities, and when the site adds features later, they will be missed again.

**Keep a copy of the site's original batch of charts yourself.** Once `S.cfg.pins` is overwritten, the original value cannot be retrieved,
and the "default" tab would have nothing to switch to. And pins are only in `/api/runs`'s response, so the telemetry layer in
the `window.fetch` interceptor does one extra step for `/api/runs`: `res.clone().json()` copies `pins` and stores it
(`noteSitePins()`); both paths, `api()` and the offline bundle's `bundleApi()`, also call it once each.
In the offline bundle, `BUNDLE.config.pins` is the original value, so it can be copied just the same.

**Dashboards are stored in localStorage (`telemetry.boards`).** In the form
`{active: "<id>|default", list: [{id, name, tags: [...]}]}`. They are kept locally rather than written into the repository,
because "which charts I want to see" is a personal preference, not site data; putting them in localStorage also incidentally lets the offline copy (`file://`)
create tabs just the same. Metric names may become invalid due to a site revamp, and the edit dialog will list "the site no longer has these metrics"
as a separate group, making them easy to delete.

**The UI is split into three parts, all in the telemetry layer:**

| Where | What it is |
| --- | --- |
| above the overview chart area | Tab bar (default / each custom tab / ＋ new), `本 Tab N 张图`, edit, clear |
| each chart card of `#metrics/<族>` | top-left checkbox + bottom floating `已选 N · 全选本页 · 清空 · 加入看板 ▾` |
| edit dialog | left side grouped by metric family, right side collapsible sections with checkboxes; search / show selected only / clear all / delete tab |

The injection point and linkage are the same as the announcement panel: `MutationObserver` on `#main` runs once per DOM change
`ensureBoards() / ensurePickBoxes() / ensurePickBar()`, and fills in what is missing. There was a pitfall here:
**Writing `innerHTML` itself also triggers this observer**; if `renderBoardBar()` unconditionally rewrites every time, it will poke itself,
and the page freezes completely. Now it first computes a signature (active + each tab's name and count); if it is the same, it returns without touching the DOM;
The floating bar's visibility and count also each do the same thing.

**Switching tabs only swaps the chart area; the scroll position does not jump.** The first version did a full-page redraw of `render()`, and the result was that every time you click a tab
The page just jumps: `renderOverview()` first clears `#view-overview` (`root.innerHTML = ...`),
The document height instantly collapses to just the page header, the browser conveniently clamps the scroll position back to the top, and by the time the charts are rebuilt the position can no longer be returned to.
—— The user is looking at chart 12, switches tabs, and is sent back to the top of the page. Now `M.bind()` passes one more
`board(grid, tags)` handle, and app.js only does "destroy the cards in this grid + build new ones in place":
removes the records that fall within the grid from `S.cards`, destroys the charts, `grid.innerHTML = ""`,
then builds them one by one according to the new set `chartCard(tag)`. The page header, status cards, announcements, benchmarks, and batch composition are all left untouched,
Measured before and after switching tabs, the viewport position of `window.scrollY` and the Tab bar is completely unchanged.

`applyBoard()` still first compares `app.pins()` with the target set, and if they are the same it does nothing —— this is the second gate that prevents
the "injection → redraw → re-injection" loop; only when the chart area has not yet rendered does it fall back to redrawing the whole page,
On that path the scroll position is restored. In the edit dialog, checking boxes in succession is not applied immediately (each application requires rebuilding this group of charts),
changed to 500 ms debounce + a fallback application once when the dialog is closed.

## 7.5 How correlation analysis is done

After a user clicks and holds a certain step on the chart, the most natural question is "why did this step jump". This question cannot be answered by a single curve,
you have to put three things together: the cross-section at the same step, historical co-movements, and engineering events within the time period of this step.

### How the entry point is wired in

`onChartClick()` originally did only one thing: record the step number into `sync.step`. Now it records two more things:

- **Anchor**: which curve was clicked. For ordinary metric charts it is obtained from `card.__card.tag` (app.js's card record is attached to the element),
  The leaderboard card has no tag, so `data-bench` was added to that card (the 4th patch to app.js).
- **run**: the two runs are completely aligned on the step axis, so x alone cannot distinguish them, therefore the click point is compared with "the point of each curve at this step"
  by **pixel distance** —— whichever one is closer is the one that was clicked. The comparison is done only on curves that have a value at this step, to avoid a curve missing this step and being counted as the neighboring step.

So the badge has an extra line with the anchor name and a `分析这一步` button; the same button is also placed at the bottom of the chart detail box
(when step is not locked, the last step of this chart is used as the default), and you can enter without first turning on linking.

### Where it is computed

`/api/correlate` (newly added in server.ts) fetches **all** metric series for a run from SQLite —— about 2000,
The page does not have the full series on hand, so this layer must be on the server side. It returns three parts: `movers` (the metrics with the largest movement at this step,
folded by family), `corr` (metrics that co-move with the anchor), `context` (restarts / version switches / announcements / neighboring steps within the time period).

The algorithm kernel is placed separately in **`site/js/correlate.js`**, written as UMD: browsers load it with `<script>` and attach it to
`window.TelemetryCorrelate`, and server.ts uses `await import(...)` to get the same copy. **There is only one implementation**,
so the numbers computed online and offline are consistent (offline, `bundleApi` has a new `/correlate` branch added to compute in place,
because the offline package already contains the full series).

### Three methodological decisions

1. **The anomaly score takes the smaller of the two scales, z and MAD.** The standard deviation (z) of the change is inflated by a single outlier,
   so a median/MAD scale (zr) is also added; but conversely, for metrics like trajectory-level `max`/`min` that sit near the upper limit all the time
   the MAD of their change is almost 0; if only zr is used, any slight jitter would be counted as dozens of standard deviations and dominate the leaderboard.
   Computing both and taking the smaller value is equivalent to requiring "anomalous under both scales".
2. **Fold by family.** `dataset-xxxx`, `harness-xxx`, and the numeric buckets under `partial/` are all normalized to wildcards,
   within a family only the most anomalous one is kept, and the rest are collected into `members`. Without folding, 33 code datasets would fill the top few places.
   Folding is only for readability, not a statistical definition, so the UI can expand to show family details.
3. **The semantics of `tagset_versions` must be written correctly.** The panel's "within the time period of this step" lists changes in the snapshot of the dashboard metric set.
   It is **not a training config version**: in `tags.json`, the second segment of the version string `3-5513.<步>.<x>.<y>` is exactly the number of completed steps at that time
   (all 9 snapshots of pro were checked one by one and all matched), and `n` is the number of metric names at that moment. A changed list means **the dashboard exposed new metric names**
   —— this is a change in telemetry definition, and is still useful context for "why this step jumped" (be careful when comparing new and old metrics across steps),
   but it cannot be read as the training config having changed. The field is deliberately named `tagset_versions` rather than `versions` precisely to prevent misreading.

4. **First-difference correlation.** Two curves that are both climbing are naturally highly correlated (`dynsam/avg@n` and length's level rank correlation
   is +0.79/+0.93), so the "detrended" column must also be provided —— for each curve, take the difference between adjacent two steps and then compute rank correlation.
   The panel's hint literally says "look at this column first".

There are also two smaller decisions: `training/global_step` (a pure step counter) is blacklisted outright; it and every metric that changes over time
will be highly correlated; the sparse leaderboard series uses pairwise deletion, and the sample size varies by metric, so every row displays `n=`.

### A pitfall to avoid

The event stream (`events.json`) is retained on a rolling basis —— in the repository, flash's events only start at step 8. So when restarts cannot be found for early steps,
the panel cannot say "there was no restart", only "cannot be found". `/api/correlate` will, when "the moment this step completed is earlier than the first entry in the event stream"
additionally push a methodology hint, alongside three fixed hints (small sample, spurious correlation, correlation does not imply causation).

## 9. How to run on a schedule

Windows Task Scheduler or keeping a background process running will both work. The simplest is a loop:

```powershell
while ($true) {
  bun src/sync.ts
  Start-Sleep -Seconds 1200
}
```

The site completes a step in about 3 hours, and the collector emits a report about every 30 seconds, so **once every 20 minutes** is enough.
Running it more frequently will not produce more information, only make the logs longer.

At the end of each sync, announcement translation is run automatically (Section 7.3). It only translates newly added announcements and ones whose original text changed,
When there are no new announcements, not a single model call is made; if you really do not want it to call the model over the network, add `--no-translate`,
then run `bun run mimo:translate` separately afterward to fill it in.

If you run it long-term, note that `data/store/runs/<run>/live.jsonl` and `timeline.jsonl` are appended to each time,
one line every 20 minutes, 72 lines a day. `timeline.jsonl` is currently about 9 KB (18 sync points), and about 3 MB a year.
Starting 2026-09-20, each line in `live.jsonl` carries the sampler details between two syncs (about 40 entries, 10~17 KB),
It will be the larger of the two files: estimated at 20-minute syncs and two runs, about 1.5 MB per day.
If you think it takes up too much space, lengthen the sync interval — the longer the interval, the less of the part outside the detail window (30 minutes) can be captured anyway.

## 10. Extension directions

- **Add more runs.** `paths.ts` and `store.ts` do not hardcode run names,
  the sync logic loops over the list returned by `/runs`. New runs will be collected automatically.
- **Store rollout-level details.** Currently only step-aggregated metrics are stored. If you want to store per-problem results,
  the data volume will increase by an order of magnitude, at which point you should switch to Parquet or DuckDB, see Section 4.
- **Add derived metrics.** The relations in Section 7 of `docs/01` (cost identity, KL weighted sum,
  staleness weighted sum) have already been implemented as `check.ts`; run it and it verifies them one by one, exit code 0 if all pass,
  it can be hooked into a scheduled task as a sentinel — if the site changes its algorithm, it will be the first to find out.

  ```bash
  bun src/check.ts
  ```

  Currently all 22 items pass. It has found two things I had originally taken for granted: the number of buckets in `partial/` for pro is 8,
  and 10 for flash (hardcoding 8 would make flash's weighted sum not match); and `ctx_total = prompt + response`
  is not mathematically exact, but only exact to the 6 significant digits the site provides.
