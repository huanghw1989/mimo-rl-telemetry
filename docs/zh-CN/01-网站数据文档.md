# mimo RL 看板数据文档

这份文档讲清楚 `https://mimo.xiaomi.com/rl/` 这个页面上的数据是怎么来的、每个字段是什么意思、
单位是什么、哪些能直接信、哪些需要留个心眼。

内容全部来自实际抓取（2026-09-17 到 2026-09-18 之间约 18 次同步），不是照抄页面文案。
凡是官方给了说明的，我会标明"官方说明"；凡是我自己推断出来的，会写明这是推断。

---

## 1. 数据从哪来

页面本身是一个静态站点，所有数字都来自背后的 7 个公开 GET 接口。不需要登录、不需要 token，
浏览器打开页面时前端就是去调这些接口。接口根路径是 `https://mimo.xiaomi.com/rl/api`。

页面上写的是"read directly from the trainer's logs"——数据是从训练器日志直接读的，
中间没有人工录入这一步（唯一的例外是离线评测成绩，见 3.5，那是手填的）。

站点在跑两个训练作业：

| key | 名称 | 说明 |
| --- | --- | --- |
| `pro` | mimo-v2.6-pro | 大一点的那个，成本费率 $5.71/秒 |
| `flash` | mimo-v2.6-flash | 小一点的那个，成本费率 $2.855/秒 |

两个作业的指标名不是同一套：pro 有 2019 个，flash 有 2062 个。多数重名，但各自都有独占的。

---

## 2. 接口清单

| 路径 | 干什么 | 返回体积（实测） | 更新频率 |
| --- | --- | --- | --- |
| `/runs` | 运行列表、首页固定的指标、数值格式规则、官方指标说明 | 约 3.5 KB | 基本不变 |
| `/status?run=` | 当前状态：成本、进度、步数事件流、累计量 | 约 3 KB | 秒级变化 |
| `/live?run=` | 动态采样器最新一次报告 + 最近 60 条滚动明细 | 约 17 KB | 约 30 秒一条 |
| `/notices` | 官方公告 | 约 1 KB | 随机 |
| `/benchmarks` | 离线基准评测成绩 | 约 1.2 KB | 出成绩时 |
| `/tags?run=` | 该作业的全部指标名 + 数据版本号 | 约 96 KB | 有新指标时 |
| `/series?run=&v=&tags=` | 指定指标的逐步历史 | 335～424 KB | 与步同步 |

两个要注意的地方：

- **`/series` 必须分批请求。** 指标名很长（有的单个超过 200 字符），一次性把 2019 个指标塞进
  一个 URL 会返回 414。实测按 URL 编码后 5000 字符一批比较稳，2019 个指标大约切成 23 批。
- **`/series` 不认区间参数。** 我试过 `from`、`since`、`start`、`step_from`、`offset`，
  全部被忽略，每次都是全量返回。所以想省流量只能在"要不要发这个请求"上做文章，见第 8 节。

## 3. 逐个接口的字段

### 3.1 `/runs`

```jsonc
{
  "title": "mimo-v2.6 RL",
  "subtitle": "Two reinforcement-learning runs, ... read directly from the trainer's logs.",
  "runs": [{ "key": "pro", "label": "mimo-v2.6-pro", "note": "", "color_index": 1 },
           { "key": "flash", "label": "mimo-v2.6-flash", "note": "", "color_index": 0 }],
  "pins": ["dynsam/avg@n", ...],          // 首页图表区固定展示的 18 个指标，见第 5 节
  "formats": [["^timing_s/", "duration"], ...],  // 数值显示规则，见第 6 节
  "compositions": [ ... ],                // 首页"batch composition"区块的两张图怎么分组
  "categories": ["code", "general", "cyber", "visual", "chat"],
  "social": { "handle": "@XiaomiMiMo", "url": "https://x.com/XiaomiMiMo" },
  "footer_note": "Open is what we value.",
  "stream_start": 1789531200.0,           // 2026-09-16 04:00 UTC，直播开始时间
  "descriptions": { "dynsam/avg@n": "mean pass rate: ...", ... },  // 只有 22 条
  "about": ["We are streaming our RL big runs. ...", "Follow us @XiaomiMiMo."],
  "headline_tag": "dynsam/avg@n",         // 首页大数字用的是哪个指标
  "hist_prefix": "dynsam/passrate/hist9_ratio/"
}
```

`compositions` 告诉前端"batch composition"那两张图怎么切：

```jsonc
[
  { "key": "source",  "label": "data source",      "prefix": "dynsam",
    "groups": ["code","general","cyber","visual","chat"], "derive": "trained", "unit": "prompts" },
  { "key": "harness", "label": "harness (trained)", "prefix": "train/harness",
    "metric": "training/rollouts", "unit": "rollouts" }
]
```

**`descriptions` 只有 22 条，而指标有 2000 多个。** 这是理解这个看板最重要的一件事：
官方只解释了首页会用到的那些指标，剩下 99% 的指标名没有公开定义，只能靠命名规律和训练常识去推。
本仓库的 `notes/06-读看板容易踩的坑.md` 和 `analysis/A1-看板数据解读.md` 里有对这部分推断的详细说明，
以及哪些是不该硬猜的。

### 3.2 `/status?run=`

```jsonc
{
  "run":   { "key": "pro", "label": "mimo-v2.6-pro",
             "start": 1789468339.334, "end": null, "mode": "live" },
  "cost":  { "rate_per_s": 5.71, "so_far": 1358312.77 },
  "clock": { "now": 1789706222.48 },
  "version": "3-5513.17.10.17",
  "step": {
    "last": 17,               // 最后一个已完成的步号
    "last_wall": 1789699763.5,// 那一步完成的墙钟时间
    "since": 6458.97,         // 距那一步完成过了多少秒
    "expected": 12807.7,      // 站点对"一步大概要多久"的估计（秒）
    "progress": 0.5043,       // since / expected
    "phase": "training",      // 当前在哪个阶段
    "gen_frac": 0.4855,       // 生成占这一步的比例，用于进度条上那个分隔刻度
    "restarted_at": null      // 当前这个训练进程是什么时候起来的
  },
  "totals": {
    "tokens_step": 2296260000,  // 这一步训了多少 token
    "trained_step": 25088,      // 这一步训了多少条序列
    "sandboxes_step": 22365,    // 这一步开了多少沙箱
    "prompts_per_step": 1568,   // 一个训练批有多少道题
    "tokens_cum": 37159090000, // 累计
    "trained_cum": 426496,
    "sandboxes_cum": 2108592,
    "restarts": 9               // 累计重启次数（训练器进程自己的计数器）
  },
  "events": [
    { "t": 1789475059.334, "kind": "restart" },
    { "t": 1789492877.82, "kind": "step", "step": 1, "value": 0.564662,
      "delta": null, "tokens": 1800520000.0, "redo": false }
  ],
  "headline": { "tag": "dynsam/avg@n", "last": 0.629303, "prev": 0.635523,
                "first": 0.564662, "first_step": 1 }
}
```

几个关键点：

- **成本是算出来的，不是记的。** `cost.so_far` 恒等于 `rate_per_s × (clock.now − run.start)`。
  我在 15 份历史快照上逐条核对过，误差是 0。
  推论：重启期间成本照算，成本曲线是一条绝对的直线，不含任何信息量。
- **`run.start` 从头到尾没变过**，即使中间重启了 9 次。所以这里的"重启"重启的是训练器进程，
  整个 run 的计时没有重置。
- **`events` 是只追加的完整事件流**，从第一步一直留到现在，包含每次重启。
  两类事件：`kind: "restart"`（只有 `t`）和 `kind: "step"`。
- **`events` 里同一个步号可能出现两次。** 那就是这一步被重跑了，第二次的 `redo` 是 `true`。
  实测 flash 的 step 16 和 17 各出现两次，两条事件的 `value` 还不一样。
  这是个大坑，详见第 8 节第 3 条。
- **`step.phase`** 见过 `training`、`rollout` 等值，站点没有公开枚举。它和 `gen_frac` 一起
  驱动首页那个进度条。
- **`restarted_at`** 用来判断"这条采样器报告是不是当前这个进程发的"——报告时间早于
  `restarted_at` 就说明是上一个进程的遗留。

### 3.3 `/live?run=`

```jsonc
{
  "log_time": 1789705579.334,
  "latest": {
    "t": 1789705579.334,
    "step": 18,            // 正在跑的这一轮是第几步
    "accept": 2504,        // 这一轮已经收进来的序列数
    "target": 1568,        // 目标（= prompts_per_step）
    "judged": 2403,        // 其中已经判过的
    "judged_of": 2504,
    "ds": {                // 按数据源分的四个数：[accepted, target, judged, in flight]
      "code/dataset-bvg7": [71, 52, 65, 41],
      "general/dataset-epqd": [95, 64, null, 5],
      ...
    },
    "passrate": 0.561,     // 采样器自己统计的通过率
    "n": 7203,             // 统计基数（序列数）
    "pr0": 0.155,          // 一次都没做对的题占比
    "pr1": 0.283,          // 次次都做对的题占比
    "partial": [0, 0, 0],
    "working": 256,        // 正在跑的沙箱
    "remain": 422,
    "remain_partial": 691,
    "remain_seq": 220,
    "prewarm": 351,        // 预热中的沙箱
    "prewarm_wait": 1841.6 // 预热平均等待秒数
  },
  "entries": [ ... 最近 60 条同样的结构 ... ]
}
```

- `latest` 里的 `passrate` 和 `/series` 里的 `dynsam/avg@n` **不是一回事**。
  采样器统计的是"当前这一轮已经收到的序列"，`avg@n` 是"这一步训进去的全部 prompt 的平均通过率"。
  两个数一般差几个百分点，不要混用。反过来，`pr0` / `pr1` 与 `/series` 的
  `dynsam/passrate/zero` / `/one` 是同一个统计量，差在快照是步内过程值（pro 第 23 步
  `pr0` 0.131 vs 序列 0.131014）。
- **`ds` 四元组的列名出自原站前端**（`js/app.js` 的
  `{acc: v[0], tgt: v[1], j: v[2], r: v[3]}` → accepted / target / judged / in flight），
  但站点没有为这四个数写过任何文字说明。仓库里能复算的关系（见
  `src/sampler_report.ts`，截至 2026-09-20 共 29 份留档）：
  - `Σ accepted == 面板 accept`、`Σ target == 面板 target == 1568`（29/29）；
  - `Σ c + Σ accepted(未上报 c 的源) == 面板 judged`（29/29），
    等价地 `accept − judged == Σ(accepted − c)`，缺口只来自上报 `c` 的那 8 个 code 数据源；
  - `c ≤ accepted`（232/232 个非空值）；其余 17 个数据源这一位恒为 null；
  - `Σ d == 面板 remain + remain_partial`（29/29，最大差 2）。
  **没有公开材料定义 `judged` / `in flight` 的计数单位**（题还是序列、是否含 partial rollout）；
  站点 `descriptions` 里也没有这四项。表头的 `remaining` 一列不是接口字段，是页面现算的
  `max(0, target − accepted)`，所以受理量一超配额它就恒为 0。
  完整的考证过程见 `docs/zh-CN/03-采样器表格字段口径考证.md`。

### 3.4 `/notices`

```jsonc
{ "notices": [
  { "id": "n-4e29eb", "t": 1789703382.889, "text": "the pro run restarted at step 17 due to a GPU OOM ...", "run": null }
] }
```

`run` 字段目前全是 `null`，说明公告没有绑定到具体某个 run。`id` 是稳定去重键。
公告是理解数据的最重要旁证——比如某一步为什么耗时特别长、某个指标为什么跳变，
答案往往在这几条文字里，而不是在数字里。

### 3.5 `/benchmarks`

```jsonc
{ "benchmarks": [
  { "key": "deepswe", "title": "DeepSWE v1.1", "note": "mini-swe-agent, avg@3", "format": "num2",
    "results": { "flash": { "1": 48.67, "2": 53.1, ... }, "pro": { "1": 58.41, ... } } }
] }
```

三个基准：DeepSWE v1.1、In-house Coding Bench、AutomationBench v1.0.6。

- **这是页面上唯一人工维护的数据。** 点不是自动出现的：某个 step 的成绩是在评测跑完、人工填进去之后
  才冒出来的。所以某个 step 没有点，不代表那一步没评测，只代表成绩还没出。
- key 是字符串形式的步号，不是连续数组——经常跳号。
- 前端只在对应训练步已经完成时才把这个点画出来。

### 3.6 `/tags?run=`

```jsonc
{ "run": "pro", "version": "3-5513.17.10.17", "tags": ["actor/entropy_loss", ...] }
```

- `tags` 是**该作业曾经出现过的全部指标名**，不是当前有值的那些。
  2019 个指标名里，实际有数据的只有 1926 个左右。
- `version` 是数据版本号。看着像 `3-5513.<n>.<m>.<k>`，其中 `<n>` 大致跟着步数走，
  但 **不能当步数用**：flash 在 version `3-5513.26.4.25` 时实际只跑到第 24 步。
  它更像是站点内部的一个修订计数。
- **`version` 变了不代表数据变了。** 实测 pro 在步数完全没变的情况下，
  version 从 `3-5513.14.7.0` 变成 `14.8.0` 再变成 `14.8.15`。想拿它当缓存键要小心。
- **指标名会来也会走。** flash 的 `penalty/signed/pos_scale_clamped`、
  `penalty/stage_credit_group/dev_neg_turns` 等 4 个指标在某一轮之后整条消失了。
  所以"指标集合"不是单调增长的。

### 3.7 `/series?run=&v=&tags=`

```jsonc
{
  "run": "pro", "version": "3-5513.17.10.17",
  "steps": [1, 2, 3, ..., 17],
  "walls": [1789492877.8, 1789506681.7, ...],   // 与 steps 一一对应的墙钟时间
  "run_start": 1789468339.334,
  "series": { "dynsam/avg@n": [0.564662, 0.555333, ...] }
}
```

- **数组与 `steps` 严格对齐，长度相等。** 我在全部 15 份快照上核对过，长度不一致的有 0 个。
  没有数据的位置是 `null`，不是截断。整体填充率约 93%。
- `series` 里只包含**至少有一个非空值**的指标。`/tags` 列了 2019 个，
  `/series` 一般只返回其中 1926 个左右。
- `walls[i]` 是第 `steps[i]` 步完成时的墙钟时间。**只有当新的一步完成时它才会更新**——
  在步与步之间反复抓取，`walls` 的最后一项是不动的。
- **数值会被重写，但只在重跑的情况下。** 详见第 8 节第 3 条。

## 4. 指标名怎么读

指标名是路径式的，第一段是模块，后面逐级细分。以 pro 的 2019 个为例：

| 前缀 | 条数 | 大致是什么 |
| --- | --- | --- |
| `penalty/` | 535 | 奖励惩罚项的中间量。站点自研，没有公开文档，推断成分最多 |
| `partial/` | 327（pro）／385（flash） | 按数据新鲜度分桶的统计。见下面单独说明 |
| `critic/` | 324 | 价值网络相关的量 |
| `actor/` | 257 | 策略网络的损失、熵、梯度 |
| `train/` | 191 | 训练侧统计，包括按 harness 和数据集细分 |
| `ctx_total_length/` | 108 | 上下文总长度（prompt + response）的分布统计 |
| `dynsam/` | 83 | 动态采样器：通过率、题目数、轮数 |
| `ctx_prompt_length/` | 81 | prompt 长度分布 |
| `ctx_response_length/` | 81 | response 长度分布 |
| `env/` | 15 | 沙箱环境状态 |
| `train_infer_diff/` | 11 | 训练器与推理引擎的不一致 |
| `timing_s/` | 3 | 耗时 |
| `training/`、`perf/` | 3 | 杂项 |

几个常见后缀的含义：

- `/mean`、`/max`、`/min`、`/p50`、`/p90`、`/p99` —— 该统计量的不同分位。
  108 个 `ctx_total_length/*` 就是这么来的。
- `/zero`、`/one`、`/mid` —— 通过率恰好为 0、恰好为 1、以及中间的比例。
- `/hist9_cnt/<k>`、`/hist9_ratio/<k>`（`k` = 0～8）—— 把 prompt 按通过率切成九桶后的计数/占比。

**`partial/` 这一段要单独说。** 它把同一组指标按"数据有多旧"切成若干个桶：
`partial/<i>/<指标名>`，`i` 是桶号，桶 0 是这一步新采的，桶号越大越旧。

**两个 run 的桶数不一样**：pro 是 0～7 共 8 个桶，flash 是 0～9 共 10 个桶。
写代码算加权和的时候不能写死 8——写死了在 flash 上会少算一部分，
看起来像"关系式不成立"，其实是数错了桶。

另外还有一个不分桶的全局值 `partial/avg_staleness`，表示"从采样到训练平均隔了几个策略版本"。

实测关系式（pro 17 步、flash 24 步全部成立，最大相对误差 0.15%）：

```
全局 KL = Σ_i (桶 i 的占比 × 桶 i 的 KL)
```

也就是说首页那条"训练推理不一致"曲线，是这些桶的加权平均。它涨起来不一定是模型变了，
也可能只是数据变旧了——这两件事在这个指标里混在一起。第 8 节第 1 条展开讲。

## 5. 首页固定展示的 18 个指标

`/runs` 的 `pins` 数组，按页面顺序：

| # | 指标 | 官方说明（有的话） |
| --- | --- | --- |
| 1 | `dynsam/avg@n` | mean pass rate: for each prompt sampled this step, the fraction of its n attempts that succeed, averaged over prompts |
| 2 | `critic/rewards/mean` | mean reward over trajectories trained on this step |
| 3 | `actor/entropy_loss` | mean per-token entropy of the policy |
| 4 | `actor/pg_loss` | clipped policy-gradient objective |
| 5 | `actor/grad_norm` | global gradient norm before clipping |
| 6 | `train_infer_diff/new_infer/kl` | KL between inference-engine and trainer log-probs on the same tokens |
| 7 | `ctx_total_length/mean` | total context length per trajectory (prompt + response), in tokens |
| 8 | `dynsam/agg_turn/mean` | agent turns per trajectory |
| 9 | `perf/total_num_tokens` | tokens trained on this step |
| 10 | `timing_s/step` | wall-clock of the whole step |
| 11 | `timing_s/outer_gen` | wall-clock of rollout generation |
| 12 | `timing_s/trainer_ops` | wall-clock of the trainer |
| 13 | `dynsam/passrate/zero` | share of prompts where no attempt succeeded |
| 14 | `dynsam/passrate/one` | share of prompts where every attempt succeeded |
| 15 | `dynsam/infra_error/seq_rate` | share of sequences lost to infrastructure failures |
| 16 | `env/active` | sandbox environments in flight |
| 17 | `partial/avg_staleness` | policy versions between sampling and training, on average |
| 18 | `dynsam/num_measurable` | prompts with a measurable pass rate this step |

官方 `descriptions` 里还有 4 条不在 pins 里，但首页别处会用到：

| 指标 | 官方说明 |
| --- | --- |
| `dynsam/avg@n_no_infra` | avg@n with attempts that failed for infrastructure reasons excluded |
| `ctx_response_length/mean` | tokens generated per trajectory |
| `dynsam/passrate/hist9_ratio` | share of prompts by pass rate, in nine bins from none solved to all solved |
| `train/harness/*/training/rollouts` | rollouts in the training batch, per agent harness |

## 6. 数值怎么显示（`formats`）

`/runs` 的 `formats` 是一串 `[正则, 格式名]`，**从上往下匹配，第一个命中生效**，都不命中用 `auto`。

```
^timing_s/                    → duration   秒数转成 "1h 20m" 这种
^perf/time_per_step$          → duration
^perf/gpu_time_s/             → duration
_ns$                          → compact    纳秒当数字压成 1.5M 这种
_gb$                          → gb         保留一位小数，带 GB
^actor/lr$                    → sci        科学计数法
(^|/)(avg@n|avg@n_no_infra|score_mean|accept_rate|valid_rate)$   → ratio   三位小数
(^|/)(seq_rate|effect_ratio|ok_frac|missing_frac|zero|one|mid|
       zero_no_infra|one_no_infra|mid_no_infra|hist9_ratio/\d+)$ → pct     乘 100 加百分号
(^|/)(hist9_cnt/\d+|num_[a-z_]+|n_[a-z_]+|count|size|in_flight|
       active|total|rollouts|max_load|min_load|dead_replaced)$    → int     千分位整数
(length|tokens|_len|decode|prefill)                             → compact
```

注意最后一条是**子串匹配**，不是锚定的。任何名字里带 `length`、`tokens`、`decode`、`prefill`
的指标都会被压成 `12.3M` 这种形式。所以看到某个指标显示成缩写，先确认它是不是被这条规则误伤了。

还有一个坑：`pct` 规则只匹配**最后一段**是 `zero`/`one`/`mid` 等的指标名。
`dynsam/passrate/zero` 会命中，但 `partial/0/dynsam/passrate/zero` 也会命中——因为它匹配的是路径分段。

## 7. 已验证的关系式

下面这些我在抓下来的数据上逐条验算过。它们不是官方文档里的东西，是我自己核对出来能对上的，
写下来是因为它们能帮你判断数据有没有被读错。

| 关系式 | 验证范围 | 误差 |
| --- | --- | --- |
| `cost.so_far = rate_per_s × (clock.now − run.start)` | 18 个同步点 × 2 个 run | 0 |
| `ctx_total_length/mean = ctx_prompt_length/mean + ctx_response_length/mean` | 全部步 | 相对 5×10⁻⁶ 以内 |
| `perf/total_num_tokens = 1568 × 16 × ctx_total_length/mean` | 全部步 | 1～3% |
| `critic/rewards/mean == critic/score/mean` | 全部步 | 精确 |
| `全局 KL = Σ_k (partial/k/frac × partial/k/train_infer_diff/new_infer/kl)` | pro 17 步 / flash 24 步 | 0.15% 以内 |
| `partial/avg_staleness = Σ_i i × partial/i/frac` | pro 17 步 / flash 24 步 | 4×10⁻⁶ 以内 |

`ctx_total_length` 那条的 5×10⁻⁶ 不是真的误差，是**取值粒度**：站点只给大约 6 位有效数字，
12 万的数粒度就是 0.5，三个数各自的舍入加起来能到一个 token。
绝对差最大见过 0.54 个 token，相对就是百万分之五。

`perf/total_num_tokens` 那条里的 1568 是 `prompts_per_step`，16 是每条 prompt 采样的序列数
（首页显示成 `1,568 × 16 seqs`）。这个乘积只能近似对上，因为有些序列会被判为无效。

这几条都写进了 `src/check.ts`，跑一下就能复验：

```bash
bun src/check.ts
```

它同时也能当"站点有没有偷偷改算法"的哨兵——哪天某条不再成立，它会报出来。

## 8. 坑

### 第 1 坑：首页那条 KL 曲线涨了 3 倍，但模型其实没怎么变

`train_infer_diff/new_infer/kl` 在观察期内从 0.0022 涨到 0.0101。看着像训练推理分歧在恶化。
但把这个数按 `partial/` 的桶拆开就发现不是这么回事。

| | pro 第 1 步 | pro 第 17 步 | flash 第 1 步 | flash 第 24 步 |
| --- | --- | --- | --- | --- |
| 全局 KL | 0.00219 | 0.00442 | 0.00287 | **0.01011** |
| 桶 0（最新鲜数据）的 KL | 0.00219 | 0.00264 | 0.00287 | **0.00341** |
| 桶 0 的占比 | 1.000 | 0.882 | 1.000 | **0.161** |
| `partial/avg_staleness` | 0.000 | 0.209 | 0.000 | **2.183** |

两条曲线在整个观察期内的取值范围：

- pro：全局 KL 0.00219～0.00980，桶 0 的 KL 只有 0.00217～0.00264。
- flash：全局 KL 0.00287～0.01011，桶 0 的 KL 只有 0.00254～0.00351。

全局值和 `partial/avg_staleness`（平均过期代数）的相关系数是 **+0.944**（两个 run 都是）；
和桶 0 的相关系数只有 +0.331（pro）／+0.151（flash）。

也就是说，全局 KL 的涨跌几乎全部来自"训练数据里旧数据占比"这个加权效应。
flash 第 24 步最典型：全局 0.0101，但那是只有 16% 的权重来自新鲜数据的结果；
新鲜数据自己的 KL 是 0.0034，只比第一步高了 19%。

最硬的证据是一个天然实验：pro 第 15 步因为重启，这一步用的是 100% 新鲜数据，
它的全局 KL（0.00258）**正好等于**桶 0 的值（0.00258），一位不差。

**怎么用**：要判断训推分歧有没有真的恶化，看 `partial/0/train_infer_diff/new_infer/kl`，
不要看首页那个全局值。要看"数据有多旧"，看 `partial/avg_staleness`。这两个数是两件事，
首页把它们乘在一起显示了。

### 第 2 坑：`timing_s/step` 和卡片上的"本步已用时"不含重启等待

用事件流里的时间戳逐条核对：没有重启的步，`timing_s/step` 和真实墙钟差在 ±14 秒以内；
有重启的步，差好几个小时。

- pro：15 步里被排除掉的重启等待合计 **16.8 小时**，占真实墙钟 52.6 小时的 32%，
  按 $5.71/秒算是 **$344,411**。
- flash：排除掉 7.6 小时，约 $78,422。

**怎么用**：拿 `timing_s/step` 算"每步成本""每步吞吐"得到的都是下界。
真实墙钟要用 `events` 里相邻两个 step 事件的时间差。

### 第 3 坑：重跑过的步，`/status` 和 `/series` 会对不上

站点对"重跑"的处理是两套：

- `/status` 的 `events` 只追加：原来那次 step 16 的事件留着，后面再补一条 `redo: true` 的事件。
- `/series` 的数组会被重写：`dynsam/avg@n` 在 step 16 上的值被换成重跑后的值。

实测 flash 的 step 16、17：

| step | events 里第一条 | events 里 redo 那条 | series 里的值 |
| --- | --- | --- | --- |
| 16 | 0.602504 | 0.594958 (`redo: true`) | **0.594958** |
| 17 | 0.585664 | 0.601257 (`redo: true`) | **0.601257** |

所以在 `events` 上直接画一条"主指标随时间变化"的曲线，和用 `dynsam/avg@n` 画出来的曲线，
在重跑过的步上会不一样。**取数的时候要么只认 `series`，要么只认 `events` 里每条步号的最后一条**，
不要混。

另外这也说明"序列只增不改"这句话有个例外：默认不改，但重跑会改。
本仓库的同步脚本对这种情况做了专门处理：发现某一步出现两条事件，就重新抓序列并允许覆盖那一步的值。

### 第 4 坑：有数据的指标比列出来的指标少

`/tags` 说 pro 有 2019 个指标，`/series` 只返回 1926 条序列。
差的那 93 个是这个 run 从头到尾都没产生过值的。按 `/tags` 遍历去取数据会拿到一堆空数组。

### 第 5 坑：`penalty/` 那一大段不要硬解读

`penalty/` 底下有 535 个指标，占了四分之一还多，但官方一条说明都没有。
这一块是站点自研的奖励惩罚管线，从命名上看大概和"哪一步该给多少功劳"有关，
但没有公开文档，网上也找不到对应实现。

能确认的一件事：`penalty/action/adv_reduction_total` 恒等于 0，而且
`train/adv_*_sum_pre_penalty` 和 `train/adv_*_sum_post_penalty` 逐值完全相同。
也就是说这条惩罚管线**在测量，但没有真的改写优势值**。这是从数据里能读出来的事实，
至于为什么，不知道。

### 第 6 坑：`actor/pg_clipfrac` 和 `actor/ppo_kl` 全是 0

所有 run、所有步、所有细分（`actor/agentic/pg_clipfrac` 等）都是精确的 0。
不可能是巧合，但原因不明——可能是这两个指标在当前配置下没有被写日志。
**不要**把它解读成"训练完全没被裁剪"。

### 第 7 坑：几个"看起来能直接除"的比值其实不能除

- `dynsam/num_measurable` 和 `dynsam/agg_turn/mean` 的分母口径不一样，相除没有意义。
- `train/harness/*/training/rollouts` 全加起来约 2.24 万，而 `totals.trained_step` 是 25,088。
  两个数来自不同的记账口径，对不上是正常的。
- `partial/i/n_tokens` 全部加起来大约是 `perf/total_num_tokens` 的一半，原因不明。

### 第 8 坑：`env/total_setup` 和 `env/total_error` 是进程内累计值

它们不是"这一步"的量，而是"当前训练器进程启动以来"的累计。重启会清零，
所以这两个指标会出现看起来莫名其妙的锯齿。判断某一步的真实情况要用相邻两步的差。

**但别拿这两个数的差值当"环境错误率"**：早先我们这样算过，得到千分之一以下；
而 MiMo-V2-Flash 官方 README 给的运行环境是「1 万+ 并发 pod、约 70% 的环境建立成功率」，
差三个数量级。所以 `total_setup` 不是"环境建立尝试数"、`total_error` 也不是"建立失败数"，
这个比值没有可解释的分母。官方口径见 `content/sources.json` 的 `mimo-v2-flash-readme-env`。

### 第 9 坑：`cost` 曲线没有任何信息量

既然 `cost.so_far = rate × (now − start)` 且 `start` 恒定，这条线就是一条绝对的直线。
拿它推导任何训练相关的结论都是错的。

## 9. 本地遥测多出来的东西

原站只能看"现在"。本仓库的遥测在这个基础上加了回放：给任何 `api/*` 请求挂一个
`asof=<epoch 秒>` 参数，服务端就把数据切成"那一刻为止"的样子返回。

**它的依据是第 3 条坑之外的那条规律**：某一步的数值只在那个步完成时才出现，
出现之后就不再变（重跑除外，重跑会在事件流里留下痕迹，同步脚本会跟进覆盖）。

回放模式下：

- `steps` 只包含完成时间早于 `asof` 的步，`series` 数组按此截断。
- `clock.now` 返回 `asof` 本身，所以页面上的时钟、成本、"已用时"全部冻结在那个时刻。
- `notices` 只返回发布时间早于 `asof` 的。
- `benchmarks` 只返回对应训练步已完成的点。
- `/live` 返回不晚于 `asof` 的最后一次采样器快照（60 条滚动明细没有留档，所以 `entries` 为空）。

原站没有这个能力，所以这是遥测的增量部分。具体实现见 `docs/02-本地遥测与同步机制.md`。
