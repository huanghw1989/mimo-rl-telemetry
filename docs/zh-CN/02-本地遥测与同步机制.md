# 本地遥测与同步机制

这份文档讲的是本仓库怎么把 `https://mimo.xiaomi.com/rl/` 搬到本地、
怎么增量更新、数据存在哪、回放是怎么做出来的。

数据本身每个字段是什么意思，看 `01-网站数据文档.md`。这份只管工程实现。

## 2. 一次同步做了什么

```
bun src/sync.ts
```

1. 抓 `/runs`、`/notices`、`/benchmarks`（共约 6 KB）。
2. 对每个 run：
   - 抓 `/status`（约 3 KB），判断要不要抓序列（见第 3 节）。
   - 需要的话抓 `/tags` 和 `/series`（约 500 KB，23 批）。
3. 把结果并进 `data/store/`：
   - `notices` 按 `id` 去重合并。
   - `benchmarks` 按 `(key, run, step)` 合并，只增不改。
   - `events` 按 `(kind, step, t)` 去重合并。
   - `tags` 登记新出现的指标名，更新时间戳。
   - `series` 补齐新格子。已有非空值默认不动；只有那一步被重跑过才允许覆盖。
4. 追加一条同步记录到 `syncs.jsonl`，这是回放功能的时间轴来源。
5. 增量更新 SQLite 索引。
6. 比对原站前端资源的哈希，有变化就提示。
7. 给新增 / 原文改过的公告补中文译文（第 7.3 节，`--no-translate` 可跳过）。

第一次用（或者要重建历史）跑：

```
bun src/sync.ts --bootstrap
```

它会把 `data/seed/` 下那 15 份早期快照按时间顺序灌进仓库，
然后再做一次在线同步。灌完之后仓库里就有从 run 第一天到现在的完整历史，
回放能一直翻到 2026-09-15 第一步。

常用开关：

| 开关 | 作用 |
| --- | --- |
| `--bootstrap` | 先导入历史快照 |
| `--force` | 跳过"没有新数据"的判断，强制重抓全部序列 |
| `--reindex` | 只重建 SQLite 索引，不联网 |
| `--no-assets` | 不比对原站前端资源 |
| `--no-translate` | 不给新增公告补中文译文 |

## 3. 差量是怎么做的

`/series` 不认任何区间参数（试过 `from`、`since`、`start`、`step_from`、`offset`，全被忽略），
每次都是全量返回。所以省不下来的是"发出去的那个请求"，能省的是"要不要发"。

### 第一层：要不要发这个请求

抓完 `/status` 之后判断：

- 仓库里那个 run 的最高步号和 `status.step.last` 一致，**并且**
- 没有"我们还没见过的新重跑步"，**并且**
- 连续跳过的次数没到 12 次

三条都满足就跳过 `/tags` + `/series`。实测两个 run 都跳过时，一次同步的流量
从约 1 MB 降到约 40 KB。

那 12 次的强制全量是兜底：万一站点有我们没预料到的补写，最多漏 12 个同步周期
（按 20 分钟一次算就是 4 小时）就会被纠正。

**这里有个反直觉的点**：判断条件不能用"事件条数等于步数"。重跑会让事件条数比步数多
（flash 有 24 步但 26 条 step 事件），用条数判断会永远认为数据变了，每次都全量重抓。
正确的判断要么用 `status.step.last` 比步号，要么对重跑单独处理。
这个 bug 我在实现过程中真的踩到了，日志里能看到当时的输出。

### 第二层：写不写这份数据

`mergeSeries` 逐个指标逐个格子比对：

- 本地是 `null`、远端有值 → 填进去，计入"新增格子"。
- 本地有值、远端相同 → 什么都不做。
- 本地有值、远端不同 → 分两种情况：
  - 那一步在事件流里出现过两次（重跑）→ 按远端值覆盖，记一条日志。
  - 否则 → **保留本地值**，并打一条 `!!` 警告，提示"和站点对不上、且不是重跑导致的"。

我用 15 份历史快照验证过：在没有重跑的正常情况下，同一格的值从来不会变。
这条守卫至今没有触发过一次，说明数据是干净的；留着它是因为一旦触发就说明
我们对站点的理解和实际不一样，必须知道。

## 4. 存储格式选型和实测

同一份数据，三种存法的实测体积：

| 存法 | 体积 | 说明 |
| --- | --- | --- |
| 老采集脚本留下的 15 份原始快照 | **14,489 KB** | 每份都是全量，同一份数据存了 15 遍 |
| 本仓库的 JSON 列式（`data/store`） | **1,325 KB** | 去重之后的权威副本 |
| └ 其中 `series.json` 两个 run | 720 KB | 一个指标一行，方便 grep 和 diff |
| └ 其中 `tags.json` 两个 run | 509 KB | 指标名 + 生命周期，指标名本身就很长 |
| SQLite 索引（`data/telemetry.sqlite`） | **1,768 KB** | 派生，可重建 |

去重把 14.5 MB 压到 1.3 MB，约 11 倍。至于为什么最后还要有一个 SQLite：

**JSON 适合当仓库，不适合当查询接口。**

- 前端按 tag 取序列时，如果直接读 JSON，每次请求都要把整个 `series.json` 解析一遍。
  现在 720 KB 还能忍，指标上千、步数上百以后就是几十 MB 反复解析。
- 回放要按"某时刻之前完成的步"筛数据。JSON 里得先把全量读进内存再过滤；
  SQL 就是一句 `WHERE step <= ?`。
- bun 自带 `bun:sqlite`，不需要装任何依赖。

### SQLite 里数值为什么存 BLOB 而不是长表

先说结论：长表在这个数据形状下非常吃亏。

我第一版用的是最自然的三列长表 `series(run, tag, step, value)`，实测：

| 方案 | 体积 |
| --- | --- |
| `series` 三列长表 | 10.6 MB（外加 7.7 MB 未回收的 WAL） |
| `series(run, tag, n, v)`，`v` 是 Float64 二进制 | **1.7 MB（整库）** |

差 11 倍的原因是**指标名在长表里每一行都要存一遍**。实测指标名平均 45 字节，
7.5 万行就是 3.4 MB 纯粹重复的字符串，再加上 B 树的开销就变成了 10 倍。

改成列式之后的布局是：

```sql
CREATE TABLE series (
  run TEXT NOT NULL, tag TEXT NOT NULL,
  n INTEGER NOT NULL,      -- 已写入的格数
  v BLOB NOT NULL,         -- Float64 数组，下标 = step - 1
  PRIMARY KEY (run, tag)
) WITHOUT ROWID;
```

- 指标名一个指标只存一次。
- 数值以 8 字节一格定长排列，用下标直接定位，取某个指标就是一次主键查询加一次切片。
- 缺值用 `NaN` 表示。站点的数值来自 JSON，不可能是 `NaN`，所以不会和真值撞车。
- 3905 个指标的 blob 加起来 **612 KB**，也就是每格 8 字节、没有额外开销。

**什么时候该换更重的格式。** 现在两个 run 加起来 7.5 万格、1.7 MB。按目前约 3 小时一步的速度，
跑到 1000 步大约是 400 万格、32 MB，SQLite 完全撑得住。真正的拐点在两个方向上：

- 如果以后要存 rollout 级别的明细（每道题、每条轨迹），数据量是百万到亿级，
  那时候该上的是 Parquet 或者 DuckDB，按列压缩 + 谓词下推，而不是继续往 SQLite 里塞。
- 如果只是指标变多、步数变多，现在这套 blob 列式已经够用很久。

## 5. SQLite 表结构

```sql
meta(key, value)                 -- /runs 的配置，一个键一行，值是 JSON
runs(key, label, note, color_index, start, mode, rate, headline_tag, version)
tags(run, tag, first_seen, last_seen)          -- 指标名的生命周期
steps(run, step, t, wall, value, delta, tokens, redo)
series(run, tag, n, v)                          -- 上面说的 Float64 blob
notices(id, t, run, text)
benchmarks(bkey, title, note, format, run, step, value)
syncs(sid, captured, server_now, source)        -- 同步点，sid 与 syncs.jsonl 行号一致
timeline(sync_id, run, cost, step, phase, progress, gen_frac, ...)  -- 每个同步点的运行状态
live(sync_id, run, t, step, passrate, n, pr0, pr1, json, entries)  -- entries 是采样器滚动明细
assets(path, sha256, bytes, fetched)            -- 原站前端资源哈希
```

写入是增量的：`indexRun` 读每个指标现有的 blob，按 JSON 仓库里的数组补齐尾巴，
只有真的变了才写回。全量重建 0.1～0.2 秒，同步时的增量更新通常在 0.1 秒以内。

索引阶段整体包在一个事务里，因为服务端可能是另一个进程在只读查询，
逐表 DELETE + 重插会让它读到半成品。

## 6. 回放是怎么做出来的

核心是一条不变式：

> 某一步的数值，只在那个步完成时才出现在 `/series` 里；出现之后就不再变。

（例外是重跑，重跑会在事件流里留下两条同号事件，同步脚本据此跟进覆盖。）

于是"某时刻的看板"就等于**把每个指标数组截到那个时刻为止**。具体做法：

1. 时间轴上每个同步点有一个 `captured` 时间戳，记在 `syncs` 表里。
2. 请求带上 `asof=<epoch 秒>` 之后：
   - `steps` 只取 `COALESCE(t, wall) <= asof` 的行。优先用事件流里的时间戳，
     没有就退回序列时间轴里的 `wall`。两者差在分钟级，不影响回放。
   - `series` 按最大可见步号做 `WHERE step <= ?` 截断。
   - `notices` 取 `t <= asof` 的。
   - `benchmarks` 只保留对应训练步已完成的点。
   - `live` 取 `captured <= asof` 的**最后一条留档**（严格往回找，找不到就返回空，
     绝不拿"最新那条"兜底——那会把未来的采样器数据塞进过去的切面），
     并把那一刻之前的采样器滚动明细拼出来（见下一节）。
   - `timeline` 取 `captured <= asof` 的最后一行拿阶段、进度、重启次数。
   - `clock.now` 直接返回 `asof`，所以页面上的时钟、"已用时长"、成本全部冻结。
3. 成本是重算的：`rate × (asof − run.start)`。这会和当时快照里记下的
   `cost.so_far` 差几秒的量（因为快照里的 `clock.now` 比 `captured` 略晚一点），
   属于口径差异，不是错误。

> **`asof` 必须原样传，不能取整。** 同步点的 `captured` 是带小数的
> （例如 `1789871319.416`），早先前端用 `Math.round()` 把它转成整数再传：
> 小数部分小于 0.5 时结果比 `captured` 小，服务端的 `pickSync` 就落到**上一个**
> 同步点——表现是滑块停在最新一格，看到的却是前一格的数据。现在原样传。

### 采样器数据（dynamic sampler）怎么回放

采样器面板有两块数据，来源不同、回放方式也不同：

- **按数据源的那张表**：来自 `/live` 的 `latest.ds`。每次同步都会把 `latest` 整条留档到
  `runs/<run>/live.jsonl`，回放时按 `captured <= asof` 取最后一条，所以每个切面看到的是
  那一刻的配额、受理、判分和在途量。
- **滚动报告（feed）**：`/live` 的 `entries`（约 30 秒一条、窗口 60 条）。
  以前只留 `latest`，回放时 feed 里就只剩 step/restart 事件，采样器自己发的
  "accepted X/Y · judged … · pass …" 全丢了。现在同步时把 `entries` 一并留档：
  按上一条留档的 `log_time` 去重（窗口 30 分钟 > 同步间隔，不去重会存两遍），
  写进 `live.jsonl` 的 `entries` 字段，索引进 `live.entries` 列。
  回放时把 `asof` 之前各次留档的明细分并、按 `t` 去重，取最后 60 条。
- **老仓库没有 `entries`**（这个字段是后加的）：退回用每次同步的 `latest` 拼一份
  **同步粒度**的报告，并在面板上标「明细为同步粒度」——不会把 20 分钟一条
  冒充 30 秒一条。在线（`/api/live` 的 `entries_approx`）和离线（`bundleLiveEntries`）
  两条路径都带这个标记。

### 切面明细面板的渲染竞态

`enterReplay()` 是「先 `setExpanded(true)` 再 `goto(idx)`」，两次都会调 `renderSlice()`
并且并发地发请求；第一次调用时 `asof` 还是 null，会把**实时**数据渲染到
**第一个切面**的时间戳上，而且它可能后到、覆盖掉正确的那次渲染。表现是工具条写着
「第 29/29 个切面」，面板正文却是「第 1/29 个同步点」+ 实时数据。
修法是给 `renderSlice()` 一个守卫：异步返回后如果 `i !== state.index` 就直接丢弃。

### 前端怎么接上去

原站的 `js/app.js` 里所有请求都是写死的相对 URL（`api/status?run=pro` 这种）。
遥测层不去改这些调用，而是在 `js/telemetry.js` 里**换掉 `window.fetch`**：
只要路径匹配 `/api/` 就补上 `asof` 参数。这样原站代码一行都不用为了回放而改。

但有几件事光靠拦截做不到，所以在 `app.js` 里加了 6 处改动（都带 `[telemetry]` 注释，
共 9 个标记）：

1. **`isFinal()` 要认得回放。** 原站把 `mode === "ended"` 当"这个 run 结束了"，
   结束了就不再轮询、不画采样器面板。回放切片里 `mode` 保持原样，但如果照原逻辑处理，
   采样器面板会整个消失。加一层 `&& !M.replay()` 解决。
2. **`vnow()` 要冻结。** 原站算"现在"是 `服务器时钟 + 本地已经过了多久`，会一直往前走。
   回放时必须直接返回 `clock.now`，也就是切面时刻，否则页面上的相对时间会慢慢漂。
3. **状态词要能显示切面。** 原站显示 `in progress` / `completed`，回放时改成
   `replay · 2026-09-17 15:11Z`，免得被误读成"这一步正在跑"。
4. **要给遥测层一个刷新入口。** 原站的序列是按指标缓存的（`S.series`），
   换切面时缓存必须作废，否则图表还是老数据。所以 `app.js` 通过 `Telemetry.bind()`
   交出一个 `refresh()`，里面清缓存、重取状态、重画。
5. **评测榜卡片带上 `data-bench`。** 图表联动点中评测榜时要能认出点的是哪个榜。
6. **采样器明细的粒度提示。** 回放时如果明细只有同步粒度，在 feed 卡片的时间旁
   补一句「明细为同步粒度」。

另外 `index.html` 只加了两行：一行引入 `telemetry.css`，一行在 `app.js` **之前**
引入 `telemetry.js`（必须先装好 fetch 拦截，不然第一次请求就漏了 `asof`）。

导航上那个"回放"按钮是开关：`enterReplay()` / `exitReplay()` 互为反向，
`state.on` 记着现在开着没有（以工具条显不显示为准，不拿 `asof` 反推——刚点开、
时间轴还没读完的那一瞬间 `asof` 还是 null）。所以再点一次就直接回到实时，
不用绕到工具条上去按"回到实时"。

遥测层和原站代码的接口总共就两个：`Telemetry.replay()` 和 `Telemetry.bind()`。

### 回放界面为什么是整屏的

回放面板有两种状态，切换按钮在工具条最右边：

- **整屏**（默认）：`.telemetry-bar` 变成 `position: fixed; top: var(--nav-h); bottom: 0`，
  里面是一列 flex——42px 的工具条固定，明细区 `flex: 1` 加上 `overflow: auto` 吃掉剩下的高度。
  导航本身不动，所以切面控件和"回到实时"始终够得着。
- **收起**：退回一条贴在导航下面的 42px 工具条，明细整块 `display: none`，
  下面的原看板就露出来按这个切面渲染。

一开始是做成半个页面高的面板嵌在工具条里的，实际用起来很别扭：明细有二十多步的表格、
公告和评测三块内容，塞进 52vh 里只能不停内部滚动，屏幕下半截还留着原看板占位。
改成整屏之后，一个切面的全部信息一屏能看完，原看板退到一个按钮后面。

写这个布局时踩了一个 flex 的坑：`.telemetry-bar.expanded` 是 column 方向的 flex 容器，
而 `.wrap` 自带 `margin: 0 auto`，**auto 外边距会覆盖 `align-items: stretch`**，
于是工具条缩成了内容宽度、居中悬在中间。给 `.telemetry-bar > .wrap` 显式加 `width: 100%` 才解决。

### 离线副本

`bun src/export.ts` 会把仓库里的数据压成一个
`window.__TELEMETRY_BUNDLE__` 写进 `site/data/bundle.js`（约 2 MB，其中约 0.3 MB 是
采样器滚动明细——回放 feed 要用），再生成一个 `site/offline.html`。

有 bundle 的时候，`telemetry.js` 的 fetch 拦截直接就地切片返回，一个网络请求都不发。
所以双击 `offline.html` 就能打开，不需要起服务、不需要联网，回放照样能用。

代价是它是导出那一刻的快照，不会自己更新，数据变了要重新导出。

### 两条路径的一致性

同一份数据有两条取数路径：在线走 SQLite，离线走 bundle。两边各有一套 asof 切片逻辑，
实现重复是有风险的——所以我把它们逐字段对过，确认可以互换。

做法是打开 `offline.html`（它和 `/api/*` 同源），用 `XMLHttpRequest` 绕过 `telemetry.js`
的 fetch 拦截去打真实服务端，再和 `Telemetry.api()` 拿到的 bundle 结果比：

```js
const a = await xhr('/api/status?run=pro&asof=1789648245');   // 服务端
Telemetry.setAsof(1789648245);
const b = await Telemetry.api('api/status?run=pro&asof=1789648245'); // 离线包
// 对象键排序后 stringify 再比，避免键顺序造成假差异
```

在 4 个切面（最早的、中间的、倒数第二个、最新的）× 7 类接口上共 45 项比对，
除了 `offline` 这个刻意不同的标记位，其余全部一致。

这个比对查出过三个真 bug，都不是靠"看着对"能发现的：

1. **服务端的 `totals` 用了最新的值。** 回放时 `/api/status` 里的 `tokens_cum` 应该是那个
   时刻的数字，但当时兜底读的是最新 `status.json`。原因很隐蔽：给回放用的
   `getTimelineAll` 那句 SELECT 没有把 `totals` 列出来，`tl.totals` 就是 undefined，
   于是静默退回最新值。现在改成专门的 `getTimelineAt()` 直接取整行。
2. **benchmarks 顺序变了。** 表主键是 `(bkey, run, step)`，`WITHOUT ROWID` 的表按主键排序，
   查出来就成了字母序 `automation / deepswe / inhouse-coding`，而原站是
   `deepswe / inhouse-coding / automation`。加了 `ord` 列记住原始顺序。
3. **离线包的步列表有重复。** `export.ts` 当时拿事件流的行数去推步列表，
   而重跑过的步在事件流里有两行，于是那一步在明细表里出现了两次、步数也虚高。
   改成以 `axis.steps` 为准。

还有一个同类问题是在离线包里：`/api/tags` 没有按 `asof` 过滤，
回放时会列出那一刻还不存在的指标名。现在导出时带上了 `tagFirstSeen` 数组。

## 7. 服务端

```
bun src/server.ts --port 8787
```

**实时模式（URL 不带 `asof`）**

| 接口 | 数据来源 |
| --- | --- |
| `/api/runs`、`/api/status`、`/api/live`、`/api/notices`、`/api/benchmarks` | 转发原站（合计约 25 KB） |
| `/api/tags`、`/api/series` | 本地 SQLite（约 500 KB） |
| `/api/content` | 本地 `content/` 下两个 JSON |

`/api/content` 是原站没有的，返回 `{metrics, insights, ...}`，给文档面板用。
它**忽略 `asof`**——解读和洞察是文档不是数据，按时间切面对它没有意义。
每次请求现读文件，所以改完 `content/` 不需要重启服务。

任何转发失败（断网、原站挂了、超时 6 秒）都会自动退回用仓库里的数据重建，页面不会白屏。
加 `--offline` 可以完全关掉转发，全部走本地。

**回放模式（带 `asof=`）** 全部走本地，不联网。

## 7.1 指标解读与洞察是怎么接进页面的

这套内容有三个入口，都做在遥测层里，原站代码只多挂了两个按钮：

1. **导航上的"解读"按钮** → 打开整屏文档面板，左边按分组筛选，右边是卡片。
   面板是独立于 app.js 路由的浮层，这样就不用改原站的路由表，离线副本也能用。
2. **任意图表的详情框** → 用 `MutationObserver` 盯着 `#modal` 的 class 变化，
   一打开就把这个指标的解读追加进去。原站的 `openChart(tag)` 会把指标名写进
   `#modal-title`，遥测层读它做查表，所以**一行原站代码都不用改**。
   详情框里只放最相关的几段（它量什么、为什么盯它、这一轮实测），
   细读的部分折在 `<details>` 里。

   详情框的版式踩过一个坑：`.modal-card` 是 `max-height:100%` 的纵向 flex，
   解读块一进去就会**按比例压缩所有子项**，`.modal-chart` 从 420px 被挤到 44px，
   而 `.chart-plot` 的 `min-height:60px` 让 canvas 反而溢出容器，坐标轴和曲线叠成一团
   （展开"怎么读"之后更明显）。修法是遥测层用 `modalSplit()` 把统计和图表收进左栏、
   解读单独占右栏并自己滚动：只挪 DOM 位置，图表和统计仍按 id 查找，app.js 依旧不用改。
   左栏 `flex:1 1 auto` 撑满、右栏 `flex:0 0 400px` + `overflow-y:auto`，
   展开解读只影响右栏的高度，图表列一格都不动。
3. **卡片之间互相跳转** → 每条解读底下列出相关指标，点一下跳到那一条；
   洞察卡片底下列出它涉及的指标，同样可点。
4. **第三个页签"溯源总览"** → 反过来按材料看：每条论文/博客/官方文档/自有核算是一张卡，
   列出它被哪些条目引用、各是什么立场。侧栏给出交叉验证的总账
   （登记 N 条、被引用 M 条、多少处标为「存疑 · 边界」），以及一块**检索空白**：
   没找到能验证对应读法的公开材料。空白也是一种结论 —— 单列出来，读者才不会
   默认每条解读都有文献背书。
5. **看板表格的列头** → dynamic sampler 的 data sources 表和 batch composition 的两张表
   由 app.js 渲染。遥测层不改它，而是用**事件委托**接住列头上的点击，按"表的种类 +
   列头文字"映射到 `table/...` 这批条目（分组「采样器表格」），再走同一个 `openDoc`。
   表格每 10 秒轮询就整块重建，所以不能直接给 `th` 绑监听；`title` 也是鼠标扫过时
   惰性补的。`table/` 开头的条目没有对应曲线，卡片里不画"看这条曲线"按钮。
   这批条目的口径考证过程见 `docs/zh-CN/03-采样器表格字段口径考证.md`。

查表有个细节：有些解读是按"族"写的一份覆盖一族指标，比如新鲜度桶的
`partial/<k>/frac` 一份讲完 pro 的 0~7 和 flash 的 0~9。所以精确匹配不到时会把
tag 逐级泛化再找一次：纯数字段换成 `<k>`，`dynsam/<类目>/dataset-<id>/...`
里的类目和数据集段换成占位。这样点 `partial/3/frac` 也能看到那段解读。

**面板的位置写在地址栏里**，刷新或把链接发给别人就能直达同一栏、同一条：

```
#doc/metrics                                 指标解读，全部
#doc/insights                                数据洞察
#doc/metrics/group:奖励信号                   只看"奖励信号"这个分组
#doc/sources/srckind:paper/@adamw            只看论文，并定位到 adamw 这条材料
#doc/metrics/@critic%2Frewards%2Fmean         定位到 critic/rewards/mean 这条解读
```

格式是 `#doc/<页签>[/<筛选名>:<值>][/@<条目 id>]`，值一律 `encodeURIComponent`
（指标 id 里的 `/` 会变成 `%2F`）。触发点全覆盖：点"解读"按钮、切页签、点左栏筛选、
从详情框点"看完整解读"、点卡片标题，都会改写地址；**滚动列表时也会**——滚完停 150 ms，
把当前压在列表顶部的那条写进去，所以随手滚到某处，复制地址栏就是那一条的链接。
滚动监听只改地址不重画（`replaceState`），滚一路也不会堆历史记录。

为什么不用 `location.hash = ...`：那会触发 app.js 的 `hashchange` 路由，而 `#doc` 不是它的
路由表里的视图，会被当成未知视图回落到 overview 重画一遍。面板是浮在整屏上的，
下面那张图重画纯属白费，还可能在切分组时闪一下。所以这里"改地址但不触发路由"，
只在首次带 `#doc/...` 进页面时（刷新、外链）由 `routeDocHash()` 打开面板；
关掉面板会把地址换回打开前的那个视图，免得刷新一下又自己弹出来。
`file://` 下 Chrome 只允许纯 fragment 的 `replaceState`（带路径的会被拒），
这里传的正是 `#doc/...`，所以离线副本的深链一样能用；真被拒就退回改 hash，路由函数是幂等的。

离线副本里这部分照样能用：`export.ts` 会把 `content/` 的内容一起打进
`bundle.js`，`telemetry.js` 的 `bundleApi` 里加了 `/content` 分支就地返回。
（这个分支原先漏了 `sources` / `sources_note` / `sources_gaps` 三个字段，
所以 `offline.html` 里"溯源总览"是空的，已经补上。）

### 内容怎么维护

解读不写成散落在 HTML 里的字符串，而是结构化 JSON。每条有固定字段
（`what` / `how` / `why` / `read` / `observed` / `traps` / `related`，可选 `table`），
这样渲染逻辑只有一份，改版式不用动内容。分组的草稿放在 `content/_draft/`，
一组一个文件（并发写不同文件不会互相覆盖），合并：

```
bun run mimo:content          # 校验 + 合并成 content/metrics.json
bun run mimo:content --check  # 只校验不写
```

合并时会做三件事：

- 校验每条都有全部必需字段、`read` 在 3~6 条之间、`traps` 不超过 4 条
- 按 id 去重（两组都写了同一个指标时保留字段更全的那条，并报出来）
- 把 `dynsam/<类目>/dataset-<id>/num_accepted/{step,held,carryover}` 这一族
  收成 3 条：25 个数据集逐个写会得到 25 条内容雷同的卡片，改成"概念讲一次 +
  一张各数据源对照表"，数字一个不少。表里的数字是合并时从 store 现算的。

`insights.json` 是手写的，不受合并流程管，但也会被校验一次。
特意挡的是这个坑：**JSON 里把中文引号写成半角引号会把字符串提前截断**，
报错位置很难一眼看出来，所以给它一句明确的提示。

### 溯源依据

每条解读可以带一组「溯源依据」，说明这条读法的出处：公开论文、工程博客、官方文档，
或者我们自己从数据里算出来的结论。页面上是一个「溯源依据 · N 条」的圆角按钮，
点开才展开完整说明（题目、作者、年份、**逐字原文引用**、以及它具体佐证/推翻了哪一句）。

结构上做了一个刻意的切分：

```
content/sources.json     登记表：题目、作者、链接、逐字引用。**所有 URL 只存在这里**
content/_draft/*.json    条目里只写 ref：{"ref":"grpo","stance":"support","note":"…"}
content/_research/*.json 调研子智能体的原始产出，apply_sources.ts 消费它
```

这样切有三个好处：URL 的准确性只取决于登记表（人工核验过），子智能体**没有机会编造链接**；
一个来源被多处引用时改一次就够；引用错的 ref 会在构建时直接失败，页面上不会出现
点不开或对不上的来源。`stance` 只有三种：`support`（支持我们的读法）、
`challenge`（冲突或给出边界条件）、`context`（背景）。`challenge` 是最有价值的一类，
它记录的是"这条读法在什么条件下不成立"。

流程：

```
# 1. 调研子智能体写 content/_research/*.json（只允许写 ref，逐字原文必须来自亲自抓取的页面）
# 2. 落到条目上（族 id 会写到该族所有数据集条目上，构建时按 ref 取并集）
bun run mimo:apply-sources
# 3. 合并成登记表
bun run mimo:registry
# 4. 核验：arXiv 按 id 比对真实标题（70 条），网页检查引文是否逐字存在
bun run mimo:verify-sources
# 5. 展开成完整来源并校验
bun run mimo:content
```

核验脚本值得单说，因为**凭记忆写 arXiv id 出错的概率很高，而错了以后链接照样打得开、
只是指向另一篇论文，肉眼几乎不可能发现**。这一轮调研里，我们自己的简报就写错了 5 个 id
（`2002.11803`、`2506.17863`、`2506.10947`、`2508.10695`、`2509.23798`），全都是靠这个脚本
和子智能体的逐篇核对抓出来的。`verify_sources.ts` 的做法是：按 id 问官方 API 拿真实标题，
和登记表里的标题做词集比对；真标题被登记表标题完全包含时（标题里带「附录 B」这类说明后缀）
也算通过。网页条目则抓正文检查引文是否逐字出现 —— 这一条对前端渲染的页面无效
（Notion 那两个页面就是这么漏出来的），只能另外用真实浏览器渲染后核验，结论记在脚本的
`RENDERED` 白名单里。

构建时还会自动补两类来源，保证每张卡片都有溯源可点：

- **官方口径**：原站 `meta.json` 的 `descriptions` 里有的指标（22 个固定指标），
  以官方英文原文作为 `quote`，标注"如果和它冲突以官方为准"；
- **本站数据**：既没有文献也没有官方说明时，明说"这一轮溯源没有检索到直接对应的
  公开文献"，并给出该指标的曲线链接，让读者自己核对。

解析在 `sources.ts` 里，服务端和离线导出共用同一个函数；它对**已展开的条目是幂等的**，
所以 `metrics.json`（构建产物）被再解析一次也不会重复插入来源。


**遥测自己加的接口**（原站没有）：

| 接口 | 用途 |
| --- | --- |
| `/api/telemetry/timeline` | 回放滑杆的时间轴：同步点 + 每个同步点的状态 |
| `/api/telemetry/summary?asof=` | 某个切面的横向摘要，回放面板用 |
| `/api/telemetry/store` | 仓库规模统计 |

`/api/tags` 有个刻意的偏离：它会**回显请求里带来的 `v`**。原站返回的是自己的版本号，
但前端拿 `v` 当缓存键，如果实时的 `/status` 版本比仓库新，两边对不上会导致序列缓存
被反复作废。回显可以避免这个问题。

## 7.2 图表联动是怎么做的

功能本身（勾选"联动"，点任意图表上的一步，所有图跳到同一步）写在 README 里，
这里只说实现，以及为什么这么做。

**需求长什么样。** 原站的每张图各管各的：`pointermove` / `pointerdown` 触发自己的
`_hover`，把竖线、取值点和读数框画在自己这张 canvas 上，`pointerleave` 再收掉。
要"点一下就全部跟上"，就得同时够到这些互相独立的图表对象，而 `app.js` 把实例存在
自己的闭包私有状态里（`S.cards`、`S.telemetry`），外面拿不到。

**三条路，选了第三条。**

1. 在 `app.js` 里多开一个 `[telemetry]` 出口，把 `S.cards` 交出来。可行，但每加一个功能
   就要动一次原站文件，而且 `S.cards` 只覆盖卡片图，benchmarks、批组成、详情框
   各是各的容器，交出来也得再挑一遍。
2. 从 DOM 反推实例：给 canvas 挂数据属性、再靠事件冒泡维护一个映射。能不动原站，
   但图表实例上没有任何标记，映射本身就得靠额外改动来建立。
3. **包一层构造函数。** `charts.js` 在 `telemetry.js` **之前**加载（`index.html` 的顺序是
   `format.js → charts.js → telemetry.js → app.js`），所以 `telemetry.js` 执行时
   `window.Charts` 已经在了。把 `Charts.Line` / `Charts.Stacked` 各包一层：

   ```js
   var Wrapped = function (container, opts) {
     var inst = new Orig(container, opts);
     registerChart(inst);
     return inst;            // 构造函数返回对象，new 出来的就是原实例
   };
   Wrapped.prototype = Orig.prototype;
   ```

   构造函数返回对象会覆盖 `this`，所以 `app.js` 里的 `new Charts.Line(...)` 拿到的
   还是原实例，`instanceof`、`destroy()`、`setData()` 一切照旧，而遥测层在
   `registerChart` 里拿到了每一个实例。原站两个文件都不用改。

**拿到实例之后做三件事：**

- **点。** canvas 上挂 `click`：`_hover(e)` 先按原站逻辑算出最接近的 x，`Line` 用
  `prepared.series[].xs` 反查回步号，`Stacked` 直接用 `hoverI` 取 `data.steps`。
  步号是全局状态，不是 x——回放的 time 轴下两个 run 的 x 不同，只有步号能对齐。
- **画。** 直接复用原站的绘制：`Line` 设 `hoverX` 再 `draw()` + `_tooltip(x)`；
  `Stacked` 合成一个 `clientX` 落在那根柱子上的假事件喂给 `_hover()`。
  所以联动标注和"鼠标悬停"长得一模一样，没有第二套画法要维护。
- **收。** `pointerleave` 的处理器是原站注册的，换不掉，也不好抢；所以再注册一个
  `pointerleave`，跑在原站那个后面，把联动那一步补回去。两个处理器在同一个事件派发里
  同步跑完，浏览器只重绘一次，看不出跳动。

**数值列。** 卡片右上角那列原本是最新值，联动时改成"那一步的值"，靠改写
`card-head .val` 的 `innerHTML` 实现，改之前先把原样存下来，取消时还原。
chart-card 与 benchmarks 两种卡片的值列版式不同（benchmark 多一个 run 名），
所以按"原样里有没有 `span.dim`"决定要不要补 run 名，而不是写死一份模板。

**几个刻意的选择：**

- 联动关着的时候，这些处理器第一句就 `return`，页面行为与原站逐帧一致；
  勾选状态存 localStorage，锁在哪一步不存——刷新回到实时。
- 某张图没有那一步（指标缺值、benchmark 的散点是稀疏的、那个 run 还没走到），
  竖线就不画，并且**把它自己上一轮的标注清掉**。这里踩过一次：只 `return` 不清理，
  会出现别的图已经跳到第 26 步、还有几张留在第 24 步的情况。
  数值列则退到最近的一步并标出实际步号（`@s19`），因为"这个 run 当时是多少"仍然有意义，
  但步号必须标出来，否则会被当成那一步的数字。
- 控件挂在图表工具条的最右边，和 `step/time`、`linear/log`、`smoothing` 放一起。
  一开始放在导航右侧，实测在 900 px 宽的窗口里把页头撑出了横向滚动条
  （原站那排"总成本 + 四个城市时钟"本来就快满了），挪进工具条后任何宽度都不增宽。

**代价说清楚：** 这一层依赖原站几个内部成员的写法——`_hover`、`_tooltip`、
`hoverX`、`hoverI`、`prepared`。`sync.ts` 每次同步都会比对原站前端资源的哈希，
改版会打印出来；真改了这几个名字，联动会失效（其余功能不受影响），
到时候对着 `data/upstream/` 里的新版本改 `telemetry.js` 即可。

## 7.3 公告面板是怎么做的

原站的 notices 是一份只增不减的英文清单，遥测层把它换成了自己的一块（中文译文、滚动列表、
标出每条公告发布时的训练步、每个 run 一根定位滑杆）。这里只说实现和取舍。

**先说结论：这块面板不碰 app.js，但也不复用它的渲染。** 原站的 `#notices` 照常渲染，
只是被遥测层加一个类藏起来（`#notices.mn-src-hidden { display: none }`），
面板自己插在它后面、自己取数、自己渲染。理由是需求已经超出了"在原文上加一层"：
翻译、滚动、步号、滑杆都要自己的结构，把 app.js 拼好的 DOM 反解成数据再重排，
比重新渲染一遍更脆。

**那怎么知道"公告变了"？** 用 `MutationObserver` 盯 `#notices` 的 `childList`。
app.js 在三种情况下会重画它：公告列表变了、整个 overview 重画（换视图 / 切回放切面 /
数据版本变化）、以及视图重建后 app.js 自己调一次。遥测层不需要区分这几种，
统一按 120 ms 防抖重新取数即可。`#notices` 被整块重建时（`renderOverview` 里
`root.innerHTML = ...`），观察器会连着节点一起失效，所以 `ensureNoticesPanel()`
每次都比一遍节点身份：换了就重新挂观察器、重新取数；面板本身被删了就重建。

这里有个容易写成死循环的地方：面板自己渲染也会触发 `#main` 上那个观察器
（它同时还负责补图表工具条）。所以取数只由 `#notices` 的观察器触发，
`#main` 的观察器只做"节点还在不在"的幂等检查，两边不互相点火。

**数据从哪来。** 面板自己请求三个接口，而不是去读 app.js 的私有状态：

| 要什么 | 从哪来 |
| --- | --- |
| 公告正文与时间戳 | `/api/notices`（回放时服务端按 `asof` 截断） |
| run 列表与配色 | `/api/runs`（取一次缓存住） |
| 每一步的完成时刻 | `/api/status?run=<key>` 里的 `events`（只取 `kind === "step"`） |
| 中文译文 | `/api/content` 的 `notices_zh`（和指标解读同一条通路） |

**步号是怎么算出来的。** 每个 step 取最后一次完成时刻——重跑会让同一个步号出现两次，
后一次才是最终生效的（flash 有 24 步但 26 条 step 事件，这个坑第 3 节已经踩过一次）。
然后对一条公告：

```
已完成步号 = max{ step | 该步完成时刻 ≤ 公告时间 }
```

取"最大步号"而不是"最近一次完成"，是因为重跑会让"最近完成的"回退到一个更小的步号，
而读者想知道的是"当时练到哪了"。回放切面里 `/api/status` 已经按 `asof` 截断，
所以这里不用再判一次。

**定位滑杆走的是下标，不是步号。** 本地记录到的第一步不是第 1 步（早于第一份快照的
步号没有完成时刻），滑杆如果按 `1..max` 铺，前面一截拖出来什么都不会发生。
所以滑杆的取值范围是"记录到的步"数组的下标，值域和步号解耦，每一位都有对应结果。
滚动用 `getBoundingClientRect()` 的差值算，不能用 `offsetTop`：`offsetTop` 的参照物是
最近的定位祖先，和滚动容器不一定是同一个（这里踩过一次，滚动量永远算错）。

**译文为什么要存英文原文。** `content/notices.zh.json` 每条是 `{en, zh}`：
`en` 是写译文那一刻的英文原文。原站如果改写了某条公告，译文不会自动跟着变，
这时页面标「原文已更新」提醒可能过时——比默默显示一句和原文对不上的中文要好。
新公告没有译文就回落英文并标「未翻译」。这份文件由 `bun run mimo:content` 顺手校验
（每条必须有 `zh`，缺 `en` 只提示不报错），和 insights.json 一样挡住中文引号写成半角
导致 JSON 截断的低级错误。

**译文是模型自动补的（`translate.ts`）。** 每次 `sync.ts` 把数据入库、重建完索引之后，
会调一次 `src/translate.ts`：把仓库里的公告和译文文件对一遍，
挑出"没有译文"和"`en` 和现在原文对不上"的两类，剩下的不动——所以**人工润色过的译文
不会被模型覆盖**，只有原文真的改了才会重翻。译文文件和 store 里的公告顺序一致（新的在前），
`note` 字段也原样保留。

模型走 env（和 `scripts/image_prompt.py` 同一条通路）：`OPENAI_BASE_URL` / `OPENAI_API_KEY`
必填，`TEXT_MODEL` 选填（默认 `glm-5.3-flash`，缺了回落到 `VLM_MODEL`）。
一个请求最多 8 条公告、默认 2 个请求并发，批之间用固定大小的池子跑，批内一次调完。
返回要求是一个 `{"<id>": "<译文>"}` 的 JSON 对象，解析时容错一层 ```json 围栏，
译文为空、没有中文、或者和原文一模一样的都算失败——整批重试，重试还不行就跳过，
**不让翻译失败把整次同步判死**（数据已经入库了，译文下次补）。退出码只有单跑时才用得上：
有翻失败的条目就是 1。

prompt 里把两件容易翻错的事写死了：**哪些词保留英文**（`pro` / `flash` / `mimo-v2.6-pro`、
数据集与评测名 `cyber` / `DeepSWE`、`GPU OOM` / `VRAM` 这类缩略语、以及 `rollout`）和
**哪些说法要给地道译法而不是逐字硬译**（`at step 17` → 第 17 步、`from step 15` → 从第 15 步、
`the pro run` → pro 这一轮、`grader deployment` → 判分服务、`expert load imbalance` →
专家（expert）负载不均衡……）。`expert` / `grader` 这类有通行中文名的写成"中文（英文）"，
所以 `grader` 会是"判分（grader）服务"而不是光秃秃一个英文词。
prompt 里还钉了两条人工译文当示范，把语气和断句固定住；要调风格就改 `translate.ts`
里的 `KEEP_EN` / `GLOSSARY` / `EXAMPLES` 三块，然后 `bun run mimo:translate -- --force`
重翻一遍。

**顺带一提，步号关联不需要额外做。** 面板上的 `pro@s17` 是前端从 `/api/status` 的 step
事件现算的（第 7.3 节的公式），新公告一入库就自动有步号，回放切面里拿到的还是那一刻的进度；
`translate.ts` 只是把同样的口径再算一遍打在同步日志里，方便对一眼，不落盘——
落盘反而会因为重跑改写步号完成时刻而变旧。

**面板为什么默认是收起的。** 第一版是"全部公告 + 固定高度滚动"，实际用起来有两个毛病：
首屏被这块占掉 531px（状态卡和图表全被顶到第二屏），而且滚动区下沿正好把某一条公告
拦腰切断，看着像排版坏了。现在改成：默认只渲染最近 3 条（不设高度、不滚动，所以不存在
半截行），更早的点按钮才展开成滚动区；滚动区底部加一道 `mask-image` 渐隐，
滚到末尾就把渐隐去掉——"下面还有"和"到底了"该是两种不同的样子。
定位滑杆同理，默认收起：两条滑杆加提示文字是 84px，用不上的时候没必要一直杵在那儿，
所以挂在标题右侧一个"定位"按钮后面，开合状态记在 localStorage。

**定位滑杆的位置要单独存。** 面板会因为展开、切语言、切"对照原文"而整块重画，
重画后滑杆会回到默认的"最新一步"，而高亮还停在旧公告上——读数和指针不一致，一眼就看出来。
所以当前位置存在 `nz.pos[run]` 里，渲染时按它回填，重画不掉。

**详情框的统计行也顺手收了一下。** 左栏让出 400px 给解读之后只剩约 640px，原站给 run 名
留的 `min-width: 240px` 会把一排统计挤成两行（`mean`/`points` 掉到第二行），
看着像错位。遥测层把名字改成按内容宽、行内间距从 16px 收到 12px，一行就放得下了。

## 7.4 自定义看板是怎么做的

首页那批图来自 `/api/runs` 的 `pins`（18 个指标名），app.js 在 `renderOverview()` 里
`for (const tag of S.cfg.pins) grid.appendChild(chartCard(tag))`。**换一组图 = 换这个数组**，
所以遥测层的做法是：自己维护若干"看板"（一个名字 + 一串指标名），切 Tab 时把
`S.cfg.pins` 换成这个看板的数组，再让 app.js 重画当前视图。

为此在 `M.bind({...})` 里多交出去四个句柄：

```js
pins: (tags) => { if (tags) S.cfg.pins = tags; return S.cfg.pins; },
render: () => renderView(),
union: () => (S.union ? S.union.list : null),
board: (grid, tags) => { /* 只换图表区里的卡片，见下面「切 Tab 只换图表区」那段 */ },
```

`pins` 传空数组以外的值时写入并回读（`app.pins()` 不带参数就是读），`render` 重画当前视图，
`union` 给出全部指标名（批量勾选弹窗要列全量），`board` 原地换图表区（切 Tab 的主路径）。
前三个都是 1 行的箭头函数，`board` 十来行，是这一层唯一新增的原站改动。

**为什么沿用 app.js 的 `chartCard` 而不是自己画。** 自定义看板里的图和首页的图必须是同一种东西：
悬浮十字线、右上角值列、x 轴 step/time 偏好、图表联动（第 7.2 节靠包 `Charts.Line` 接进去）、
点标题弹解读（第 7.1 节靠 `#modal` 的 class 变化接进去），这些能力全都挂在 app.js 造的卡片上。
自己渲染一遍等于把这些能力再实现一次，而且以后站点加功能又会漏掉。

**站点原始那批图要自己留一份底。** `S.cfg.pins` 一旦被改写就拿不回原值了，
"默认" Tab 也就没内容可切。而 pins 只在 `/api/runs` 的响应里，所以遥测层在
`window.fetch` 拦截器里对 `/api/runs` 多做一步：`res.clone().json()` 把 `pins` 抄一份存着
（`noteSitePins()`），`api()` 和离线包的 `bundleApi()` 两条路也各调一次。
离线包里 `BUNDLE.config.pins` 就是原值，一样能抄。

**看板存在 localStorage（`telemetry.boards`）。** 形如
`{active: "<id>|default", list: [{id, name, tags: [...]}]}`。放本地而不是写进仓库，
是因为"我想看哪几张图"是个人偏好，不是站点数据；放 localStorage 也顺带让离线副本（`file://`）
照样能建 Tab。指标名可能因为站点改版而失效，编辑弹窗会把"站点已没有这些指标"
单独列一组，方便删掉。

**UI 分三块，都在遥测层：**

| 在哪 | 是什么 |
| --- | --- |
| overview 图表区上方 | Tab 栏（默认 / 各自定义 Tab / ＋新建）、`本 Tab N 张图`、编辑、清空 |
| `#metrics/<族>` 的每张图卡 | 左上角勾选框 + 底部浮动的 `已选 N · 全选本页 · 清空 · 加入看板 ▾` |
| 编辑弹窗 | 左侧按指标族分组、右侧折叠块勾选，搜索 / 只看已选 / 清空全部 / 删除 Tab |

注入点和联动、公告面板一样：`#main` 上的 `MutationObserver` 每次 DOM 变动跑一遍
`ensureBoards() / ensurePickBoxes() / ensurePickBar()`，缺了就补。这里踩过一个坑：
**写 `innerHTML` 本身也会触发这个观察器**，`renderBoardBar()` 每次无条件重写就会自己点自己，
页面直接卡死。现在它先算一个签名（active + 各 Tab 的名字和数量），一样就返回，不碰 DOM；
浮动条的显隐和计数也各自做了同样的事。

**切 Tab 只换图表区，滚动位置不跳。** 第一版走的是 `render()` 整页重画，结果是每点一次 Tab
页面就跳一下：`renderOverview()` 先把 `#view-overview` 清空（`root.innerHTML = ...`），
文档高度瞬间掉到只剩页头，浏览器顺手把滚动位置夹回顶部，等图表重建完位置已经回不去了
—— 用户正看着第 12 张图，切个 Tab 就被送回页首。现在 `M.bind()` 里多交一个
`board(grid, tags)` 句柄，app.js 只做"销毁这个 grid 里的卡片 + 原地建新的"：
把落在 grid 里的记录从 `S.cards` 摘掉、destroy 图表、`grid.innerHTML = ""`，
再按新集合 `chartCard(tag)` 逐个建。页头、状态卡、公告、基准、批组成一个都不动，
实测切 Tab 前后 `window.scrollY` 和 Tab 栏的视口位置完全不变。

`applyBoard()` 仍然先比对 `app.pins()` 和目标集合，一样就什么都不做 —— 这是防
"注入 → 重画 → 再注入"循环的第二道闸；只有图表区还没渲染出来时才退回整页重画，
那条路上会把滚动位置还原回去。编辑弹窗里连续勾选不立刻应用（每次应用都要重建这一组图表），
改成 500 ms 防抖 + 关弹窗时兜底一次。

## 7.5 相关性分析是怎么做的

用户在图上点住某一步之后，最自然会问的是"这一步为什么跳"。这个问题不能靠一条曲线回答，
得把同一步的横截面、历史上的同涨同跌、以及这一步时段内的工程事件三样东西摆在一起。

### 入口怎么接上去

`onChartClick()` 本来只做一件事：把步号记进 `sync.step`。现在多记两样：

- **锚点**：点的是哪条曲线。普通指标图从 `card.__card.tag` 拿（app.js 的卡片记录挂在元素上），
  评测榜卡片没有 tag，所以在那张卡片上加了 `data-bench`（app.js 的第 4 处补丁）。
- **run**：两个 run 在 step 轴上完全对齐，光看 x 分不出来，所以拿点击点跟"这一步上各条曲线的点"
  比**像素距离** —— 离哪条近就是点了哪条。只在有这一步取值的曲线上比，免得某条曲线缺这一步而被算到隔壁步。

角标上于是多了一行锚点名和一个 `分析这一步` 按钮；图表详情框底部也放了同一个按钮
（没锁步时用这张图的最后一步当默认值），不用先开联动也能进。

### 算在哪里

`/api/correlate`（server.ts 里新增）从 SQLite 取某个 run 的**全部**指标序列 —— 2000 个左右，
页面手里没有全量序列，所以这一层必须在服务端。返回三块：`movers`（这一步异动最大的指标，
按族折叠）、`corr`（与锚点同涨同跌的指标）、`context`（时段内的重启 / 版本切换 / 公告 / 相邻步）。

算法内核单独放在 **`site/js/correlate.js`**，写成 UMD：浏览器用 `<script>` 加载挂到
`window.TelemetryCorrelate`，server.ts 用 `await import(...)` 拿同一份。**只有一份实现**，
所以在线和离线算出的数字一致（离线时 `bundleApi` 里新增一个 `/correlate` 分支就地算，
理由是离线包里本来就有全量序列）。

### 三个口径决定

1. **异常度取 z 与 MAD 两个尺度里较小的那个。** 变化量的标准差（z）会被单个离群点撑大，
   所以再加一个中位数/MAD 尺度（zr）；但反过来，轨迹级 `max`/`min` 这类常年贴着上限的指标
   其变化量的 MAD 几乎是 0，只看 zr 的话任何轻微抖动都会算成几十倍标准差、霸占排行榜。
   两个都算、取较小值，等于要求"两种尺度下都算异常"。
2. **按族折叠。** `dataset-xxxx`、`harness-xxx`、以及 `partial/` 下的数字桶都归一成通配符，
   同族只留最反常的那个、其余收进 `members`。不折叠的话 33 个 code 数据集会把前几名占满。
   折叠只是为了可读，不是统计口径，所以 UI 里能展开看同族明细。
3. **`tagset_versions` 的语义要写对。** 面板的"这一步的时段内"会列出看板指标集快照的变化。
   它**不是训练配置版本**：`tags.json` 里版本串 `3-5513.<步>.<x>.<y>` 的第二段就等于当时已完成的步号
   （pro 的 9 条快照逐条核对全中），`n` 是那一刻的指标名条数。清单变了说明**看板暴露了新的指标名**
   —— 这是遥测口径的变化，对"这一步为什么跳"仍是有用的上下文（新老指标的跨步比较要小心），
   但不能读成训练改了配置。字段名特意叫 `tagset_versions` 而不是 `versions`，就是为了不让人误读。

4. **一阶差分相关。** 两条都在爬升的曲线天然高度相关（`dynsam/avg@n` 与长度的水平秩相关
   有 +0.79/+0.93），所以必须同时给"去趋势"那一列 —— 对两条曲线各取相邻两步之差再算秩相关。
   面板的提示语就写着"先看这一列"。

另外还有两个更小的口径：`training/global_step`（纯步数计数器）直接拉黑，它和所有随时间变化的
指标都会高相关；sparse 的评测榜序列用成对删除，样本量随指标变化，所以每行都显示 `n=`。

### 一个防坑

事件流（`events.json`）是滚动保留的 —— 仓库里 flash 的事件从第 8 步才有。所以早期步查不到重启时，
面板不能说"没有重启"，只能说"查不到"。`/api/correlate` 会在"这一步完成的时刻早于事件流第一条"
时额外推一条口径提示，和它并列的还有三条固定提示（小样本、伪相关、相关不等于因果）。

| `site/index.html` | 加 6 行（遥测层样式 1 行、`js/correlate.js` 与 `js/telemetry.js` 各 1 行 + 3 行注释） |
| `site/offline.html` | 生成物：`mimo:export` 从 `index.html` 派生，多插一行 `data/bundle.js` 并改标题 |

图表联动（第 7.2 节）、公告面板（第 7.3 节）、自定义看板（第 7.4 节）、
相关性分析（第 7.5 节）和表格逐列解读（第 7.1 节第 5 个入口）
全部落在 `site/js/telemetry.js`、`site/telemetry.css` 和 `site/js/correlate.js` 里，
`charts.js` 一行没动——联动靠包构造函数接进去，公告面板靠观察 `#notices` 的 DOM 变化接进去，
自定义看板靠 `M.bind()` 交出来的 `pins / render / union / board` 四个句柄，
相关性分析靠 `M.bind()` 交出来的 `board` 句柄加上新增的 `/api/correlate`，
表格逐列解读靠事件委托（表格本身由 app.js 渲染，遥测层只接点击）。

app.js 那 6 处补丁里，`M.bind({...})` 是四个句柄加 `refresh` 的首屏竞态护栏；
回放要用的有四处：`Telemetry` 空壳、`isFinal` 不算回放里的 run、`vnow` 冻结在切面时刻、
状态词换成切面时间；另外两处是给评测榜卡片加 `data-bench`，以及采样器明细的粒度提示。

> 首屏竞态：直接带 `?asof=` 打开时，遥测层的回放初始化会赶在 app.js 取到 `/api/runs`
> 之前调到 `app.refresh()`，那时 `S.cfg` 还是 null，`runs()` 会抛
> 「Cannot read properties of null (reading 'runs')」。这时 refresh 直接返回即可 ——
> boot 走完本来就会按当前切面渲染一次。这个错误只在带 `?asof=` 打开时有概率出现。

`sync.ts` 每次运行都会比对 `data/upstream/manifest.json` 里的哈希，
原站前端有改动会打印出来。**它不会自动覆盖 `site/`**，因为 `site/` 里有我们的改动；
需要时人工把 `data/upstream/` 里的新版本和 `site/` 对照着合。

## 9. 怎么定时跑

Windows 任务计划或者保持一个后台进程都行。最简单的是一段循环：

```powershell
while ($true) {
  bun src/sync.ts
  Start-Sleep -Seconds 1200
}
```

站点大约 3 小时完成一步，采集器大约 30 秒出一条报告，所以 **20 分钟一次**足够了。
再密也不会多出信息，只会让日志变长。

每次同步末尾会自动跑一遍公告翻译（第 7.3 节）。它只翻新增和原文改过的公告，
没有新公告时一次模型调用都不会发；确实不想让它联网调模型就加 `--no-translate`，
事后再单独跑 `bun run mimo:translate` 补。

要长期跑的话，注意 `data/store/runs/<run>/live.jsonl` 和 `timeline.jsonl` 是逐次追加的，
每 20 分钟一行，一天 72 行。`timeline.jsonl` 目前约 9 KB（18 个同步点），一年约 3 MB。
`live.jsonl` 从 2026-09-20 起每行会带上两次同步之间的采样器明细（约 40 条、10~17 KB），
它会是这两个文件里大的那个：按 20 分钟同步、两个 run 估算，一天约 1.5 MB。
觉得占地方就把同步间隔放长——间隔越长，明细窗口（30 分钟）之外的部分本来也抓不到。

## 10. 扩展方向

- **接更多 run。** `paths.ts` 和 `store.ts` 里没有硬编码 run 名，
  同步逻辑是按 `/runs` 返回的列表循环的。新增 run 会自动被采集。
- **存 rollout 级明细。** 现在只存了按步聚合的指标。如果要存每道题的结果，
  数据量会上一个量级，那时候应该换 Parquet 或者 DuckDB，见第 4 节。
- **加派生指标。** `docs/01` 第 7 节那几条关系式（成本恒等式、KL 加权和、
  staleness 加权和）已经做成 `check.ts`，跑一下就逐条验算，全部通过退出码是 0，
  可以挂到定时任务里当哨兵——站点改了算法它会第一个发现。

  ```bash
  bun src/check.ts
  ```

  目前 22 项全部通过。它发现过两件我原本想当然的事：`partial/` 的桶数 pro 是 8 个、
  flash 是 10 个（写死 8 会让 flash 的加权和对不上）；以及 `ctx_total = prompt + response`
  并不是数学上精确，只是精确到站点给的 6 位有效数字。
