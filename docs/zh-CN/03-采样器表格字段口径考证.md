# 动态采样器表格字段口径考证（2026-09-20）

## 一句话结论

`mimo.xiaomi.com/rl` 那个「dynamic sampler」面板的按数据源表格，五个列名都出自站点自己的前端代码，但**站点没有为任何一个列写过文字说明**；我用 29 份采样器留档把其中的加总关系全部复算了一遍，**四列（source / accepted·target / remaining / judged / in flight）里除“judged、in flight 的计数单位”之外都能钉死**，只有最后一层语义（计的是题还是序列、是否含跨步 partial rollout）没有公开依据，因此**这一层没有写进遥测页面**，只留在这份记录里等人工反馈。

---

## 1. 为什么要做这件事

任务要求：给采样器面板的表格加逐列解读，并且「不能理解的数据不要写进页面」。
问题是这张表的口径一直标着“未确认”——仓库文档 `docs/01-网站数据文档.md` 原本写的是：

> `ds` 的四个数只确认了第一个是“该数据集已受理的序列数”。剩下三个没有公开说明。

这次要回答三个具体问题：

1. 面板把 `ds` 四元组 `[a, b, c, d]` 渲染成哪几列？（列名算不算“官方口径”？）
2. 每一列的数能不能用数据内部的关系复算出来？
3. 哪些说法有公开材料（论文/技术报告/博客/GitHub）背书，哪些没有？

## 2. 结论速览

| 列 | 页面上的标签 | 能确认什么 | 不能确认什么 | 页面怎么写 |
| --- | --- | --- | --- | --- |
| 第 1 列 | `source` | 数据源键名形如 `类目/dataset-短码`；类目取自站点 `categories`（code/general/visual/chat/cyber）；两个 run 的行集合不同（pro 没有 cyber） | 短码对应的数据集内容 | 直接解释键名结构，不下钻内容 |
| 第 2 列 | `accepted / target` | `Σaccepted == 面板 accept`、`Σtarget == 面板 target == 1568`，29/29 份留档成立；`target` 是每个数据源的采样配额（公开材料：MiMo-V2-Flash 技术报告 §4.6.2） | 无（这两项已可复算） | 完整解读 |
| 第 3 列 | `remaining` | **页面现算**：`Math.max(0, target − accepted)`，不是接口字段（原站 app.js） | 无 | 完整解读（并指出它不是面板顶部那个 `remain`） |
| 第 4 列 | `judged` | `Σc(上报源) + Σaccepted(未上报源) == 面板 judged`，29/29 份成立；`c ≤ accepted`，232/232 个非空值成立；只有固定的 8 个 code 数据源上报 | 计数单位是题还是序列；是否含跨步 partial rollout | 只写“站点标为 judged + 这条恒等式 + 覆盖范围”，不写机制断言 |
| 第 5 列 | `in flight` | `Σd == 面板 remain + remain_partial`，29/29 份成立（最大差 2）；步内先涨后落、步末收干 | 逐源拆分口径；计数单位 | 同上：写合计恒等式与步内形状 |
| 合计行 | `total` | 合计行的 `judged` 用的是**面板整体值**，不是各列相加 | 无 | 单独提示这个陷阱 |

「批组成」两张表的列（category/prompts/share/Δ share、harness/rollouts/share）能从前端代码直接读出推导公式，已一并解读。

## 3. 数据核验：方法与结果

复算脚本：`src/sampler_report.ts`
数据：`data/store/runs/{pro,flash}/live.jsonl`，每次同步留档一行 `latest`；截至 2026-09-20 共 **29 份**（pro 18 / flash 11）。

| 恒等式 | 结果 |
| --- | --- |
| `Σ accepted == 面板 accept` | 29/29 |
| `Σ target == 面板 target == 1568` | 29/29 |
| `judged_of == accept` | 29/29 |
| `Σ c(上报源) + Σ accepted(未上报源) == 面板 judged` | 29/29 |
| `accept − judged == Σ (accepted − c)`（只减上报源） | 29/29 |
| `c ≤ accepted` | 232/232 个非空值 |
| `Σ d == 面板 remain + remain_partial` | 29/29，最大差 2（同步取整） |

一步之内的行为（用来确认这些列是“过程量”而不是“步末值”）：

- pro 第 15 步（9 份留档）里，上报源的 `Σc/Σaccepted` 从 **0.879 升到 0.965**，同期面板整体的 `judged/accept` 从 **0.943 升到 0.981**，两条曲线同向收敛。
- pro 第 15 步的 `Σd` 是 **1066 → 1203 → 1474 → 1530 → 1545 → 1537 → 1326 → 861 → 720**，先涨后落；flash 第 20 步是 **2956 → 2073 → 1162 → 640**，一路收干。
- 最新一份 pro 留档（step 28）：`accept 1840 / target 1568`，`judged 1766`，其中 8 个上报源 `Σc = 870`、其余源 `Σaccepted = 896`，`870 + 896 = 1766`；`Σd = 1594`，同刻 `remain + remain_partial = 1593`。

顺带确认了两个容易混的量：

- 面板 log 里的 `passrate` 与序列里的 `dynsam/avg@n` **不是同一个数**（例：flash 第 27 步 `0.545` vs `0.644`），因为前者是当前采样批的通过率、后者是这一步训进去那批 prompt 的平均通过率。
- 面板的 `pr0 / pr1` 与序列里的 `dynsam/passrate/zero / one` 是同一个统计量（例：pro 第 23 步 `0.131` vs `0.131014`、`0.242` vs `0.241739`），差在快照是步内过程值。

自检已把前三条恒等式写进 `bun run mimo:check`，随每次自检跑（当前 29 项全过）。

## 4. 公开材料检索结果

**官方材料：只解释机制，不定义字段。**

- MiMo-7B 技术报告（arXiv:2505.07608）§3.3.2 讲了“简单题回采池”：满分题被动态采样滤掉后存进池子、再按比例采回（对应看板上的 `carryover`）；§3.4.1 讲了连续 rollout、异步判分、early termination（凑够 batch 后按 FIFO 终止在途任务），并给出 “Sample Waste Ratio = 多采出来的有效样本 / batch 需求” 的定义——这是“受理量超过目标”的机制背景。
- MiMo-V2-Flash 技术报告（arXiv:2601.02780）§4.6.2 Data Scheduler：每个数据源有独立的 `sample quota`，并按通过率和配置比例决定受理量；动态采样中序列返回后参考历史通过率继续派题，并用 partial rollout 把超长轨迹分到多步。**这是「accepted / target」两列最接近的官方依据。**
- DAPO（arXiv:2503.14476）的 dynamic sampling：过采样后滤掉通过率为 0 和 1 的题，保证 batch 里有有效梯度。
- 站点自己的 `api/runs` 里 22 条 `descriptions` **没有** `accept / target / judged / in flight / remain / prewarm` 任何一条；站点 blog 只有一篇 MiMo-V2-Flash 发布文，不含采样器内容。

**第三方材料：只有一篇逐字段讲过，且作者自己标注是解读。**

- 量子位 2026-09-17 的报道描述了采样面板背后的异步流水线（“有的 Agent 还在环境里执行、有的等判分、有的在算 Reward”），但没有定义列。
- `bingqiangzhou.github.io/posts/xiaomi-mimo-rl-live/` 是目前唯一逐字段讲这张表的公开材料，作者明确写“我从 dashboard 里读出来的设计细节”。它把 `in flight` 读成“样本还在沙箱里跑着”，与我们的数据不冲突，但**它不是官方说明**，只能当旁证。

**站点公告提供了两条旁证。**

- “there was a network connectivity issue between the pro training cluster and the **grader deployment**.”
  —— 站点自己承认存在一个独立的判分服务，这是“judged 数的是判分进度”最强的官方旁证，
  但仍然不是对这个计数器的定义。
- “we **filtered out tasks that are relatively easy** for the current pro model.”
  —— 官方直接说明简单题会被过滤，这正是受理量会超过配额、还要继续补采的原因。
- 另外站点 `descriptions` 里 `env/active` 的定义是 “sandbox environments in flight”，
  说明 “in flight” 是站点自己的用词习惯（在途），但那是环境数、不是这张表的列。

**GitHub：有 5 个第三方镜像，其中有的把列名弄反了，但没有一个做过逐列解读。**

按仓库名检索（2026-09-20），共有 5 个项目在抓这份数据，全部建于 2026-09-17、0 star：

| 仓库 | 它干了什么 | 能不能当依据 |
| --- | --- | --- |
| `AbhyudayPatel/rl-observatory` | 忠实透传：把 `live.judged` 当一等字段读出来，不把四元组第三位叫 in flight | **可以当独立交叉验证**（它的实现与原站列名一致） |
| `LianxinRay/mimo-rl-mission-control` | 采集脚本注释写「每源 `[accepted, target, in_flight, x]`」，页面把**第三位**（原站标 `judged`）渲染成表头 `IN FLIGHT` 并丢掉第四位 | **反例，不要用**；它把 c、d 弄反了 |
| `Project516/mimo-rl-status` | 只做状态展示 | 不涉及列口径 |
| `YYY-676/mimo-rl-archive` | 纯粹存档接口快照 | 不涉及列口径 |
| `ashafizullah/mimo-baby` | 白话复述 | 不涉及列口径 |

也就是说：公开的开源遥测里，既有一个和我们的列映射一致的实现，也有一个把它弄反的，
但**没有任何一个项目对 `ds` 四元组做过逐列解读**。

**开源框架的命名对照。** 检索了 verl、slime、OpenRLHF、ROLL、AReaL 等框架：
**没有任何一个框架用 `accepted / target / judged / in flight / remaining` 这整套列名，
更没有任何框架有叫 `judged` 或 `judged_of` 的指标。**
最接近的是 AReaL 的逐 rollout 计数 `stats.{enqueued, running, accepted, rejected}`
（有 `on_rollout_accepted/rejected`，说明 `accepted` 是真实的框架词汇，但没有 `judged`），
以及 slime 的 `remaining_batch_size`（“待处理任务数”）+ `--over-sampling-batch-size` + `pop_first`（FIFO 取回）、
verl 的 `filter_groups` / `num_prompt_in_batch` vs `train_batch_size`。
`in_flight` / `inflight` 在若干框架里出现过（TRL、NeMo-RL、rLLM、ROLL 等），
但含义都是“当前在途的请求/会话”或 partial rollout 的新老权重混合，
**从来不是“按数据源拆、合计等于 remain + remain_partial”的那种在途量**。
这说明看板上的列名是 MiMo 自己的 UI 词汇，不是从某个框架继承的，所以框架文档里查不到。
（注：上表中除 rl-observatory 与 mission-control 外，另有若干框架的字段名来自二手材料、
未逐一核对到源码文件，只作线索，不写进页面。）

**容易混淆的“同名指标”。** 站点的指标树里确实有一组带 `judge` 的指标
（`penalty/stage_credit_group/judge_pool_in_flight`、`judge_pending`、`groups_judged`、
`judge_pass1_attempts` 等），但它们属于另一套子系统（判分组/信用分配），量级只有几十到一百，
和这张表里合计约 1600 的 `in flight` 不是一回事。**不要用它们来验证这一列。**

## 5. 仍未确认、留待人工反馈的部分

下面这些**没有写进页面**（页面只写了能复算的结构），也没有放进解读正文：

1. **`judged` / `in flight` 的计数单位。** 已知“面板 judged = 上报源的 c + 未上报源的 accepted”，
   但 `c` 和 `d` 数的是**题（prompt / 题组）还是 rollout 序列**（每题 16 条），
   以及是否把 partial rollout 的片段算进去，没有任何依据。这两列在数据里都能对到面板自己的
   合计，但合计本身也没有单位说明。最自然的读法是“题”，但这是推断，没有写进页面。
2. **为什么恰好是 8 个 code 数据源上报 `c`。** 这 8 个源在两个 run 上完全相同
   （bvg7 / v7yx / dnpn / ta4j / sin0 / obg8 / zg6q / x7wh），而且**“空值 = 受理量没到配额”这个猜测是错的**
   （反例：`[172, 154, null, 86]`、`[57, 55, null, 187]`）；同为 code 的 `4onq / m1dt / yfch`
   也一直是空。所以空值是按“数据源/判分方式”切的，不是按进度切的。
   合理猜测与“需要跑测试用例判分的 code 数据走独立 grader 管线”有关
   （站点公告里确实出现过 “grader deployment”），但**没有任何公开文字能证实**，
   页面只写了“覆盖固定”这个事实。
3. **`in flight` 的逐源拆分口径。** 合计恒等于 `remain + remain_partial`，但为什么有的源 `in flight` 会比它自己的 `accepted` 还大（例：最新 pro 留档里 `code/dataset-obg8` 是 257 vs 155），无法从现有数据判断。
4. **`remain` / `remain_partial` / `remain_seq` 三者的关系。** 面板 log 把它们标成 “remaining / partial / rewarding”，其中 `remain_seq` 被标为 “rewarding” 是站点自己给的唯一语义线索；这三个桶是否互斥、`in flight` 是否只取前两个，没有依据。
5. **`working` / `prewarm_wait` / `partial`（三元素数组）没有页面标签**，本次没有解读。

**给人工的判断建议**：等小米按罗福莉说的开源细节，或直接去问看板作者；在此之前，这五条不应该以任何确定语气出现在页面或 README 里。

## 6. 页面最终发布了什么、没发布什么

**发布（`content/_draft/table-columns.json`，7 条，分组「采样器表格」）**：

- `table/sampler/source`、`table/sampler/accepted-target`、`table/sampler/remaining`、`table/sampler/judged`、`table/sampler/inflight`
- `table/comp/trained`、`table/comp/metric`

写法上做了三条约束：能复算的恒等式直接写并给数字；列名一律注明“出自原站渲染代码”；公开材料只写到机制的一律标成“背景/旁证”，并把第三方解读明确标为“外部解读，不是官方说明”。第 5 节里那五条不确认的内容没有进入正文，只在 `judged` / `in flight` 卡的「容易读错的地方」里写了“计数单位没有公开说明”这句否定式提示。

**没发布**：第 5 节全部五条、以及任何“先超量接受再裁剪”“七状态机”这类第三方说法（只在溯源里以「背景」立场出现，并注明是外部解读）。

## 7. 怎么自己复核

```bash
# 采样器表格的逐条恒等式（就是本文档第 3 节的表）
bun src/sampler_report.ts

# 同样的恒等式随仓库自检一起跑
bun run mimo:check

# 产物（可复算的原始数字）
analysis/zh-CN/numbers/A3-sampler-numbers.json
```
